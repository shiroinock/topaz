## Phase 0 実装決定ログ

Phase 0(`fib(34)` を C 経由でネイティブビルドして動かす)を実装する過程で確定した、設計検討時点で開いていた選択肢の解:

- **パーサ**: `typescript` パッケージの tsc API。`ts.createSourceFile` を呼ぶだけの薄いラッパで Phase 0 は十分。乗り換え条件は `docs/parser-choice.md`。
- **runtime のレイアウト**: header-only、`static inline` 関数。Spinel の単一ヘッダ流儀を踏襲。Phase 0 では `topaz_number`(= `double`)と `topaz_console_log_number` のみ。
- **codegen の C 出力スタイル**: 全関数を `static`、トップレベル文は `int main(void)` に包む。前方宣言を全関数まとめて出してから定義。
- **未対応構文の扱い**: codegen 中に `CodegenError` を `file:line:col` 付きで投げて停止(`MEMO §3.1` の方針を実装に落とした形)。
- **number → 文字列**: Phase 0 は `printf("%.17g", n)`。`3.14` が `"3.1400000000000001"` になる divergence あり。Phase 1.2 で shortest round-trip(`snprintf+strtod` ループ)に差し替えて解消。
- **CLI のデフォルト出力**: `<input>.ts` の隣にバイナリと `.c` を落とす。`--emit-c-only` で cc をスキップして生成 C を残せる。`.gitignore` で `examples/` の生成物は無視。

## Phase 1.1 実装決定ログ

- **`boolean` の C 表現**: `<stdbool.h>` の `bool` を `topaz_boolean` に typedef。`int` を直接使うのではなく `bool` にすることで、生成 C 側で「真偽値」と「数値」が混ざる事故を C コンパイラの警告層でも捕まえやすくする。
- **条件式は strict boolean**: `if`/`while`/`for`/`do-while` の条件に数値を渡すとコンパイルエラー。`if (n !== 0)` のように明示させる。JS の truthy/falsy を持ち込まないことで、後段で `number` 以外の型(`null`/`undefined`/オブジェクト)を入れた時の意味論ブレを未然に防ぐ。
- **`==`/`!=` は未対応エラー**: `===`/`!==` を使えとメッセージで誘導。Phase 1.1 時点で `Number(x) == "1"` のような暗黙変換を実装する利得がないため、最初から切る(`§3.1` 「禁止じゃなく未対応」の応用)。
- **`let`/`const` は初期化必須**: 未初期化の局所変数を C にそのまま落とすと不定値の読み出し UB を踏む。JS の `undefined` セマンティクスを Phase 1 では実装しないので、「明示初期化を要求する」方が単純で安全。
- **型推論の置き場所**: 専用の TypedAST 層を切る前段として、Phase 1.1 では `Emitter.inferType` が AST を式単位で歩く軽量実装で済ませる。`MEMO §5` の流れ図でいう「TypedAST」「全プログラム型推論」を 1.2〜1.5 の中で切り出していく。
- **for-init は単一宣言**: `for (let i = 0, j = 0; ...)` を許すと、型が混じった場合に C の for 構文に乗らない。単一宣言だけ受理し、複数変数を回したい場合は外で `let` しておくスタイルに統一。
- **scope と関数シグネチャ**: 関数の前方宣言が全関数ぶん最初に出るのを利用して、本体 emit より先に全関数の戻り値型を `functionReturns` に登録する。これで相互再帰しても型解決できる。
- **`%` は C の `%` でとりあえず出している**: 浮動小数では JS の `%` (= `fmod`) とずれる。整数領域では一致するので Phase 1.1 のサンプル(`loop_sum`/`while_count`)に影響しないが、Phase 1.2 で Ryu と一緒に `topaz_fmod` 経由に差し替える宿題。

## Phase 1.2 実装決定ログ

- **`%` の lowering**: `topaz_number` の `%` / `%=` は常に `topaz_fmod(a, b)` に下ろす。C の `%` は整数型限定でそもそも `double` を受けないため「整数領域なら同じ」という Phase 1.1 のコメントは正確ではなく、Phase 1.1 のサンプル(`loop_sum`/`while_count`)が `%` を使っていなかっただけで、`%` を含むコードは Phase 1.1 では一切コンパイルできない状態だった。`topaz_fmod` は `<math.h>` の `fmod` を `static inline` でラップしただけのもの。
- **shortest `number → string`**: Ryu(d2s)の本家ポートは ~1500 行のテーブル付きで取り込み・検証コストが大きいので、Phase 1.2 では `snprintf("%.*e") + strtod` の精度探索(p=1..17)で shortest 桁数を見つけ、ECMA-262 ToString の場合分け(`k <= n <= 21` / `0 < n <= 21` / `-6 < n <= 0` / それ以外は指数表記)で出力する実装にした。観測上の出力は Ryu と一致するはずだが、最悪 17 回 snprintf+strtod を回すので、Ryu に比べて 1〜2 桁遅い。perf に敏感な用途が顕在化するまでは置いておく(Phase 2 のベンチ整備で差し替え)。
- **`switch` lowering**: C の `switch` は整数型しか受けないので、`do { if (d === c1) { ... } else if (...) { ... } else { default } } while (0)` の if/else ラダーに落とす。`break` は do/while の `break` でそのまま switch を抜ける。trade-off として、`switch` 本体内の `continue`(外側ループに対する continue)は do/while(0) で吸われてしまうため、AST の親をたどって「switch を間に挟む continue」を検出して `CodegenError` で落としている。JS の暗黙 fall-through は禁止(非空 case は terminator で終わる必要あり)、`default` は最終 clause のみ許可、case ラベルは判別式と同型のみ。`number` / `boolean` / `string` 判別式に対応(string は `topaz_string_eq`)。
- **`string` の表現**: `{ const char *data; size_t len; }` を値渡しで運ぶ。リテラルは C99 compound literal `((topaz_string){"abc", 3})` として埋め込み、`data` は string literal(静的寿命)を指す。連結は `topaz_string_concat` が `malloc` して詰める。Phase 1.5 まで GC/arena を持たないので連結結果はリーク前提。文字列リテラルは ASCII 限定で codegen 段で reject(JS の `.length` は UTF-16 code units、C 側のバイト長との divergence を回避するため)。
- **`+` の型分岐**: `inferType` で左辺を見て `topaz_string` なら右辺も `topaz_string` を要求して string 連結、それ以外は両辺 `topaz_number` を要求して数値加算。`+=` も同じ分岐。実装上は `inferType` を一度走らせて codegen 側で再度型を見るので少しもったいないが、Phase 1.3 以降の型推論層分離で解消する想定。
- **`.length` の扱い**: `PropertyAccessExpression` を `inferType` / `emitExpression` の両方で扱う最初のケース。今は `topaz_string.length` だけだが、Phase 1.3 以降 `Array<T>.length` でも同じ枠組みに乗せられるよう、`baseType + propertyName` で dispatch する形にしてある(現状は `if` 1 本だが)。

## Phase 1.3a 実装決定ログ(Array<T>)

- **Array<T> は monomorphize + reference 型**。`runtime.h` の `TOPAZ_ARRAY_DEFINE(name, elem_t)` マクロで要素型ごとに `topaz_array_<name>` struct(`data` / `len` / `cap`)と `_new` / `_reserve` / `_push` / `_pop` / `_at` / `_set` 関数群を生成。codegen からは `number` / `boolean` / `string` の 3 monomorph に対して `topaz_array_number *` 等のポインタ型として扱う。代入で storage を共有する JS の semantics に揃えるため value 型(struct そのまま)ではなくポインタにした。
- **TopazType の拡張方法**。`type TopazType` を `topaz_number | topaz_boolean | topaz_string | topaz_array_number | topaz_array_boolean | topaz_array_string` の文字列ユニオンに増やし、`arrayElem` / `arrayOf` / `isArrayType` / `arrayShortName` / `cTypeName` のヘルパを足した。Phase 1.4 で nested array(`number[][]`)や任意要素型のジェネリクスを入れる時に、この文字列ユニオン表現は破綻するので、その時点で structured な型表現(`{ kind: "array", elem: ... }` 等)へ移行する。今は monomorph 数が小さく事前列挙できるので文字列で十分。
- **空 `[]` の型解決**。`inferType` 単独では要素型が決まらないので、`declareVar` から annotation 由来の expected 型を `emitArrayLiteral` に thread する。`expectType` を回避して直接 `emitArrayLiteral(initializer, type)` を呼ぶ経路を declareVar に作った。non-empty な配列リテラルは従来通り inferType でいける。
- **GCC statement-expression を活用**。`[1,2,3]` を `({ topaz_array_number *t = topaz_array_number_new(); ...push... t; })` の statement-expression に下ろす。compound literal で初期化リストを書けば一発で済ませたいところだが、`malloc`+`push` の手続きが要るので statement-expression が必要。`tmpCounter` で `__topaz_arr_<n>` を生成して衝突回避。
- **`[i] = v` の lowering**。`checkAssignTarget` を `ElementAccessExpression` も受理するよう緩め、`emitExpression` の `BinaryExpression` 分岐の冒頭で「LHS が ElementAccessExpression」かつ「単純代入」のときは `topaz_array_<name>_set(a, i, v)` を吐く特殊ケースを置いた。複合代入(`a[i] += v` 等)はインデックスを 2 回評価する書き下しが必要なので、Phase 1.3 では未対応エラーで明示的に弾いている(temporary を導入する lowering は Phase 1.4 以降)。
- **`.length` / `.push` / `.pop` の dispatch**。`PropertyAccessExpression` の `.length` は string と Array で別 C 式(`.len` vs `->len`)に展開。method call は `emitCall` から `emitArrayMethodCall` に分岐させた。`push` は void を返すので `inferType` 側で「式として使えない」エラーを出し、`pop` は要素型を返す。`console.log` も配列引数を整形ポリシー未定として明示的にエラー化。
- **bounds check の `!(i >= 0)` イディオム**。`NaN` を弾くために `i >= 0` の否定で書いている(`NaN < 0` も `NaN >= 0` も false)。`size_t` への変換時に負値が wrap して巨大値になる事故も同時に防げる。
- **Map/Set は次チャンクに分離**。実装には `new Map()` 構文サポート、key 型ごとの hash 関数、open-addressing マクロ、K×V monomorph 列挙、複数メソッド dispatch(`.set` / `.get` / `.has` / `.delete` / `.size`)が必要で、Array<T> と一塊にすると粒度が大きすぎる。「刻む」方針で 1.3 を 1.3a(Array)・1.3b(Map/Set)に分割した。

## Phase 1.3b 実装決定ログ(Map<K,V> / Set<T>)

- **K×V monomorph をプリ展開**。scalar 3 種(`number` / `boolean` / `string`)の全組合せで Map 9 個 + Set 3 個を `TOPAZ_MAP_DEFINE` / `TOPAZ_SET_DEFINE` マクロでヘッダ末尾に展開。`TopazType` の文字列ユニオンは Phase 1.3a 時点で「破綻直前」と書いた通りすでに苦しく、ここで template literal 型で `` `topaz_map_${ScalarShortName}_${ScalarShortName}` `` 形式に書き換えて静的列挙を継続。Phase 1.4 でジェネリクスを入れる段で `{ kind: "map", key, value }` 等の structured 表現へ移行する想定は変わらない。
- **TopazType を template literal で再構成**。Phase 1.3a 時点では string union を手で並べていたが、Map 9 monomorph を素直に並べると 18 行になるため、`type TopazType = \`topaz_${ScalarShortName}\` | \`topaz_array_${ScalarShortName}\` | \`topaz_map_${ScalarShortName}_${ScalarShortName}\` | \`topaz_set_${ScalarShortName}\`` に集約。`arrayElem` / `mapKey` / `mapValue` / `setElem` 等のヘルパは文字列を `slice` / `split("_")` で剥がす実装にして、scalar 名にアンダースコアを含めない不変条件で押し切っている(scalar 名を増やす時はこの不変条件を見直す)。
- **key の同値性は SameValueZero、`===` ではない**。JS Map / Set は SameValueZero(NaN === NaN、-0 === +0)を採用しており、Web で動いている TS コードの暗黙の前提もこれ。`topaz_key_eq_number` を `a == b || (a != a && b != b)` で実装し、ハッシュ側でも `-0 → +0` と NaN 正規化を行う。`===` 演算子のセマンティクス(NaN !== NaN)と意図的に divergence する点だけ CLAUDE.md に明記。
- **open-addressing + tombstone**。線形プローブで実装。slot state を 3 値(empty/occupied/tombstone)で持ち、`(size + tombstones + 1) * 4 > cap * 3` で grow 判定。`size * 2 < cap` なら同 cap で rehash(tombstone だけで太った場合の縮退)。初期 cap は最初の `set` / `add` で 8 にする lazy 確保で、空の Map / Set 1 個あたりのバイト数を抑えている。
- **`new Map<K,V>()` / `new Set<T>()` 構文サポート**。`NewExpression` を `emitExpression` / `inferType` / `emitNewExpression` の 3 箇所でハンドル。`Array` 用の `new Array()` は誤用率が高いので「`[]` リテラルを使え」というエラーメッセージで明示的に弾く。bare `new Map()` / `new Set()` は `[]` 同様 `declareVar` から expected 型を thread して受理する(`let m: Map<...> = new Map()` の TS で一番自然な書き味を守るため)。`expected` を持つ場所が declareVar しかないので、関数引数や return 値では型引数必須という非対称が残るが、Phase 1.4 で全プログラム推論を入れる時に解消するつもり。
- **メソッド dispatch は型別に分岐**。`emitCall` を `isArrayType` / `isMapType` / `isSetType` の 3 分岐に拡張し、各々 `emitArrayMethodCall` / `emitMapMethodCall` / `emitSetMethodCall` に流す。`inferType` 側でも対称に同じ分岐を入れ、`.set` / `.add` が void(式中で使えない)、`.get` / `.has` / `.delete` が値を返すというルールを片側だけに書かないよう注意。
- **`.size` は property、`.length` と同じ枠**。`isMapType(t) || isSetType(t)` の `.size` を `((topaz_number)(x)->size)` に下ろすケースを `length` のすぐ下に並べる。実装パスは同じだが、`.size` という名前は JS の Map/Set の API 上の決定で、`Array.length` と揃えてくれなかったのは諦めポイント。
- **`Map.get(k)` は key 不在で `abort`**。JS では `V | undefined` を返すが、optional / union を現状持たないので、`undefined` 相当を表現する手段がない。`.has` で先にチェックする運用にし、divergence は CLAUDE.md に明記。Phase 1.5 で `T | undefined` の narrowing を入れる段で、`Map.get` の戻り値を `V | undefined` に変えて narrowing 必須にする計画。
- **`Map.set` / `Set.add` は void**。JS では `this` を返すので `m.set(k, v).set(k2, v2)` がチェーンできるが、`Array.push` を void にしたのと同じ理由で void に倒した。チェーンしたい時にはエラーメッセージで「式として使えない」と教える。Phase 1.4 で `this` 型が入った後で再検討する宿題。
- **テスト**。`examples/map_set_basic.ts` で全 monomorph(Map<string,number> / Map<boolean,string> / Map<number,number> / Set<number> / Set<string>)、重複 add の冪等性、delete 後の `.size` / `.has`、50 要素入れての grow パス、`new Map()` の context typing、`Map.get` の存在 key からの読み出し を一通り叩いている。tombstone を多数生む `delete` ストレスは未カバー(load factor 計算と rehash 縮退パスの単体検証は今回ペンディング、Phase 1.5 でプロパティテスト基盤を入れる時に拾い直す)。

## Phase 1.4a 実装決定ログ(class)

- **TopazType の文字列ユニオン拡張で乗り切った**。Phase 1.3 時点で「文字列ユニオンは破綻直前」と書いていたが、class は monomorph 数が宣言数(ユーザー定義)に等しいだけで、map みたいに K×V の組合せ爆発がないので、`type TopazType = ... | \`topaz_class_${string}\`` を 1 行足すだけで対応できた。これでよい(structured 表現への移行は Phase 1.4c の generics で本格的にコンテナ要素型として class を入れる時に再検討する)。class 名は scalar 名と違って underscore を含み得るが、`isClassType` / `classNameOf` 系のヘルパは prefix を剥がすだけで full name を取り出すので問題ない。逆に `Array` / `Map` / `Set` を class 名にしようとすると built-in と衝突するので class 宣言時にエラーで弾く。
- **明示 constructor を必須化**。フィールドがあるのに constructor がない場合は `calloc` の zero-fill だけで初期化される(JS の `undefined` セマンティクスは持っていないため)。reference field を NULL のまま渡すと segfault するし、scalar field でも 0/""/false が JS の `undefined` とは divergence するので、フィールドを持つクラスには constructor を要求するルールにした。フィールド 0 個のクラス(タグ型)だけは constructor 省略可。`field 初期化子`(`x: number = 0`)は constructor 一本化のため明示エラー。
- **reference 型(`calloc` + leak)**。Array/Map/Set と同じく `topaz_class_<Name> *` をポインタで持つ。代入で storage を共有する JS の semantics に揃えるためで、`r = p` のあと `r.y = 555` を書くと `p.y` も変わる(test ケースで明示)。確保は `calloc(1, sizeof(*self))` で zero-fill する(`malloc` だと未初期化 UB を踏みやすい)。`free` は Phase 1.5 のヒープ管理まで持ち越し。
- **`this` の C 表現は `__topaz_this`**。`this` は C++ の予約語だが C99 では reserved ではないので普通の識別子として使える。ただし C コンパイラ警告や FFI 互換のリスクを避けるため、生成 C 側では `__topaz_this` という `__topaz_` prefix 付きの名前に倒した(`__topaz_arr_<n>` / `__topaz_sw_<id>` と命名規則を揃える)。`Emitter.currentClass` という単一フィールドで「いまどのクラスの method/constructor を emit 中か」を管理し、`this` キーワードが現れたらそのクラスの instance 型を返す。`currentClass` は constructor / method の emit 前後で push/pop ではなく単純に set/clear する(class 宣言の中に class 宣言は書けないので nesting を考えなくてよい)。
- **コンストラクタは `_new` 関数として展開**。`new Point(3, 4)` → `topaz_class_Point_new(3.0, 4.0)`。`_new` の本体は `calloc` + constructor body + `return __topaz_this;`。constructor 内の `return` 文は禁止(JS では `return;` は `this` を返し、`return obj;` は別オブジェクトを返すという面倒な仕様があるので、ここで未対応エラーに切ってシンプル化)。
- **メソッドは static C 関数 + 暗黙 `this` 引数**。`obj.method(args)` → `topaz_class_<Name>_method_<m>(obj, args...)`。第 1 引数は常に `topaz_class_<Name> *__topaz_this`。`this.field` / `this.method(...)` も普通の PropertyAccess / Call として処理されるので特別な lowering は不要。
- **`new Map()` の context typing と class 構文の干渉を切る**。`declareVar` の `initIsBareNew` は元々「`new Map()` / `new Set()` で型引数が省略されているとき、annotation 側で補完する」用に作ったが、class インスタンス化 `new Point(3, 4)` も identifier `Point` のみ + type argument なしの形で同じパターンに合致してしまう。後者は identifier から型が決まるので annotation 不要。`initIsBareNew` の判定を `identifier が "Map" または "Set"` に絞り込んで切り分けた。
- **PropertyAccess 代入は `(obj)->field op= v` に native lower**。Array の `a[i] = v` は C に lvalue 表現がないので `topaz_array_X_set(a, i, v)` というヘルパを通すが、class の `obj.field = v` は C の `obj->field = v` が直接 lvalue として使えるので、`emitExpression` の BinaryExpression 分岐を特別扱いせず普通に `(emit(left) <op> emit(right))` で乗る。複合代入(`obj.field += v`)も C 側で単発の `+=` になり、`obj` は 1 回しか評価されない(Array の場合と違って index がない)。ただし `obj` が複雑な式(例: `getFoo().x += 1`)だと、文字列連結の `+=` のような特殊 lowering で `obj` を 2 回 emit する経路があるので、`checkAssignTarget` で `base が identifier / this / chained PropertyAccess` のみに制限した。
- **メソッド参照(`obj.method` without `()`)は未対応**。first-class function を持たない方針なので、メソッドを値として取り出すと使い道がない。`emitExpression` / `inferType` の PropertyAccess 分岐で「class 型 base に対する method 名」を検出した場合、明示的に「`call it instead`」エラーを出す。
- **`Array<ClassName>` などコンテナでクラスを持つ用途は 1.4c に持ち越し**。`arrayOf` / `mapOf` / `setOf` は scalar 型しか受け取らない実装になっていて、Array monomorph も number / boolean / string の 3 つだけプリ展開している。class 型まで広げるには TOPAZ_ARRAY_DEFINE をクラス宣言時に動的展開する経路を新設するか、generics 経由で monomorph を生成するインフラを作る必要があり、1.4a の範囲を超える。`class C { items: number[]; ... }` のように Array<scalar> をフィールドに持つのは普通に動く(reference 型同士のネストなので問題なし)。
- **未対応リスト(class まわり、明示エラー)**。`extends` / `implements`、`static` / `private` / `protected` / `public` / `readonly` / `abstract` / `override` 修飾子、generic class / generic method、class expression、decorator、getter / setter、static block、parameter property shorthand、`super`、暗黙コンストラクタ(フィールドあり時)、フィールド初期化子、メソッド参照、constructor 内 `return`、class を `console.log` の引数に取る、`Array<ClassName>` / `Map<K, ClassName>` などコンテナでクラスを保持する用途。1.4b で interface + 構造的型統合、1.4c で generics + クラスを含むコンテナ展開を入れる。
- **テスト**。`examples/class_basic.ts` で 2 クラス(`Point` / `Greeter`)、フィールド read / 通常代入 / 複合代入(`+=`)、メソッド呼び出し(`this.x + this.y`、`new Point(...)` の return、引数にクラスインスタンスを取るメソッド)、reference 共有(`r = p` 後の `r.y = 555` が `p.y` に反映)、関数引数・戻り値としてクラスインスタンスを渡す、`string` フィールド + メソッド内の `string` 連結、を一通り叩いている。エラー側は手動で「`new Foo("oops")` の引数型不一致」「`this` を関数外で使用」「`class B extends A {}`」「`obj.method` のメソッド参照」「`console.log(classInstance)`」「フィールドあり class で constructor なし」が全部期待通り `CodegenError` で落ちることを確認(回帰テスト化は未着手、Phase 1.5 のプロパティテスト基盤と一緒に拾い直す宿題)。

## Phase 1.4b 実装決定ログ(interface / 構造的型)

- **fat pointer + per-(I, C) vtable を選択**。代替案は (a) interface 型をそのまま class 型として monomorphize する(関数ごとに class 数分の monomorph を出す)、(b) interface は単なる型宣言だけにして dispatch を一切しない、の 2 つ。(a) は Phase 1.4c の generics で似たことをやる予定なので二重投資感がある+1 つの値が runtime で動的に「複数のクラスのうちどれか」にバインドされる(`makeShape(kind)` のような factory パターン)の表現がそもそもできない。(b) は構造的型の旨味がほぼ消える(関数引数の型を interface にしてもただの documentation になる)。fat pointer なら 16 byte(data ptr + vt ptr)で OOP 言語の interface とほぼ同じ semantics が乗るし、vtable を class × interface 単位で 1 つだけ生成すれば static const として data 領域に乗るので、runtime cost は call site の indirect call 1 回だけ。これを選択。
- **vtable はフィールドも getter/setter 関数ポインタとして持つ**。素朴には class の struct layout を interface ごとに alignment 揃えて固定する方法もあるが、複数の interface を 1 つのクラスが implement する場合に layout 制約が衝突するし、field offset を直接埋め込むと別の翻訳単位から見えなくなる。getter/setter 関数経由なら class layout が完全に自由で、後で field を class の前後どこに足しても vtable 側の wrapper を再生成するだけで済む。indirect call 1 段増えるが、固定 layout 戦略に比べると implementation complexity の差が大きい。
- **構造的一致は EXACT match を要求(coercion なし)**。`class C` が `interface I` を `implements` する時、フィールド型もメソッド signature も完全一致を要求する。例えば interface が `f(): I` と宣言していて、クラスが `f(): C`(C は I を実装する具象クラス)を返すケースは現状エラーにする。理由は、vtable wrapper の生成が単純な「`(C*)self->f()` を呼んで返す」になるため。covariant return / contravariant param まで対応すると wrapper 内で coercion を挟む必要があり、wrapper の数が増えるし C 側の型互換性も崩れる。1.4b の射程外。
- **coercion は user-visible value sites のみで挟む**。`emitWithExpected(expr, expected)` ヘルパを新設し、変数宣言の初期化子 / 関数呼び出しの引数 / `return` 文 / 代入の RHS の 4 サイトで使う。class -> interface への変換は ここでだけ起きる(fat pointer の compound literal `((topaz_iface_I){ .data = ..., .vt = &topaz_iface_I_for_C_vt })` を emit する)。`==`/`!==` を含む式中の値比較や `console.log` 引数では coercion しない(`console.log(iface)` 自体が未対応エラー、`iface === iface` も未対応で十分)。これで coercion の挿入箇所がほぼ網羅できる。
- **`return` 文の coercion のため `currentReturnType` を Emitter に追加**。関数 / メソッドの本体を emit 中、`return expr;` の expr に対して `emitWithExpected(expr, currentReturnType)` を呼ぶ必要があるが、`emitFunctionDefinition` / `emitMethodDefinition` の中でしか分からない情報なので、Emitter のメンバとして push/pop する。`functionReturns` を `functionSigs`(params + returnType)に rename して、関数呼び出し側でも param type を引いて coercion をかけられるようにした。
- **emit 順序: vtable wrapper / instance は user 関数より前に置く**。`describe(new Circle(3))` のような coercion site が user 関数本体に入ると `&topaz_iface_Shape_for_Circle_vt` を参照する必要があり、forward declaration だけだと不十分(static const のアドレスを取るので definition が見える必要がある)。emit の順序は: include → class struct fwd → interface fat pointer typedef + vt struct fwd → class struct def → interface vt struct def → fn/method fwd → vt wrapper def + vt instance def → user fn def → class method def → main、に固定。
- **interface 経由の dispatch は stmt expression で base を一度だけ評価**。`makeShape(2).area()` のような「base が副作用を持つ式」を `(base).vt->area((base).data)` の素朴 lowering で出すと、base が 2 回呼ばれてしまう。GCC/clang stmt expression `({ topaz_iface_X __t = base; __t.vt->m(__t.data, args); })` で base を temp に固定する形に統一(getter / setter / method call すべて同じパターン)。base が identifier の場合は temp が冗長だが、C compiler が最適化で取り除くので codegen を分岐させるより読みやすい。
- **interface field 代入は void 評価**。`iface.f = v` は `({ topaz_iface_X __t = base; __t.vt->set_f(__t.data, v); })` という stmt expr で、setter が void を返すので式全体の値も void。chained assignment `x = (iface.f = v)` は使えないが、TypeScript ユーザーの実コードでほぼ書かないパターンなので未対応で割り切る。class の field 代入(C lvalue がある)とは divergence する。
- **interface field の compound assignment は未対応**。`iface.f += v` を実装するなら getter + setter を 1 文に統合する必要があり、stmt expr で書けなくはないが、divergence が増えるだけなので明示エラーで弾く(`iface.f = iface.f + v` を書けと案内する)。
- **interface 値の Map/Set/Array 要素は未対応**。`Array<Shape>` などは `arrayOf` が scalar 型しか受け取らないため `no Array monomorph for element type topaz_iface_Shape` で自然に弾かれる。本格対応は 1.4c の generics monomorphize で interface も含めて再設計する。
- **interface に対する `new`、interface の `extends`、generic interface、optional フィールド / メソッド、modifiers、index / call / construct signature、getter / setter** は collectInterfaceMembers の段で全部明示エラー。「`new Shape()`」は class 名と interface 名が同じ namespace に乗っているので emitNewExpression / inferType 両方で interface かどうか判別して「instantiate an implementing class instead」と案内する。
- **エラーメッセージは class 由来の文言を流用**。「`'<m>' is a field, not a method, on interface ...`」「`interface '<I>' has no method '<m>'`」など、class の同種エラーと並びを揃えてある。ユーザーが class と interface を切り替えた時にメッセージで混乱しないようにするため。
- **テスト**。`examples/interface_basic.ts` で 2 クラスを 1 interface に implements、`describe(s: Shape)` / `makeShape(kind: number): Shape` の interface 引数・戻り値、`const a: Shape = new Circle(2)` の変数初期化での coercion、`a.name`(field read)/`a.name = "renamed"`(field write)/`a.area()` / `a.scale(3)` のメソッド・フィールド dispatch、`makeShape(2).area()` の「return された interface 即 method call」(stmt expr の base 一度評価が効くケース)を一通り叩いている。エラー側は手動で「`class C implements I` で field 型不一致」「method signature 不一致」「missing field/method」「`new Shape()`」「`Array<Shape>`」「`console.log(iface)`」「`iface.method`(値として)」が `CodegenError` で落ちることを確認。

## Phase 1.4c-1a 実装決定ログ(Array<class/interface>)

- **1.4c はサブフェーズに分割**。「generics(関数・クラスの型パラメータ、monomorphize、コンテナ展開)」を 1 コミットで着地させると差分が大きすぎるので、self-hosting で先に要るものから刻む。1.4c-1a = `Array<ClassName>` / `Array<InterfaceName>`、1.4c-1b = `Map`/`Set` の class/interface 要素、1.4c-2 = generic function、1.4c-3 = generic class。`ClassInfo[]` や `InterfaceInfo[]` のような「クラス/interface を要素に持つ配列」が self-hosting の symbol table 周りで真っ先に必要になるので 1.4c-1a を最初に置いた。
- **`TopazType` に array variant を 2 つ追加(string union のまま)**。`topaz_array_class_<C>` と `topaz_array_iface_<I>` を `TopazType` に追加し、`arrayOf` / `arrayElem` / `arrayShortName` をそれぞれ class/interface 分岐させた。本格的に structured な型表現(`{ kind: "array", elem: TopazType }` のような object)へリファクタするのは 1.4c-2 で generic function を入れるタイミング(`Array<Box<number>>` のような型パラメータが入ってからじゃないと structured 化のメリットが薄い)。今回は string union のまま延命して差分を小さく保つ判断。
- **monomorph は on-demand 収集 → emit 末尾で splice**。`Emitter.arrayMonomorphs: Set<TopazType>` に `recordArrayMonomorph` 経由で追加し、`emit()` の終わりに `TOPAZ_ARRAY_DEFINE(class_<C>, topaz_class_<C> *)` / `TOPAZ_ARRAY_DEFINE(iface_<I>, topaz_iface_<I>)` を組み立てて placeholder index に splice する。記録サイトは 4 つ:(1) `typeFromAnnotation` の `T[]` / `Array<T>` 解釈、(2) `emitArrayLiteral` の非空リテラル、(3) `inferType` の `ArrayLiteralExpression`。これで「ユーザーが書ける型注釈経由 + 配列リテラル経由」全部を網羅。空 `[]` は型推論できないので、型注釈経由で必ず記録される。
- **macro の配置は interface vtable struct typedef の後・class struct definition の前**。macro が参照するのは `topaz_class_<C> *`(pointer なので forward decl で十分)と `topaz_iface_<I>`(fat pointer struct typedef が full definition で必要)なので、interface fat pointer typedef が出た直後 = class struct typedef・interface vtable struct fwd の後、class struct definition の前、というのが最も早い tipping point。元の `emit()` の出力順序にちょうど境目があったのでそこに placeholder slot を 1 つ差し込むだけで済んだ。
- **`#pragma GCC diagnostic ignored "-Wunused-function"` で macro 展開を囲む**。`TOPAZ_ARRAY_DEFINE` は `_new` / `_reserve` / `_push` / `_pop` / `_at` / `_set` の 6 関数を `static inline` で展開する。runtime.h での scalar pre-expand では header-scope static inline で warning が出ないが、ユーザーの .c file scope では「unused static function」として clang が警告する。`.pop` を使わないケースが普通なので、macro 全体を pragma で囲んで一括抑制した。`-Werror` で困らないように、また「.pop だけ使ったケース」「.push だけ使ったケース」のような呼び出しサイトの組み合わせを codegen で枝分かれさせないため。
- **配列リテラル各要素に `emitWithExpected` を適用**。`const shapes: Array<Named> = [new Square(3), new Circle(2)]` のような「型注釈経由で要素型が固定 + 要素ごとに違う class が並ぶ」ケースは、最初の要素から型推論して残りを揃える形だと「2 番目で type mismatch」になる。`emitArrayLiteral` を改修し、`expected` が array 型なら先にそれを採用して各要素を `emitWithExpected(e, elemType)` で出す。`expected` がない場合だけ最初の要素から推論して残りに `expectType` をかける現状の経路を維持。これで「`Array<Interface>` の各要素 class」「`Counter[]` の各要素 `new Counter(...)`」が両方とも自然に動く。
- **`.push` 引数と `[i] = v` の RHS にも `emitWithExpected`**。`shapes.push(new Square(4))` / `shapes[0] = new Circle(5)` が 1.4b の coercion 4 サイト(変数初期化・関数引数・return・代入 RHS)では捕捉できない(`.push` は組み込み method call で `functionSigs` に載っていない、`shapes[0] = v` は `array_set` 呼び出しに lower される)。`emitArrayMethodCall` の push 分岐と `emitArrayIndexAssign` の RHS で個別に `emitWithExpected(arg, elem)` を挟む。これで「配列要素経由の class→interface coercion」が 1.4b の coercion 4 サイト + 配列の 2 サイト = 計 6 サイトで動く。
- **`.pop` の戻り値型は interface 要素でもそのまま fat pointer**。`const last = shapes.pop()` のように受ければ `topaz_iface_<I>` 値型として束縛される。interface 値を返り値で受けるパターンは 1.4b の `makeShape` 経由でテスト済みで、今回 array でも同じ paths を通る。テストでは class 要素の `.pop` を 1 ケース、interface 要素の `.pop` は省略(関数 / 戻り値での coercion とほぼ同じ paths なので冗長と判断)。
- **テスト**。`examples/array_class_iface.ts` で(a) `const cs: Counter[] = [new Counter(1), ...]` の class 要素配列(`.length` / `[i]` / `[i] = new C(...)` / `.push` / `.pop`)、(b) `const shapes: Array<Named> = [new Square(3), new Circle(2)]` の interface 要素配列(リテラル時点で 2 クラスが混じるパターン、`.push(new Square(4))`、`shapes[0] = new Circle(5)` で coercion がリテラル以外でも走ること、`shapes[i].method()` / `shapes[i].name` の dispatch)、(c) 空 array 注釈 `Counter[]` / `Named[]` に push で生やすパターンを叩く。Map/Set の class/interface 要素は明示的に未対応(1.4c-1b で着地)。
- **divergence と将来の宿題**。`Array<Array<T>>`(ネスト)はまだ未対応(elem 型が array 自身になるパスを `arrayOf` / `recordArrayMonomorph` でまだ書いていない)、generic 宣言(`function f<T>(...)`, `class Box<T>`)も未着手。1.4c-2 で generic function + monomorph 表の structured 化に進む。

## Phase 1.4c-1b 実装決定ログ(Map<scalar, class/iface> / Set<class/iface>)

- **1.4c-1a の monomorph 収集パターンを Map/Set に拡張するだけ**。`Emitter.arrayMonomorphs` の隣に `mapMonomorphs: Set<TopazType>` / `setMonomorphs: Set<TopazType>` を追加し、`recordMapMonomorph` / `recordSetMonomorph` を `typeFromAnnotation` / `emitNewExpression` / `inferType` の `new Map/Set` 経路にぶら下げる。`TopazType` は string union のまま延命:`topaz_map_<KShort>_class_<C>` / `topaz_map_<KShort>_iface_<I>` / `topaz_set_class_<C>` / `topaz_set_iface_<I>` の 4 形を追加した。array variant と同じく structured 表現への移行は 1.4c-2 でまとめてやる。
- **`mapKey` / `mapValue` のパーサを `indexOf("_")` ベースに書き換え**。1.3b 当時は scalar 名にアンダースコアを含めない不変条件で `split("_")` していたが、`topaz_map_string_class_Counter` のように value 側に underscore を含む形が入ったので、最初の underscore で K と V を 1 回だけ分割する形に変更した。残り(V 側)は `class_` / `iface_` prefix を見て分岐。同じ書き換えを `setOf` / `setElem` にも適用。
- **per-(class/interface) hash + eq wrapper を codegen で生成**。`TOPAZ_MAP_DEFINE` / `TOPAZ_SET_DEFINE` マクロは hash / eq 関数名を引数で受ける設計なので、class 値 / interface 値ごとに `topaz_hash_class_<C>` / `topaz_key_eq_class_<C>` / `topaz_hash_iface_<I>` / `topaz_key_eq_iface_<I>` の薄い `static inline` を codegen が吐く。class は素直に pointer hash + pointer 比較、interface は fat pointer の `.data` を取り出して同じことをやる。これで Set の同値判定が **reference identity** = JS の Set が object 要素に対して採用しているのと同じ semantics に揃う(`===` のオブジェクト比較と同じ)。
- **`topaz_hash_pointer` を runtime.h 側に置く**。Wang/MurmurHash3 系の 64-bit finalizer(`xor + multiply + xor + multiply + xor`)を `static inline size_t topaz_hash_pointer(const void *p)` として `topaz_hash_boolean` の隣に追加。class / interface wrapper の両方から呼ぶので runtime 側に置くのが妥当(codegen 側にインライン展開する方法もあるが、wrapper が 2 × 宣言クラス数 だけ増えるので redundancy を runtime 側に押し付ける方が見通しがよい)。
- **structural equality を採用しなかった理由**。Set<Counter> で同じ field を持つが別 instance が来た時に「同じ」と判定する設計も筋としてはあり得るが、(a) JS Set の published セマンティクスが reference identity、(b) class が `equals` メソッドを持たない現状で構造的等値の意味が「全フィールドの recursive `===`」になり、reference field のさらに reference field… と再帰する必要が出てくる、(c) 値型ベースの dedup が欲しい場面はそもそも `Map<key-projection, instance>` で書く方が TS らしい、の 3 つで reference identity 一本にした。Phase 1.4c-3(generic class)で `class Box<T>` を入れて値型コンテナを作れるようになった段で再検討の余地はある。
- **interface dedup は `.data` ポインタ比較で十分**。同じ class instance を `Set<Shape>` に「Square として」入れた直後に「Shape へ coerce してから」もう一度 `.add` しても、fat pointer の `.vt` は per-(I, C) で違っても `.data` は同じポインタなので 1 件扱いになる。テストでも `named.add(sq)` を 2 回呼んで `.size` が 2 のままなことを確認(`sq` は `Square` 型変数で、`.add` の引数位置で class→interface coercion がかかる)。これは 1.4b で「同一 instance を異なる interface view 経由で扱っても data ポインタは保存される」設計にしたおかげで自然に通る。
- **`Map.set` の string key だけ特殊**。`TOPAZ_MAP_DEFINE` には `eq_fn` を渡す設計だが、scalar 3 種のうち `topaz_key_eq_number` / `topaz_key_eq_boolean` は runtime.h で定義しているのに、string だけは `topaz_string_eq` という別名で定義していた(1.2 時点の名残)。`emitMapMonomorphMacro` で `kShort === "string"` だけ `topaz_string_eq` に分岐させて回避。runtime.h 側に `topaz_key_eq_string` を新設して統一する手もあったが、`topaz_string_eq` が string 連結周りからも参照されている既存 API なので、codegen 側を 1 行分岐させる方が侵襲が小さい。
- **`.set` / `.add` / `.get` / `.has` / `.delete` の引数 / 戻り値で coercion**。`emitMapMethodCall` / `emitSetMethodCall` の `set` / `add` 引数を `expectType + emitExpression` から `emitWithExpected` に置換。これで `counters.set("a", new Counter(1))` が `counters.set("a", _coerce(new Counter(1)))` 相当にならずに済み、interface 値 map では `shapes.set(1, new Square(3))` の RHS class→interface coercion が自然に走る。`.get(k)` の戻り値は value 型(class なら pointer、interface なら fat pointer)で、そのまま method chain して `shapes.get(1).area()` のような interface dispatch ができる。
- **container monomorph slot を共有**。1.4c-1a で導入した「class struct 定義の前 / interface vt struct fwd の後」の placeholder slot に、`TOPAZ_ARRAY_DEFINE` だけでなく `TOPAZ_MAP_DEFINE` / `TOPAZ_SET_DEFINE` と上記 per-(class/iface) wrapper を全部一緒に吐く。slot 名を `arrayMonomorphSlot` から `containerMonomorphSlot` にリネーム。order は「set elem helpers(class / iface 用 hash + eq wrapper)→ Array macros → Map macros → Set macros」で、wrapper は macro 展開前に来る必要があるので Set elem helper だけは先頭に置く。
- **`Map<class, V>` / `Map<iface, V>`(class / interface を key にする方向)は未対応のまま**。reference identity で hash + eq できるので技術的には対称に展開可能だが、`Map.get` の missing key で abort する現状の semantics と組み合わせると「ポインタを覚えていないと取り出せない map」になりほぼ役に立たない。`Map.get` が `V | undefined` を返せるようになる Phase 1.5 まで保留。class / interface を key にしたいユースケースが self-hosting で出てきたら 1.4c-1b に後追いで足す。
- **テスト**。`examples/map_set_class_iface.ts` で(a) `Map<string, Counter>` の `.set` / `.get`(method chain `counters.get("a").bump(10)` を含む)/ `.has` / `.delete` / `.size`、(b) `Map<number, Named>` の interface 値 map と `shapes.set(1, new Square(3))` 経由の class→interface coercion、(c) `Set<Counter>` の reference identity dedup(同じ field 値を持つ別 `new Counter(11)` は別物扱い)、(d) `Set<Named>` の interface 要素 dedup(同じ `sq` instance を再 add しても 1 件、`.delete` で正しく消える)、(e) 60 要素入れて Set の grow path、(f) `new Map()` / `new Set()` の context typing(`Map<string, Counter>` / `Set<Named>` annotation 側で型を補完)を一通り叩く。

## Phase 1.4c-2 実装決定ログ(generic function)

- **monomorphize は worklist で遅延展開**。`function f<T>(...)` の宣言は `Emitter.genericFunctions: Map<name, { typeParams, decl }>` に登録するだけで signature 解決は遅延。呼び出しサイト(`emitCall` / `inferType` の identifier-callee 分岐)で `resolveGenericCall` を通り、(a) `expr.typeArguments` があれば `typeFromAnnotation` で各 `T` の TopazType を決める、(b) なければ各 param の TypeNode を引数の inferred type に対して `unifyTypeParam` で構造マッチして bind、を経て mangled name と substituted FunctionSig を作る。新規 monomorph は `genericMonomorphs` に登録 + `genericWorklist` に積む。`emit()` の末尾で worklist が空になるまで `emitMonomorphDefinition` を回すので、body の中で別の generic を呼んでも再帰的に展開される(mutually recursive generics も同じ機構で吸収)。
- **`TopazType` は structured 表現に移行しなかった**。MEMO §6 では「1.4c-2 で structured 化」と書いていたが、generic function 単体では型パラメータを monomorph 時に既存の TopazType 値に置換するだけで足りる(`Array<T>` の `T` が決まれば `topaz_array_class_Box` などの既存 variant に落ちる)。`Array<Box<number>>` のような type-arg ネストは generic class が入る 1.4c-3 で初めて顕在化するので、structured 化はそこで一緒にやる。1.3a / 1.3b 時点で同じ「string union で延命」判断をした流れを踏襲。
- **`typeParamScope` で type param を解決**。`Emitter.typeParamScope: Map<string, TopazType> | undefined` を新設し、monomorph body / type-arg 解決中だけ active。`typeFromAnnotation` の `TypeReferenceNode` 分岐で、識別子が `typeParamScope` に登録されていれば即その TopazType を返す。**class / interface 検索の前に置く** のが重要で、ユーザーが `class T {}` を宣言したクラスより type param の `T` が優先される(generic function の中ではローカル scope のシャドウイングと同じ semantics)。`typeArguments` が付いた `T<U>` は明示エラー(type param に高階を持ち込まない)。
- **mangling は `__` 区切り**。`identity<number>` → `identity__number`、`pair<class_Box, string>` → `pair__class_Box__string`。`mangleTypeArg(t)` は `topaz_` prefix を剥がすだけ。class 名 / interface 名に `__` を入れる可能性は薄いが、入れた場合の衝突は構文側のリンタ層(あれば)で reject する想定。生成 C の関数名は `static <ret> <mangled>(...)`。
- **inference は best-effort、bound 漏れだけ厳格チェック**。`unifyTypeParam` は (a) `T[]` / `Array<T>` / `Map<K, V>` / `Set<T>` の TypeNode と TopazType を構造的に decompose、(b) `TypeReferenceNode` の名前が type param なら bind、(c) それ以外(concrete class / interface / scalar 参照)は黙ってスキップ、の 3 動作で、unify 失敗を即エラーにはしない。代わりに resolve の末尾で「全 type param が bound されたか」を確認し、漏れがあれば「`cannot infer type parameter 'T' for f; provide explicit type arguments`」で reject。実際の型不一致は call 後の `emitWithExpected` で substituted param type と引数式の inferred type を比較する段で出るので、unify が中途半端でも user-visible エラーとしては正しく落ちる。同じ type param に異なる型が unify された場合だけは `unifyTypeParam` 内で即エラー(`inferred as both number and string` 形式)。
- **monomorph fwd decl と def の slot 配置**。fwd decl は user 関数 / class method の fwd decl の直後、def は user 関数 / class method 定義の後・`main` の前に slot を切る。worklist drain は **`main` も含む user 全体の emit が終わってから** 走らせる:理由は、monomorph body の emit が更なる monomorph を必要としても worklist で吸えるが、container monomorph slot を埋めるのは drain の後にしないと「monomorph body 内で発見した `Array<class_X>` などのコンテナ monomorph」を取りこぼすため。Phase 1.4c-1a で `containerMonomorphSlot` を「emit 末尾で splice」設計にしておいたのが効いた。
- **`-Wunused-parameter` を pragma で抑制**。`function pickSecond<A, B>(a: A, b: B): B { return b; }` のような「型パラメータの片方が body 中で使われない」generic は実用上ありふれる(例えば self-hosting で `function get<K, V>(m: Map<K, V>, k: K): V | undefined`、value 側を取り出さない paths)。`(void)a;` を body 先頭に注入する方法もあるが、AST 改変が必要な上に「unused でないケース」と分岐する必要があるので、monomorph def 全体を `#pragma GCC diagnostic push / ignored "-Wunused-parameter" / pop` で囲む方が単純。container monomorph slot で同じ pragma パターンを `-Wunused-function` 用に既に使っているので、それと同じ形に揃えた。
- **collectParams は既存の関数経路をそのまま流用**。`resolveGenericCall` で substituted FunctionSig を作るとき、`typeParamScope` を sub に差し替えてから `collectParams(generic.decl.parameters)` と `typeFromAnnotation(generic.decl.type)` を呼ぶ。これで「return type が `Array<T>`」「param が `T[]`」のような type-param 経由の型注釈も既存の resolver でそのまま解決できる(type param 解決を typeFromAnnotation の冒頭に挟んだのが効いた)。`emitMonomorphDefinition` 側でも同じ scope を被せ、各 param を `scope.declare(p.name, substitutedType, ...)` で declare してから body を emit する。
- **constraint / default は未対応**。`function f<T extends Shape>(...)` の `extends` 制約と `function f<T = number>(...)` の default は宣言登録時に明示エラー。constraint は「class→interface coercion のような structural check」を入れる仕掛けが要るので 1.5 の全プログラム型検証と合わせて再設計。default は monomorphize されない関数(呼ばれない generic)を許容するかとも絡むので、現状 generic は call site があるものだけ emit する設計と整合性が悪い。
- **エラー側未対応**。重複した type param 名(`function f<T, T>`)、type param に typeArguments を渡す(`T<U>`)、explicit type args の数不一致、inference 不能、interface key にした `Map<I, V>` の延長(これは 1.4c-1b 時点で既存)、generic class(`class Box<T>`)、generic class インスタンス化、generic method、`new` 経由の type args、型引数のみが違う関数 overload — これらは引き続き明示エラー / 未対応。
- **テスト**。`examples/generic_fn.ts` で(a) `identity<T>` を number / string / boolean それぞれで explicit / inferred 両方、(b) `first<T>(xs: Array<T>): T` / `last<T>(...)` の `Array<T>` param からの T inference、(c) `pickSecond<A, B>(a: A, b: B): B` の 2 type param + unused param、(d) `singleton<T>(x: T): Array<T>` の return type が `Array<T>`(class 型引数だと `Array<Box>` monomorph が generic 経路から記録される)、(e) `firstOfSingleton<T>(x: T): T { return first<T>(singleton<T>(x)); }` で 1 つの generic の中から別の generic を呼ぶ + 外側の type param が内側にそのまま forward される、(f) `singleton<Box>(new Box(777))` で class 型引数を取って `Array<Box>` を返すパス、を一通り叩く。期待出力は 21 行(`42 / 7 / hi / yo / true / false / 10 / 30 / alpha / gamma / two / 2 / 1 / 99 / solo / 1 / 123 / zzz / 1 / 777 / 555`)。

## Phase 1.4c-3 実装決定ログ(generic class + `TopazType` structured 化)

- **`TopazType` を string union から tagged union へ移行**。1.3a 以来 `` `topaz_${ScalarShortName}` `` のような template literal string union で延命してきたが、`Array<Box<number>>` のように type argument がネストすると mangled name の文字列を decompose / reconstruct する経路が増え、`__` 区切りの命名衝突も顕在化する(`class Foo__Bar` のような identifier を user が書けてしまう、mangle と判別がつかない)。Phase 1.4c-3 着手のタイミングで `TopazType` を `{ kind: "number" | "boolean" | "string" } | { kind: "array", elem } | { kind: "map", key, value } | { kind: "set", elem } | { kind: "class", name } | { kind: "iface", name }` の tagged union に置換し、`typeEq(a, b)` で structural 比較、`typeIdent(t)` で `topaz_array_class_Box__number` のような C 識別子へ折り畳む方式に統一した。等値比較は全箇所 `===` を `typeEq()` に、エラーメッセージ内の `${type}` は全部 `typeIdent(type)` に書き換え(`expectType` / `isAssignableTo` / `applyCoercion` / `unsupported method '.${method}' on ${baseType}` 計 4 サイト)。`mangleTypeArg(t)` は `typeIdent(t)` から `topaz_` prefix を剥がすだけのヘルパに化けた。
- **PoC を generic class と同 PR にした理由**。MEMO §6 では「1.4c-2 で structured 化」と書いていたが、generic function 単独では `Array<T>` の T が monomorph 時に scalar / class に落ちるだけで string variant で十分だった(`Array<Box<number>>` のネストが発生しない)。1.4c-3 で `class Box<T>` を入れた瞬間に `Array<Box<number>>` / `Map<string, Box<number>>` のようなネストがユーザー側から書けるようになるため、structured 化を遅延させると mangled string をパースして depth を取り戻すコードが大量に要る。1.4c-2 → 1.4c-3 の境界で一気に張り替える方が、generic class 実装本体への差し戻しが少ない。
- **generic class も worklist monomorphize、`genericFunctions` の構造をそのまま踏襲**。`class Box<T> { ... }` の宣言は `Emitter.genericClasses: Map<name, { typeParams, decl }>` に Pass 1a で登録、ClassInfo の構築は遅延。`new Box<number>(42)` / `Box<number>` の型注釈・`Array<Box<number>>` の inner type ref / generic function 経由の inference それぞれが `instantiateGenericClass(refName, typeArgNodes, anchor)` を経由し、mangled name(`Box__number`、generic function と同じ `__` join)と substituted ClassInfo を作って `classes` / `classMonomorphs` に登録、`classMonomorphWorklist` に積む。drain は `emit()` 末尾で `genericWorklist` と round-robin に走らせる(class monomorph の body emission が更なる generic function を呼んでも吸えるし、その逆もある)。
- **recursive class を pre-register**。`class Node<T> { next: Node<T>; }` のような自己参照型が `collectClassMembers` の中で `next` フィールド型を解決する時に `Node<T>` を再度 `instantiateGenericClass` する。ここで `classes` への登録を後回しにすると無限再帰になるので、`instantiateGenericClass` は (a) mangled name から ClassInfo の **空の枠**を作って `this.classes.set(mangled, info)` する、(b) `typeParamScope = subs` を立てる、(c) `collectClassMembers(decl, info)` で枠を埋める、の順で展開する。`collectClassMembers` 自体も `(cls, infoOverride?)` の 2 引数版に拡張して、monomorph 経由で来た時は既存の枠を埋める、生 class declaration を Pass 2b から処理する時は新規に作る、を切替える。
- **member 関数 body の `typeParamScope` を保存・復元**。method body 中の `const old: T = this.value;` のような局所 `T` 注釈や、`return this.value;`(`return` 型 coercion で `T` の substituted type を要求)が `typeParamScope` 経由で解決される。Pass 3(emitClassMemberDefinitions)の中で各 monomorph の `subs` を再 active にしないと「monomorph 登録時の scope では type param が解決できたが、後から def を emit するタイミングでは scope が空」になり、`unsupported type (TypeReference)` で落ちる。worklist drain ループで `const prev = this.typeParamScope; this.typeParamScope = mono.subs; try { ... } finally { this.typeParamScope = prev; }` でラップした。
- **4 slot で monomorph 出力を分散**。concrete class struct / 関数 sig / 関数 def とは別に 4 つの slot を切る: (a) `classMonoTypedefSlot` を **全 concrete class struct の前**(他の concrete struct が `topaz_class_Box__number *` のような pointer field を持つケースを通すため、typedef だけ先に出す)、(b) `classMonoStructSlot` を concrete struct 定義の後・interface vtable 定義の前(interface vtable が monomorph class の field 型を参照することがあるので、struct 完了後)、(c) `classMonoSigSlot` を concrete 関数 sig fwd と並べて、(d) `classMonoDefSlot` は generic function def の前、それぞれ `#pragma GCC diagnostic push / ignored "-Wunused-parameter" / ignored "-Wunused-function" / pop` で囲む。`-Wunused-function` は「`Box<string>` を作ったけど `replace` は呼ばなかった」のような **monomorph された method の subset のみ呼び出される** 通常パターンで必要(generic function の monomorph には不要だった分岐)。
- **`unifyTypeParam` に generic class 分解を追加**。`unwrap(b)` のように `function unwrap<T>(b: Box<T>): T` に既存の `Box<number>` 値を渡すと、unifier は param TypeNode `Box<T>` と arg TopazType `{ kind: "class", name: "Box__number" }` を見て、(a) `classMonomorphs.get("Box__number")` で `{ origName: "Box", typeArgs: [number] }` を取り戻し、(b) `unwrap` 側の TypeNode の type-arg と `typeArgs` をペアワイズで再帰 unify する。これで generic function 経由で `T = number` が bind される。`Box` と `Pair` のように origName が異なる場合や typeArgs 数が違う場合は unify 失敗扱い(全 type param が bind されないと resolve 末尾で reject)。
- **interface 経由の coercion / 普通の new はそのまま動く**。`new Box<number>(42)` は `emitNewExpression` で `instantiateGenericClass` を呼んでから既存の `topaz_class_<mangled>_new` 経路に流れ、`emitWithExpected` での coercion も `typeEq()` ベースに移行済みなので追加変更不要。`Array<Box<number>>` も `typeFromAnnotation` の TypeReference 分岐で再帰的に inner type を解決し、`elem` に `{ kind: "class", name: "Box__number" }` を持つ array type を返すだけで、既存の `arrayMonomorphs` 登録経路がそのまま `topaz_array_class_Box__number` を生成する。
- **未対応**。generic class への `extends` / `implements` は heritage clause を見た時点で明示エラー(構造的一致を type param に対して走らせる仕掛けがない、Phase 1.5 の variance 議論まで保留)。generic method(`class C { f<U>(...) {} }`)も同様に Phase 1.5 以降(class 全体の monomorph と method 単独の monomorph が直交する)。generic interface も同じ Phase 1.5 に寄せる。constraint / default / 重複 type param 名 / explicit type args 数不一致 / inference 不能 はすべて宣言登録時 or call site で明示エラー、generic function と同じメッセージ形式に揃えた。
- **テスト**。`examples/generic_class.ts` で (a) `class Box<T>` の `get / replace` の round-trip(number / string / boolean それぞれで instantiate)、(b) `class Pair<A, B>` の 2 type param + 一方の field を string で返す `swapToString`、(c) `Array<Box<number>>` の monomorph 経由パスと `[1]` indexing → `.get()`、(d) `function unwrap<T>(b: Box<T>): T` の explicit と inferred 両方(後者で `unifyTypeParam` の generic class 分解を踏む)。期待出力は 11 行(`42 / 42 / 99 / hello / true / 1 / one / 3 / 20 / 99 / hello`)。method body 内で `void` 戻り値や `!` non-null は使わない(どちらも未対応)、`replace(v: T): T` のように戻り値で値を返す形に統一。

## Phase 1.5-1 実装決定ログ(例外 throw / try / catch)

- **Phase 1.5 を 1.5-1〜1.5-N に刻む**。MEMO §6 では Phase 1.5 に「例外、ES module、全プログラム型検証、ヒープ管理、generic method / interface、self-hosting 通過」が同居していたが、self-hosting に直接効くのが `CodegenError` の throw / catch であり、他項目より明らかに小さい。1.5-1 として例外だけを単独で着地させ、他項目はそれぞれ独立した 1.5-N サブフェーズに分解する方針に切り替えた。1.4c で `MEMO §3.1` の刻む方針を 1.4c-1a / 1.4c-1b / 1.4c-2 / 1.4c-3 に分けた流れと同じ。
- **setjmp/longjmp を採用、`__attribute__((cleanup))` は採らなかった**。C99 移植性と「単一 TU」の制約が動かないため、unwinding は setjmp/longjmp の linked-list frame stack(`topaz_try_top` をルートにした単方向リスト)で実装。代替として GCC/Clang の `__attribute__((cleanup))` で frame を auto-pop する案も検討したが、cleanup 関数が frame の `active` フラグを読みに行く必要があり、setjmp 後に longjmp で戻ってきた局所変数の値は標準上「indeterminate」とされる(C99 7.13.2.1p3)ため、最適化器が auto local の読みを保守的に扱わない事故が起きうる。`volatile` で pin する手もあるが、cleanup 関数経由の auto-pop ロジック自体が複雑化して読みづらくなるので、`topaz_throw` 側で frame を pop する + try body 末尾で `topaz_try_pop()` を明示呼びする方針に倒した。これで catch body は frame-local state を一切触らず、global の `topaz_throw_value` だけ読めば済むので、setjmp 後の「auto local indeterminate」問題自体を回避できる。
- **`topaz_throw` が自分で frame を pop**。`topaz_throw(v)` は (a) `topaz_throw_value = v`、(b) top frame を取り出して `topaz_try_top = top->prev` でリストから外す、(c) `longjmp(top->env, 1)` の順で動く。catch 側は frame を pop しなくて済むので、catch body 中に `throw` / `return` / 例外を出す関数呼び出しがあっても余計な frame 漏れがない。try body fall-through(正常終了)時は `topaz_try_pop()` を明示呼びする。「成功パス」と「例外パス」のどちらでも frame は 1 度だけ pop される、というシンプルな不変条件を維持。
- **try body 内の return / break / continue を一律禁止**。これらは frame を pop する前に C ブロックを抜けるため、dead jmp_buf が `topaz_try_top` に残り、次の throw で UB を踏む。lowering 側でこれらの構文ごとに「内部 cleanup を吐く」設計は可能だが、ネストや label 付き break / outer continue まで考えると複雑度が跳ねる。Phase 1.5-1 のスコープでは codegen の `checkTryBodyNoEscape` が AST を walk して全部明示エラーで弾く設計に倒した(nested function / class / method declaration の中までは降りない:そちらの制御フローは try 境界を跨がない)。loop が **try body の内側で完結**しているケース(`try { for (let i = 0; i < n; i++) break; }` のような自己完結 break)も保守的に reject — 「try 内で break を見たら拒否」のワンライナーで済ませる方が、利用者にも実装者にも単純で誤読が少ない。
- **catch binding の型注釈を必須化**。TS では `catch (e)` の `e` は `unknown`(strict)もしくは `any`(non-strict)で、JS は任意の値を投げられる。Topaz はそもそも `throw` 値を class instance に限定しているので、catch site でも「どのクラスに narrow するか」が決まっている必要がある:`catch (e: MyErr) { console.log(e.code); }` の `.code` は class type が分かって初めて解決できる。**全プログラム型検証(Phase 1.5-N)が入るまでは** 注釈なし catch を解決する手段がないので、`catch (e: ClassName)` の形式で明示注釈を要求し、無い場合は明示エラーで案内する。将来 Phase 1.5-N で `unknown` 型 + class narrow の構造的判定が入ったら、注釈省略時のデフォルトを `unknown` に倒して typeof-narrowing 等で絞らせる方向に拡張する。
- **throw 値は class instance のみ**。JS / TS は任意の値(`throw 42` / `throw "boom"` / `throw {}`)を投げられるが、Topaz は (a) primitive を throw すると `void *` payload に bit pattern を埋める仕掛けが必要で複雑、(b) plain object は class instance と区別する型タグがない、(c) self-hosting で実際に投げたいのは `CodegenError` などのカスタム class、という 3 点から **class instance に限定**。`emitThrowStatement` で `inferType(stmt.expression)` を確認し、class type 以外は明示エラー。これで catch site も「class instance pointer を `void *` で受けて class type に cast し直す」の単一パターンで済む。`Error` のような組込み class は持たない(JS / TS の `Error` を再現すると stack trace API / `cause` chain / プロト継承が要るので、Phase 1.5-1 のスコープに入らない)。
- **`topaz_throw_value` は global、`_Thread_local` 不要**。Topaz は単一 TU・single-thread でしか走らず、Phase 1.5-1 でその前提は変えない。`_Thread_local` を付けると C11 必須・MSVC で `__declspec(thread)` 差分・楽観的に WASM target を見据えると更に話がややこしい。global で十分なところを `_Thread_local` で先取りしない。将来本気で threading を入れる時に runtime.h ごと再設計する。
- **uncaught exception は `abort`**。`topaz_throw` が呼ばれた時点で `topaz_try_top == NULL` だったら `fputs("topaz: uncaught exception\n", stderr); abort();`。JS だと console にエラー出して非 0 終了するだけだが、Topaz は stack trace を持たないし、`abort` 経由で SIGABRT 出した方が core dump / debugger trap で原因を追える(self-hosting 用途では十分)。class 名や `.msg` を表示するのは reflection / RTTI 相当が要るので諦め。
- **`static inline` で `-Wunused-function` 回避**。`topaz_throw` / `topaz_try_push` / `topaz_try_pop` は他の runtime helper(`topaz_fmod` 等)と同じく `static inline` にする。最初 `static void topaz_throw(...)` で書いたら例外を使わない examples の cc に `-Wunused-function` 警告が出た(`-O2` だと inline されて消えるが、警告自体は `static inline` で消える)。runtime header 全体の流儀に揃えるのが正解。
- **scope 管理は try body / catch body を別 push**。最初 `try { const v = ...; } catch ... try { const v = ... }` を書いたら `redeclaration of 'v'` で C cc がエラーを出した。`emitTryStatement` で try body / catch body の statement emit をそれぞれ `this.scope.push()` / `this.scope.pop()` で囲むことで解決。catch binding(`e`)は catch body の scope に declare する(catch body だけで参照可、try body / 外側からは見えない)。`try_catch_basic.ts` の最後のケース(`const sentinel = 999; try { ... } catch (e: MyErr) { ... }; console.log(sentinel);`)で「catch binding が catch block 外に leak しない」「try 外で宣言した `sentinel` が catch body 後にも見える」を両方カバー。
- **生成 C のレイアウト**。`{ topaz_try_frame __topaz_try_<id>; topaz_try_push(&__topaz_try_<id>); if (setjmp(__topaz_try_<id>.env) == 0) { <try body>; topaz_try_pop(); } else { topaz_class_<E> *<e> = (topaz_class_<E> *)topaz_throw_value; <catch body>; } }`。外側を `{ ... }` で包むのは frame を block scope に閉じ込めるため(ネスト try でも frame 名は `tmpCounter` 由来でユニークだが、念のため block 単位で scope を切る)。nested try は同じパターンが入れ子になるだけで、`topaz_try_top` の linked list が outer → inner の順に積まれ、inner で `topaz_throw` が走ると inner frame が pop されて inner catch に行く、というのが自然に成立する。
- **未対応**。`finally` 句(現状 cleanup が要らないテストパターンしかないため deferred、必要なら try body 内の return / break / continue 解禁とセットで Phase 1.5-N で入れる)、bare `catch` / 注釈なし binding(`unknown` narrowing が入るまで)、`throw` 値が class 以外(primitive / interface / array)、`catch` で複数型を union 受け(`catch (e: A | B)`、union 型自体が未対応)、`Error.cause` / stack trace、`new.target` / `Error.captureStackTrace`、try body 内の return / break / continue。
- **テスト**。`examples/try_catch_basic.ts` で (a) class instance を直接 throw → catch、(b) 関数経由で throw が伝播して呼び出し側で catch、(c) try 内が正常終了する happy path、(d) nested try で inner catch が処理、(e) nested try で inner catch が別 class を rewrap して outer catch が拾う、(f) catch binding が catch block 外に leak しないことと外側 `const sentinel` が catch 後にも見えること、を 6 ケース。期待出力は 13 行(`boom / 1 / negative / 42 / 10 / 7 / 100 / 9 / rewrapped / 2 / 0 / 999`)。`smoke.sh` に `run_case try_catch_basic` を追加。

## Phase 1.5-2 実装決定ログ(ES module 静的解決)

- **スコープを「ユーザー定義 module 限定」に絞る**。`docs/archive/self-hosting-inventory.md §6` の通り、src/ の import 関係は `parser ← cli → codegen` の DAG で循環無し、依存先は全部 `node:*` か `typescript`。`node:*` / npm パッケージ依存は parser 戦略(1.5-6)と地続きでここに混ぜると仕様が捻じれるので、**1.5-2 では相対パス (`./foo` / `../foo` / `.js` 拡張子含む) のみ受ける**。非相対 specifier は loader 側で `non-relative module specifier 'X' is unsupported` で明示エラー。`node:*` を再現するための builtin shim も 1.5-2 では作らない。
- **loader を新規 module に切り出す (`src/loader.ts`)**。当初は `parser.ts` を拡張して `parseModuleGraph(rootPath)` を返す方向も考えたが、`parser.ts` は `ts.createSourceFile` を呼ぶだけの 13 行の薄い wrapper で、import 解決 / DFS / 循環検出を持ち込むと責務が肥大化する。loader を別ファイルに分け、`parser.ts` は単一ファイルの parse に専念させる。`loader.loadModuleGraph(root)` は (a) `parser.parseFile` で AST を起こし、(b) AST 走査で `ts.isImportDeclaration` のみ抜き出して specifier を resolve、(c) 再帰 DFS の visiting set で循環検出、(d) topological 順の `SourceFile[]` を返す、の最小実装に倒した。エラーは `LoaderError` で `file:line:col` 付き(`CodegenError` と同じ format)に揃えてある。
- **`.js` 拡張子は `.ts` に置換**。TS のお作法に従い、source は `./foo.js` で書く想定。loader 内で `spec.endsWith(".js")` を見て `.ts` に置換し直す。`.ts` 直書きも一応受ける(loader 内部のテスト用)。拡張子無し `./foo` は `./foo.ts` を探す。index ディレクトリ解決 (`./foo/index.ts`) は持ち込まない — Node の resolution algorithm を真似ると `package.json` の `exports` まで再現する圧力がかかるので、Phase 2 の `std/fs` 整備のタイミングで判断する。
- **import の構文受付は最小**。`import { a, b } from "./foo.js"` と side-effect `import "./foo.js"` のみ受ける。`import X from`(default)、`import * as ns from`(namespace)、`import { a as b }`(rename)、`import type`(type-only)は **loader 側で全部明示エラー**。理由: (a) default export を許すと「どの export 名が default だったか」を別ルートで保持する必要があり、(b) namespace import は識別子の `.` チェーンに化けるので codegen 側のスコープ表現に新しい次元が増える、(c) rename はスコープ内で alias を解決するパスが必要、(d) `import type` は 1.5-3 の全プログラム型検証で型レベル import を別レイヤに分けるまで保留。全 module の export 名が単一 global namespace に flatten される設計 (`§名前空間` 参照) なので、import で名前を取り込まなくても codegen は名前で引ける。**loader 段の import 文の役目は依存グラフを作ることだけ**で、codegen は import 文を `continue` で読み飛ばす。
- **名前空間は単一 global、衝突は明示エラー**。複数 module で同じ class / interface / function 名を宣言したら codegen の `redeclaration of '...'` で落ちる(既存の重複登録エラーがそのまま発火する)。`topaz_class_<C>` などの C 識別子に module prefix を載せる案も検討したが、(a) mangled 名がさらに長くなり、(b) self-hosting で人間が読む頻度の高い名前なので削減したい、(c) ユーザー側で名前を選ぶだけで衝突を回避できる(`Counter` を 2 module で別物として定義したいケースは稀)、という理由でフラットを選んだ。Spinel も同じレイアウト。
- **`Emitter` 1 インスタンスで `emit(SourceFile[])` を 1 回呼ぶ**。`functionSigs` / `classes` / `interfaces` / `genericFunctions` / `genericClasses` / `arrayMonomorphs` / `mapMonomorphs` / `setMonomorphs` などの per-Emitter テーブルは全 module の宣言を吸う前提に拡張。`emit()` の Pass 1〜3 のループだけ「全 SourceFile の statements を flatten してから走らせる」形に書き換え、collectClassMembers / instantiateGenericClass / formatSignature 等の中身は無変更。これで monomorph テーブルが module 跨ぎで共有され、`Box<number>` が util.ts と main.ts の両方で使われても 1 つの monomorph に集約される。
- **非 root module は宣言のみ許可**。root file (CLI 引数で渡された .ts) は `SourceFile[]` の末尾、それ以外は依存ファイル。非 root module の top-level に `let` / `const` / 式文 / `if` / `while` 等の executable statement があれば codegen で明示エラー(`non-root module may only contain import / class / interface / function declarations (Phase 1.5-2)`)。ES module の「import が静的解決された後、module-level の executable は import 順に走る」セマンティクスを 1.5-2 ではあえて持ち込まない。理由: (a) topological 順での init を入れると monomorph や class field の初期化と順序が絡んで段違いに難しくなる、(b) src/ の self-hosting で「module level の初期化を書きたい」ケースは現状 0 件(全部 main 内の処理)、(c) 後で 1.5-4 (ヒープ管理) のタイミングで module init を扱うほうが arena 確保とセットで考えられる。今は宣言だけ flatten すれば十分。`main()` body は **root 1 ファイルの top-level statement のみ** で構成する。
- **`export` 修飾子は受け入れる、`export default` は明示エラー**。codegen の class / interface modifier チェックを `validateExportableModifiers` ヘルパに集約し、`ExportKeyword` のみスルー、`DefaultKeyword` は `\`export default\` is unsupported (Phase 1.5-2)` で落とす。それ以外の modifier(`abstract` / `declare` / `static` 等の class 単体修飾子)は従来通り「class modifier '...' is unsupported」エラー。function declaration には元々 modifier チェックが無かったので `validateExportableModifiers` を function にも呼ぶように追加(以前から `export function f() {}` は素通りしていた可能性があるが、`export default function` を弾く必要があるため明示)。`export class` / `export function` / `export interface` のいずれも codegen 上の意味は 0 — 全 module の宣言が単一 global namespace に flatten されるため、`export` の有無は同じ codegen 出力になる。可視性の厳密化は 1.5-3 (全プログラム型検証) で再評価する。
- **循環検出は visiting set ベースの DFS**。loader の `visit(absPath, importedFrom)` 内で `visiting.add(absPath)` → import 解決 → `visiting.delete(absPath)` の前後で再入を検出。再入時は `importedFrom` のソース位置を添えて `circular import detected: 'X' is already being loaded` で落とす。`importedFrom` が null になるのは root の最初の visit のみで、root が自己 import するケースでは別の visit() 内部で再入するので importedFrom は必ず non-null になる(non-null 断言で受けて typecheck を通している)。src/ では循環がないため `examples/module_cycle_{a,b}.ts` を a → b → a の最小循環として置き、`tests/smoke.sh` の `run_fail_case` で「コンパイル時にエラー、エラー出力に `circular import detected` が含まれる」を回帰検証する。なお `examples/` 直下の `.gitignore` ルールが `*.ts` のみを許可しているため、サブディレクトリは作らず flat 命名 (`module_basic_*.ts` / `module_cycle_*.ts`) で並べる。
- **生成 C の構造は変わらない**。multi-SourceFile 化しても、最終的に Emitter が吐く C は 1 本の翻訳単位(`runtime.h` を include して、全宣言を flat に並べ、`int main(void) { ... }` で root の top-level を実行)。複数 .c 出力 / 別 TU リンクは取らない。理由: (a) self-hosting で `cc` を 1 回叩く設計を維持したい、(b) monomorph テーブルを TU 跨ぎでリンク時に重複定義しないよう調整するコストが高い、(c) generic class / generic function の monomorph は全プログラムを見ないと完全な集合が決まらないので、結局 LTO 相当の処理が要る。Spinel も単一 TU 出力。バイナリサイズが問題になったら Phase 2 で再評価。
- **既知の divergence**。(a) JS の module 単位の hoisting は再現しない (= 全宣言を flat に並べて declaration order の影響を消す)、(b) `import` した名前を rebind / shadow しても警告は出ない(全部 global なので、ローカルで `const Counter = ...` を書くと外側が見えなくなるのは TS と同じ)、(c) circular import 時の partial export(JS では循環でも `undefined` 値で動く構造)は再現せず常にエラーで落とす — Phase 1.5-3 の strict field init で「使う前に未初期化を許さない」を強める方針と整合。
- **テスト**。`examples/module_basic_{shapes,util,main}.ts` を 3 ファイル module グラフとして配置(flat 命名は `.gitignore` の `examples/*.ts` ルールに合わせるため)。`module_basic_shapes.ts` が `interface Shape` と `class Square` を export、`module_basic_util.ts` が `Shape` を import して `function describe(s: Shape)` と `class Counter` を export、`module_basic_main.ts` が両方を import して `Square` → `Shape` の coercion / `Counter.step()` の round-trip を回す。期待出力は 6 行(`7 / 11 / 12 / 12 / 25 / 25`)。`examples/module_cycle_{a,b}.ts` は `class A { link: B; }` ↔ `class B { back: A; }` の最小循環で、`run_fail_case module_cycle` が `circular import detected` を含むエラーを期待。`tests/smoke.sh` に `run_module_case` / `run_fail_case` ヘルパを追加し、両 case を末尾に登録。既存の 17 ケースは全部そのまま pass。
- **未対応 (1.5-2 段階)**。(a) `node:*` / bare specifier / 絶対パス module(parser 戦略 1.5-6 まで保留)、(b) default import / namespace import / rename import / type-only import、(c) `export default` / `export { a, b }`(named re-export) / `export * from`、(d) 非 root module の executable statement(`let` / `const` / 式文 / 制御フロー、1.5-4 で module init 設計時に再評価)、(e) index ディレクトリ解決 / `package.json` の `exports` 解決(Phase 2)、(f) module-level の strict visibility(`export` 無し宣言を他 module から参照できないようにする、1.5-3 の全プログラム型検証で導入する想定)、(g) dynamic `import()`(MEMO §4.2 に元から未対応として記載済み)。

## Phase 1.5-3a 実装決定ログ(strict field init)

- **Phase 1.5-3 をさらに刻む**。MEMO §6 では Phase 1.5-3 に「全プログラム型検証 + discriminated union narrowing + `T | undefined` narrowing + strict field init + Map.get の戻り値変更 + catch binding の `unknown` narrowing」が同居していたが、union 型を持ち込む変更(後述の 1.5-3b)はランタイム ABI(reference の NULL 表現 / scalar の sentinel)に影響する一段大きな設計で、それと独立に着地できるのが **strict field init** だけ。1.4c で `MEMO §3.1` の刻む方針を 1.4c-1a / 1.4c-1b / 1.4c-2 / 1.4c-3 に分け、1.5-1 → 1.5-2 でも同じ流れを踏襲した通り、1.5-3 も 1.5-3a (strict field init) → 1.5-3b (union/optional 表現) → 1.5-3c (Map.get) → 1.5-3d (`T | undefined` narrowing) → 1.5-3e (discriminated union narrowing) → 1.5-3f (多態検出 + catch unknown) に刻む。1.5-3a は他に依存しない最小サブフェーズ。
- **constructor body の top-level のみを走査する保守実装**。`verifyDefiniteFieldInit(info)` が `info.ctor.decl.body.statements` を flat に舐め、`ExpressionStatement` の `BinaryExpression` で `operatorToken === EqualsToken` かつ LHS が `this.<ident>` のものだけを「definitely assigned」とカウントする。`if` / `for` / `while` / `try` / `switch` の中の `this.f = ...` は **無視 (= 「無代入」扱い)**。理由: (a) flow-sensitive な definite-assignment 解析を本格的に書くのは narrowing 基盤(1.5-3d)とセットでやる方が筋がよく、ここで先食いするとあとで `Scope` / narrowing stack の構造と二重になる、(b) examples / src/ の全 class は `constructor(args) { this.f = args.x; ... }` のフラットなパターンしか持たず、保守版でも実害ゼロ、(c) 将来 narrowing 基盤を入れた後でこの関数を flow-sensitive 版に置き換えるのが自然な進化。エラーメッセージに「control-flow inside if/for/while/try is not analyzed yet」を含めて、保守版であることを利用者に明示する。
- **`infoOverride` 経由 (generic class monomorph) は検査スキップ**。`collectClassMembers(cls, infoOverride?)` は (a) 通常の class declaration 処理、(b) generic class の monomorph 構築 (`instantiateGenericClass`) の両方から呼ばれる。strict field init の検査は ctor decl ノード自体を見るので、同じ generic class から生まれた monomorph はどれも同じ ctor decl を見ることになり、結果が同じになる。重複検査しても害はないが、`Array<Box<number>>` 経由で 1 クラスから何個も monomorph が生まれるケースで無駄が増えるので skip する。元の generic class declaration を Pass 2b で 1 度処理するタイミング(`infoOverride === undefined`)でのみ検査が走る。
- **field initializer / optional field の扱いは変えない**。`x: number = 0` の field initializer は引き続き `collectField` で「field initializers are unsupported; assign in the constructor」エラー、`x?: number` の optional field も「optional fields are unsupported」エラー。これらは 1.5-3b で union/optional 表現を入れた後に「optional field は constructor 代入不要、それ以外は 1.5-3a の検査対象」として整理する。1.5-3a 単独では「全 field を constructor で代入」一択。
- **検査位置は `verifyImplements` の直前**。`info.fields.size > 0 && !info.ctor` の「field-without-ctor」エラーが先、`verifyDefiniteFieldInit` が次、`verifyImplements` が最後。interface implements 検査は class が field を持つ前提で走るので、field 構造が確定した後・interface 整合性確認の前、というのが自然な順番。`verifyDefiniteFieldInit` 自体は info.fields / info.fieldOrder / info.ctor だけを見るので、infoOverride 分岐以外に状態を持たない pure な検査。
- **既存 examples すべて pass**。`class_basic.ts` (Point / Greeter) / `array_class_iface.ts` (Counter / Square / Circle) / `interface_basic.ts` (Circle / Square) / `map_set_class_iface.ts` (Counter / Square / Circle) / `try_catch_basic.ts` (MyErr / OtherErr) / `generic_class.ts` (Box / Pair) / `generic_fn.ts` (Box) / `module_basic_*.ts` (Square / Counter) はすべて constructor 直下で `this.f = arg` を順に代入するパターン。回帰なし。
- **テスト**。`examples/strict_field_init_fail.ts` を負例として追加 (`class Bad { x: number; y: number; constructor(a: number) { this.x = a; } }` — `y` 未代入)。`tests/smoke.sh` に `run_fail_case strict_field_init_fail` を追加して、エラー文字列 `is not definitely assigned in the constructor` を含むことを確認。`module_cycle` と同じ run_fail_case パターン。既存の 17 ケースは全部そのまま pass。
- **次サブフェーズ (1.5-3b〜f) の依存関係**。1.5-3b (TopazType に union/optional variant 追加) → 1.5-3d (T | undefined narrowing) → 1.5-3c (Map.get 戻り値変更) と 1.5-3e (discriminated union narrowing) と 1.5-3f (多態検出 + catch unknown narrowing)。1.5-3b は他全部の前提、1.5-3d は 1.5-3c / 1.5-3e の narrowing 機構基盤、1.5-3f は 1.5-3b の上で独立に進められる。

## Phase 1.5-3b 実装決定ログ(TopazType に union/optional 表現を追加)

- **`undefined` と `union` を別 variant として独立させる**。最初は `undefined` を「`union` の degenerate ケース」として扱う案も考えたが、(a) bare `undefined` は値を持たない sentinel で、変数として宣言できない(`cTypeName` が reject)一方、`T | undefined` は実在する値、(b) `typeFromAnnotation` が `undefined` キーワード単体を見たときに union を作るのは過剰、(c) `containsUndefined` / `withoutUndefined` のような操作が単独 variant の方が読みやすい、という理由で `{ kind: "undefined" }` と `{ kind: "union", variants }` の 2 variant に分離した。bare undefined は実用上は `===` / `!==` の片側、または `let x: T | undefined = undefined` のような widening 経由でしか現れない(inferType の identifier ブランチで `expr.text === "undefined"` を直接 T_UNDEFINED に分岐する)。
- **union の canonical 形を `makeUnion` で固定**。union の `variants` は (i) ネストした union を flatten、(ii) `typeKey` (= `typeIdent`) ベースで dedup、(iii) `typeKey` でソート、の 3 段で正規化する。これで `typeEq` を「sorted variants の positional 比較」だけで済ませられる(順序依存しない set-equal を毎回 O(n^2) で書かなくていい)。`makeUnion` が単一 variant のときは union を作らずその variant を返す(`T | T` を `T` に collapse、user が `Box | undefined | undefined` を書いても自然に `Box | undefined` になる)。empty variants は事前に reject(設計上発生しないが防御)。
- **C 表現は inner type に collapse、scalar | undefined は遅延**。`T | undefined` の C 型は (a) T が reference (array/map/set/class) → `T *` で NULL を sentinel に使う、(b) T が interface → `topaz_iface_<I>` の fat pointer で `.data == NULL` を sentinel に使う、(c) T が scalar (number/boolean/string) → cTypeName でエラー (`scalar | undefined is deferred to 1.5-3c`)、の 3 通り。scalar | undefined は別途 sentinel struct (`{ bool present; T value; }`) が必要で、Map.get の戻り値変更 (1.5-3c) と一緒に再評価する。理由: (a) class / interface | undefined だけで src/ や generic class / function の戻り値の大半をカバーできる、(b) sentinel struct を入れると runtime.h の monomorph テーブルが scalar × 3 倍に膨らみ、Map / Set の monomorph 増殖と直交するので別フェーズで扱いたい、(c) 1.5-3c で `Map.get` を `V | undefined` 化すると scalar key の Map で必然的に scalar | undefined が出るため、そのタイミングで sentinel 表現を決めるのが自然。
- **`===` / `!==` の型一致を `typesOverlap` で緩める**。従来は `expectType(right, leftType)` で右辺が左辺と同型であることを要求していたが、これだと `x: Box | undefined` に対して `x === undefined` が型不一致になる。`typesOverlap(a, b)` で「a と b に共通の variant が 1 つでもあるか」を判定し、なければエラー。これで `x === undefined` (overlap on `undefined`) は通り、`Point | undefined === Circle` (no overlap) は型エラーになる。完全に型が disjoint な比較は dead code なので拒否する設計を踏襲(JS `===` の「常に false」を許容するセマンティクスとは divergence)。
- **`===` / `!==` の lowering: undefined 片側のときだけ専用化**。lt/rt の inferType を見て、左右どちらかが `undefined` 識別子なら、value 側の表現に応じて `(x == NULL)` (reference) または `(x.data == NULL)` (interface fat pointer) に lower。interface | undefined の場合は fat pointer 全体を NULL と比較できない(vt が NULL でも data が non-NULL ならその逆も)ので、sentinel として data のみを比較する。`emitUndefinedLiteral` (undefined を assignment 文脈で吐く側) と表現を揃えてある(代入は data=NULL, vt=NULL の compound literal、比較は data のみ)。
- **widening は `applyCoercion` で no-op**。T → `T | undefined` の coercion は C 上の値表現が同一(reference は同じポインタ、interface は同じ fat pointer)なので、`applyCoercion` で「expected が union で inner が actual を受け入れられる」場合は inner で再帰するだけ。`((Box *)b)` のような cast も不要 — `Box *` と `Box * (with NULL sentinel)` は C 型として同じ。class → interface coercion(従来の唯一の暗黙変換)も union を剥がした後に直交して適用される。
- **narrowing 未実装なので union 値の使用を厳格に reject**。`inferType` の PropertyAccessExpression で base が union ならエラー、`emitCall` の console.log で arg が union/undefined ならエラー。method call は callee.expression を inferType に通すので PropertyAccess 経由で自動的に reject される。これで「コンパイル時には型が `T | undefined` でも、実行時には常に T だから大丈夫」のような場当たり的な runtime narrowing は書けない。1.5-3d で `if (x !== undefined)` の narrowing が入るまで、union 値で出来ることは (a) 代入、(b) `=== undefined` / `!== undefined` 比較、(c) 関数引数として渡す、(d) return する、の 4 つに制限される。エラーメッセージに「narrow it first; full narrowing arrives in 1.5-3d」を含めて利用者に次フェーズを示唆。
- **`emitWithExpected` の早期分岐: undefined 識別子は専用 path**。`emitWithExpected(expr, expected)` の最初で `ts.isIdentifier(expr) && expr.text === "undefined"` を判定し、`emitUndefinedLiteral(expected, expr)` で専用 lowering する。これを通さないと一般 path で `inferType(undefined identifier) === T_UNDEFINED` → `applyCoercion(T_UNDEFINED, T_BOX_OR_UNDEFINED)` で widening は通っても、`emitExpression(undefined identifier)` の scope lookup で「unknown identifier 'undefined'」になるので、`emitExpression` を呼ぶ前に専用 path で切る必要がある。bare `undefined` target (`emitUndefinedLiteral` の expected が `T_UNDEFINED` のケース) は実用上発生しないが、`NULL` を返して防御してある。
- **typeFromAnnotation に UndefinedKeyword / ParenthesizedTypeNode / UnionTypeNode を追加**。`undefined` キーワード単体は `T_UNDEFINED` を返す(`let x: undefined = undefined;` のような書き方ができるが意味は限定的)。`(T | undefined)` のような parenthesized type も透過、`T | undefined` の UnionTypeNode は variant ごとに recurse して `makeUnion` で正規化。3 つとも cTypeName / typeEq / isAssignableTo が後段でちゃんと判別できるように最小限の handle。
- **テスト**。`examples/optional_basic.ts` (positive): class | undefined と interface | undefined 両方を宣言、`undefined` で初期化、別の値を再代入、`=== undefined` / `!== undefined` を比較して boolean を console.log、helper function (`present(b: Box | undefined): boolean`) を経由しても動くことを確認(10 行出力)。`examples/optional_field_access_fail.ts` (negative): `let b: Box | undefined = new Box(1); console.log(b.v);` で `cannot access '.v' on union type` エラー。`run_case optional_basic` と `run_fail_case optional_field_access_fail` を smoke.sh に追加、合計 20 ケース全部 pass。
- **次サブフェーズの依存関係**。1.5-3c (Map.get 戻り値変更) は scalar | undefined 表現が必要なので、(a) sentinel struct を入れる、(b) scalar key の Map のみ object-wrapping する、(c) Map.get に渡された expected type を context にして codegen 戦略を変える、のいずれかが要る。先に 1.5-3d (narrowing 機構) を入れて `if (m.has(k)) { /* m.get(k) is V */ }` 的な assertion で逃げる手もある — narrowing が無いと 1.5-3c のメリット(`.get` 後に必ず narrow させて型安全に使う)が出ないので、**順序を組み替えて 1.5-3d を 1.5-3c の前に持ってくる選択肢を MEMO §6 に明示** した。

## Phase 1.5-3d 実装決定ログ(`T | undefined` の flow-sensitive narrowing)

- **順序を組み替えて 1.5-3c より先に 1.5-3d**。MEMO §6 の元の順序は 1.5-3b → 1.5-3c (`Map.get`) → 1.5-3d (narrowing) だったが、1.5-3c は `m.get(k)` の戻り値が `V | undefined` になるので narrowing が無いと値が使えない(`if (m.has(k)) { m.get(k).f }` の `m.get(k)` が `V | undefined` のまま field access に到達しエラー)。narrowing 機構を先に入れて、1.5-3c で `Map.get` を変更したときに既存の `map_set_basic.ts` が「`if (m.has(k))` で narrow 経由で通る」形に書き換えられるようにする。1.5-3b の決定ログにも書いた通りの選択肢を採用。
- **narrowing は Scope frame に overlay する**。`Scope` に `narrowings: Map<string, TopazType>[]` を `stack` と同じ深さで持たせ、`push`/`pop` で同期。`lookup(name)` は (a) binding を innermost-first で探し、見つけた frame idx を baseIdx、(b) narrowings を top から baseIdx までスキャンして最初に見つかった narrowed type を返す、の 2 段。**baseIdx より深い frame の narrowing は無視する** — 別 binding を shadowing しているケースで stale narrowing を返さないため。新規 declare は narrowings を触らないので、shadowing で同名の var を宣言した場合、その frame の narrowings には何も入らず、内側 binding が素のまま見える。代替案として「scope を flow-sensitive な単一構造に置き換える」も検討したが、(a) Topaz の Scope は今のところ lexical なフレームスタックで完結している、(b) narrowing は if/else の入退場でフレーム push/pop と完全に同期できる、という理由で overlay の方が小さく収まる。
- **narrowing 抽出は `extractNarrowing(cond, polarity)` に集約**。`cond` が `BinaryExpression` で `===` / `!==`、片側が `undefined` 識別子・他方が `Identifier`(scope に存在 + 型に `undefined` を含む)のときだけ `{ name, type }` を返す。それ以外(複合 condition、property access、関数呼び出し)は `undefined` で「narrowing なし」を意味する。`polarity = true` (then-branch) と `false` (else-branch) で strip vs. set-to-undefined を切り替える。strip 結果が空(= variable 型が `undefined` だけだった)場合は narrowing 不可で `undefined`。**compound condition (`x !== undefined && y !== undefined`) や type guard / instanceof / `in` は 1.5-3e / 1.5-3f で必要に応じて拡張する**。
- **if 文ハンドラ: branch 直前に extract、`emitStatementAsBlock` に渡す**。従来の `emitStatementAsBlock(stmt, indent)` に optional の `narrow` 引数を追加。新引数があれば push 直後に `scope.narrow(name, type)` する。これで then / else の中身 emit 中は narrowed view、外に出れば pop でクリーン。`extractNarrowing` を 2 回呼ぶ(then 用と else 用)が重複コストは小さい(数 if 分の判定だけ)、ハンドラの読みやすさを優先。
- **early-exit narrowing は `emitBlock` で carry**。1 statement ずつ emit したあと `applyCarryNarrowing(s)` を呼ぶ。`s` が `IfStatement` で (a) else なし + then が必ず exit、(b) else あり + then だけ必ず exit、(c) else あり + else だけ必ず exit、のいずれかの場合、carry-polarity を計算して `extractNarrowing(s.expression, carryPolarity)` を呼び、結果を **現在の top frame** に `scope.narrow` で install する。emitBlock の呼び出し元(`emitStatementAsBlock` / 関数 body / try body 等)が予め push しているため、この block を抜けると carry も pop される。
- **`alwaysExits` は保守判定**。`ReturnStatement` / `ThrowStatement` / `BreakStatement` / `ContinueStatement` / `Block`(最後の statement が `alwaysExits`) / `IfStatement`(then と else 両方が `alwaysExits`)を true にする。それ以外は false。false 側にハズれても narrowing が carry されないだけで動作は正しい(narrow できないところで `.field` を書くと既存の「cannot access on union」エラーで落ちる)。`for` / `while` / `do-while` 内の break / continue を「必ず exit」と判定するのは不安定なため、ループ統合まで踏み込まない。
- **narrowed scope 内での再代入: widening は未対応**。`x: Box | undefined` を narrow して `x: Box` になった scope で `x = undefined` を書くと、`inferType(expr.left)` が narrowed `Box` を返すので RHS の `undefined` が型不一致でエラーになる。これは TS の flow-sensitive 再代入(再代入後に narrow type を更新)とは divergence するが、(a) 「narrow されたまま widening」は実用パターンとして稀(普通は外側で再宣言するか別の scope を切る)、(b) 真面目に対応するには assignment 後の narrowing 更新ロジックが必要で 1.5-3d の minimum スコープを超える、(c) 必要になったら `lookupBase(name)` を追加して assignment LHS は base 型で type-check、assignment 後は narrowing をクリア、という形で素直に拡張できる。1.5-3f の多態検出と一緒に再評価する宿題。
- **`extractNarrowing` の overlap チェックは type に依存**。`b.type` が `containsUndefined` を含まない場合(narrowing 元になり得ない非 union 型)、`extractNarrowing` は `undefined` を返す。これで `if (n === undefined)` を書いて n が単に number だった場合、(1.5-3b で `typesOverlap` 違反でエラーが出るので) ここに到達しないが、防御として残す。
- **definite-assignment 検査の flow-sensitive 化は延期**。1.5-3a の `verifyDefiniteFieldInit` は constructor body の top-level の `this.f = ...` だけを集める保守実装で、`if (cond) this.f = v;` のような条件代入は「無代入」扱い。narrowing 機構が揃った今なら flow-sensitive 版に置き換えられるが、src/ と examples の現状全クラスが flat な ctor body で書けているため、self-hosting で踏むまで延期(検査が緩い側ではないので新規エラーは出ず、緩く通っているケースが将来 strict 化されるだけ)。
- **テスト**。`examples/optional_narrow.ts` で 4 関数 + 3 inline if パターン + 1 throw 経路を計 10 行で網羅: (1) `if (b === undefined) return 0;` の early-return narrowing で `b.v` アクセス、(2) `if (b !== undefined) { return b.v; } else { return -1; }` の then/else 両方 narrowing、(3) `if (s === undefined) { ... } return s.area();` の interface narrowing、(4) `if (b === undefined) { throw new Box(99); } return b.v * 2;` の throw 経由 narrowing(`alwaysExits` で throw を exit と判定して以降 narrow を carry)、(5) inline の `if (b1 !== undefined) console.log(b1.v);`、(6) inline の `if (b2 === undefined) {} else { console.log(b2.v); }`。全 10 行が期待通りに動作、既存 22 ケースとあわせて 23 ケース全 pass。

## Phase 1.5-3c 実装決定ログ(`Map.get` の戻り値を `V | undefined` 化)

- **scalar V の sentinel は struct (`{ present, value }`)、reference/iface V は NULL sentinel を流用**。3 通りの選択肢があった: (a) 全 V kind を struct で wrap して統一する、(b) value kind ごとに最適な表現を使い分ける、(c) `topaz_nan_box` のような tagged 表現を 1 つ持つ。**(b) を採用**。理由: (a) は class | undefined / iface | undefined が `T *` / fat pointer の NULL sentinel で済む既存仕様 (1.5-3b) と整合せず、`Map.get` 結果と通常の `T | undefined` で C 表現が分かれる(`emitUndefinedLiteral` / `applyCoercion` / `===` lowering が 2 通り必要になる)。(c) は doublewordに無理矢理詰める必要があり、Topaz の TypedAST が tagged union を表現できる 1.5-3e 以降であれば検討余地があるが、現状は overkill。(b) では `Map.get` の戻り値 C 型を opt_t で表現し、scalar は `topaz_opt_<scalar>` の struct、class は `T *`(NULL = undefined)、iface は `topaz_iface_<I>`(`.data == NULL` = undefined)で kind ごとに割り振る。codegen 側の identifier emit で「narrowed scalar opt なら `.value` を経由する」分岐 1 つで済むので、`cTypeName` を含めて分岐は最小に収まる。
- **`TOPAZ_MAP_DEFINE` を 6 引数化**。旧 signature `(name, key_t, val_t, hash_fn, eq_fn)` に対し、新 signature は `(name, key_t, val_t, opt_t, opt_wrap, opt_absent, hash_fn, eq_fn)` の 8 引数(3 引数追加)。`_get` 内部は `if (slot occupied) return opt_wrap(val); else return opt_absent;` で kind に依存しない。class V / iface V には `topaz_opt_passthrough(v) (v)` という no-op マクロを `opt_wrap` として渡し、`opt_t = val_t`、`opt_absent` は class なら `NULL`、iface なら(後述の)`topaz_iface_<I>_absent` を渡す。これで `_get` の本体テンプレを kind ごとに分岐させずに済む。代替案として「kind ごとに別マクロ (`TOPAZ_MAP_DEFINE_SCALAR_V` / `TOPAZ_MAP_DEFINE_REF_V`) を生やす」も検討したが、scalar K × class V のような mixed pattern まで広がると組み合わせ爆発するため却下。
- **iface absent はマクロ展開時のカンマ問題を避けて per-iface `#define` で導入**。`((topaz_iface_<I>){ NULL, NULL })` を直接 `TOPAZ_MAP_DEFINE` の引数に書くと、compound literal 内の `,` がマクロ引数区切りと衝突する(C プリプロセッサが `{ NULL` と `NULL })` の 2 引数と解釈)。回避策として **iface typedef を吐くタイミングで `#define topaz_iface_<I>_absent ((topaz_iface_<I>){ NULL, NULL })` も一緒に吐く**(`cTypeName` 側で参照だけする)。代替案として「`TOPAZ_MAP_DEFINE` 内部で per-iface helper 関数を生成する」も検討したが、`opt_absent` を「マクロ展開可能な式」として渡したかった(関数呼び出しコストは無視できるが、コードジェネレータが式を passthrough する設計が壊れる)ので、`#define` 方式を採用。
- **identifier emit の narrowed scalar opt 分岐**。`emitExpression` の Identifier ブランチで、`scope.lookup(name)` (narrowed type) と `scope.lookupBase(name)` (un-narrowed binding) を両方取得し、base が `isScalarOptUnion` かつ narrowed と異なれば `.value` で値を取り出す(narrowed 後は present == true なので safe)。これで `if (v !== undefined) { console.log(v); }` のような pattern で `console.log(v.value)` に lower される。**`scope.lookupBase` を新設**したのは、既存の `lookup` が narrowing overlay を優先返却するため、un-narrowed C 表現を取り出す経路が必要だったから。
- **`===` / `!==` undefined lowering を kind ごとに分岐**。scalar opt なら `.present == false/true` を吐く、iface なら `.data == NULL` (or `!= NULL`)、class/array/map/set なら `== NULL` (or `!= NULL`)。scalar opt の場合だけ演算子が反転する(`x === undefined` ⇔ `x.present == false`、`x !== undefined` ⇔ `x.present == true`)ので、op を直接埋め込まず `want` 文字列で切り替える。**outer 括弧を外す**: 当初 `((x.present == false))` の形で吐いていたが、clang の `-Wparentheses-equality` が `if (((...)))` を「typo の可能性」として警告するため、`x.present == false` だけ(裸)を返すように変更。`if`/`while`/`while` 述語、`&&`/`||` 内のいずれでも `==` の precedence は `&&`/`||` より高いので safe。
- **`emitMapMonomorphMacro` で kind ごとに `(opt_t, opt_wrap, opt_absent)` を埋める**。runtime.h 側にプリ展開してある scalar K × scalar V の 9 monomorph はリテラルで `topaz_opt_<scalar>` / `topaz_opt_wrap_<scalar>` / `topaz_opt_absent_<scalar>` を埋め込んだ。class V / iface V の monomorph は codegen 側で同じパターン (kind ごとに 3 値) を組み立てる。`recordMapMonomorph` 経由で型から逆引きするので、ユーザコードから一度でも `Map<K, V>` の型注釈 / `.set` / `.add` が出れば該当 monomorph が emit される。
- **既存例の書き換え方針**。`map_set_basic.ts` と `map_set_class_iface.ts` は `console.log(m.get(k))` を直接書いていたため、`Map.get` 戻り値が `V | undefined` になった瞬間に「union を console.log できない」エラー (1.5-3b) で落ちる。各 get 結果を一旦 `const x: V | undefined = m.get(k)` に受けてから `if (x !== undefined) { console.log(x); }` で narrow するパターンに書き換え。`void` 戻り型のヘルパ関数 (`function showNum(v: number | undefined): void`) で共通化する案も検討したが、`VoidKeyword` が `typeFromAnnotation` で未対応のためインライン展開を採用(`void` 型サポートは別フェーズで必要になったタイミングで入れる)。expected output は 1 行も変わらない。
- **テスト**。新規 `examples/optional_map_get.ts` を追加し、(a) scalar V (`Map<string, number>`) の hit / miss、(b) class V (`Map<string, Item>`) の hit / miss、(c) iface V (`Map<number, Named>`) の hit / miss、(d) 関数引数で `Map<string, number>` を受け取り `m.get(k)` を narrow する経路、を計 8 行で網羅。既存 22 ケース + `optional_*` 3 ケース = 25 ケース全 pass。負例 (`m.get(k).f` を narrow なしで書いてエラー) は 1.5-3b で追加済みの `optional_field_access_fail.ts` で間接的にカバーされているため新規追加せず。
- **未対応 / 将来課題**。(1) Map K に class / interface を取る方向(reference identity で `topaz_hash_pointer` を使えば素直に拡張可能だが、現状 src/ では未使用)、(2) `Set` 側の `.add` / `.has` も将来 `V | undefined` 的な戻り値が必要になった場合 (`Set.has` は `boolean` のままで問題ないが、`Set.values()` のような iterator を入れる 1.5-3.5 で再評価)、(3) scalar | undefined の代入 lvalue ハンドリング(narrowed scope 内での widening 再代入は 1.5-3d の「未対応リスト」と同じ理由で 1.5-3f で再評価)、(4) `Map.set` を `V | undefined` 渡しで「key を消す」JS の wrong-use semantics は採用せず、`undefined` を value として受けたら型不一致エラーで落とす(`Map.delete` を明示的に使わせる)。

## Phase 1.5-3e 実装決定ログ(discriminated union narrowing)

- **TopazType に `dunion` variant を別途追加し、`union` とは並列に持つ**。`Circle | Square` のような class-only union のうち、各 variant class が同名の string-literal field(例: `kind: "circle"` / `kind: "square"`)を共有する場合のみ `{ kind: "dunion", variants, discriminator }` に collapse する。`union` (1.5-3b) と `dunion` を統合する案も検討したが、(a) `union` 側は narrowing 後に分岐ごとの C 表現が変わらない (`T | undefined` は inner T の C 型を流用) のに対し、`dunion` は fat pointer `{ topaz_string kind; void *data; }` を新規に持ち込むため、`cTypeName` / `emitWithExpected` / identifier emit の lowering が完全に分岐する。(b) `tryMakeDiscriminatedUnion` の判定(全 variant が class でかつ共通 string-literal field 名 + 各 variant ごとに異なる literal 値を持つ)は型構築時の 1 回しか走らないため、`makeUnion` 内に押し込むと build cost が上がる。型 kind を分けた方が emit パスが見やすい、を優先して別 variant に。
- **string literal field 型 (`kind: "literal"; value: string`) を 1.5-3e でだけ局所的に導入**。class field 型としては正規の `string` ではなく `{ kind: "literal", value: "circle" }` のような細い型を一時的に許容する必要がある(でないと discriminator として「`kind: "circle"` で確定」が判定できない)。但し literal 型を一級市民にすると `inferType` 側の widening (literal → string) を一斉対応する必要があり scope が広がりすぎるため、**class field の宣言時にのみ literal を受理**(`x: "circle"` 構文を field decl で許す)し、`typeEq` / `isAssignableTo` は literal を string の subtype として通すだけの最小実装にとどめた。本格的な literal 型(関数戻り値 / generic 引数 / template literal 用)は 1.5-3.5 以降で再評価。
- **C 表現は fat pointer `{ topaz_string kind; void *data; }`**。class 型と同じく `data` slot に元 instance の `T *` を入れ、`kind` slot に discriminator の値(string literal を `topaz_string` 化したもの)を redundant に保持する。代替案として「interface fat pointer と同じく vtable ポインタを参照して RTTI を引く」も検討したが、(a) 1.5-3e の時点では RTTI 機構自体がまだ無く(1.5-3f で初めて入る)、(b) `switch (s.kind)` を C の `switch` 文に lower するためには discriminator が string として直接読める必要がある(vtable 経由だと `s.vt->get_kind(s.data)` のような関数呼び出しを毎回挟む必要があり、case ラベルが定数式にならない)。kind を fat 構造体に raw に持つ方が `switch` lowering が素直。
- **`emitSwitchStatement` で dunion 専用パターン (`switch (<id>.<discriminator>)`) を検出して narrow**。判定: switch expression が PropertyAccess で、base が identifier、scope lookup した型が `dunion`、かつ property 名が discriminator と一致する場合。pre-pass で `dunionLiteralFor(unionType, className)` を全 variant 分計算して `literalToClass: Map<literalValue, className>` を作り、各 case 句の expression を見て string literal → class を引き当てる。一致した case 内では `scope.narrow(idName, classOf(narrowCls))`(1.5-3d で入れた narrowing overlay にそのまま乗る)、不一致 / `default` は narrowing 無しで処理する。`switch` 以外(`if (s.kind === "circle")` 風の比較)を narrowing 対象にする案もあったが、(a) 比較演算子経由のパターンは literal 型推論を ` ===` lowering 側に持ち込む必要があり 1.5-3e の scope を超える、(b) self-hosting で `switch (t.kind)` を多用する想定なので switch だけ通せば実用上は十分、と判断して見送り。
- **`emitWithExpected` で class → dunion 構築**。`expected.kind === "dunion"` かつ actual が class の場合、`((topaz_dunion_<sorted>){ .kind = topaz_string_literal("<discriminator-value>"), .data = (void *)<expr> })` の compound literal を吐く。discriminator 値は class info から `dunionLiteralFor` で引く(class が複数の dunion に同時に属していても discriminator 値はクラス自身の field 定義から決まるので一意)。`emitWithExpected` の coercion site は既存の 4 サイト(変数初期化 / 関数引数 / return / 代入 RHS)+ container 引数を流用、追加サイトは無し。
- **`dunionMonomorphs` で typedef 出力を遅延**。`recordDunionUse(t)` を `typeFromAnnotation` で union node を `dunion` に collapse したときに呼び、`typeKey` をキーに重複排除。`emit()` の末尾で interface vtable 定義の前に `typedef struct { topaz_string kind; void *data; } topaz_dunion_<sorted>;` をまとめて出力する。配置位置を array / map / set monomorph macro の **前** に置く理由: container の class / interface 要素経路は既存 monomorph 機構を共有するが、dunion を要素に持つ container の必要性は現状例 (`Shape[]` で代用可能) では出ていないため、後段の `arrayMonomorphs` / `mapMonomorphs` / `setMonomorphs` を触らずに済む。
- **identifier emit の narrowed dunion → class cast**。`emitExpression` の Identifier ブランチで `lookupBase` (un-narrowed) と `lookup` (narrowed) を両方取り、base が `dunion`・narrowed が class なら `((topaz_class_<C> *)(<id>).data)` で剥がす。1.5-3c の scalar opt narrowing (`.value` 経由)と同じパターンで `lookupBase` を流用。`.kind` access は narrow 前でも常に dunion の `.kind` field を直接読める(switch lowering 用)ので、PropertyAccess の base 型が `dunion` で property 名が discriminator なら `(<id>).kind` を返す分岐を 1 つ追加。
- **未対応 / 将来課題**。(1) `if (s.kind === "circle")` 経由の narrowing(literal 型を 1 級にした段階で 1.5-3.5 か後で対応)、(2) dunion 要素を持つ container (`Shape[]`)、(3) **3 variant 以上**の dunion(現状は 2 variant の `Circle | Square` のみ例に存在するが、N variant に拡張する追加コードは無いはず、self-hosting でぶつかったら踏み穴を確認)、(4) class が複数 dunion に属する複雑な discriminator graph(現状は class A が 1 つの literal 値 / 1 つの discriminator field しか持たないので衝突しない)、(5) `default` 句内での `Exclude<...>` narrowing(全 variant が case で網羅されたか判定が必要)、(6) **discriminator field の class 外からの直接書き換え禁止**(現在は readonly 強制が無く、`s.kind = "square"` で実 class と整合しない fat pointer を作れてしまう。1.5 残りの readonly / immutable 設計とセットで対応)。

## Phase 1.5-3f 実装決定ログ(catch binding の `unknown` narrowing + `instanceof`)

- **TopazType に `{ kind: "unknown" }` を追加、C 表現は `void *`**。`any` ではなく `unknown` を入れる(`any` は型検査を全部 bypass する性質で、本コンパイラの「型注釈は信用せずヒント扱い」とは別の方向に逃げ道を作るため明示的に未対応のまま)。`cTypeName` は `void *` を返し、`typeEq` / `isAssignableTo` は same-kind なら true / 他からの widening は不可(`unknown` への自動 widening は混乱の元なので、`emitWithExpected` 経由の coercion も unknown 側を expected に持たせない)、`typeIdent` は `topaz_unknown` (monomorph 名衝突回避用、現状 dunion 等の名前生成で間接的に使われ得るため slot を切る)。
- **catch binding の型注釈を optional 化**。`emitTryStatement` で `vd.type` が無い場合 → `T_UNKNOWN`、`UnknownKeyword` → `T_UNKNOWN`、class type → 既存パス(`(topaz_class_<E> *)topaz_throw_value` cast)を維持。背景: 1.5-1 で「catch (e: ClassName) の型注釈を必須」にしたのは、catch binding を class instance 以外から守るための gate だった。`unknown` narrowing が入った今、`catch (e)` / `catch (e: unknown)` を受けて `if (e instanceof BoomError)` で安全に narrow できるため gate を緩める。class 注釈の backwards-compatible 受理は意図的に残す(複数 throw 種別を catch する必要がない場合、catch (e: ClassName) の方が narrow 不要で書きやすい)。
- **`instanceof` を binary operator として AST に追加**。`emitExpression` と `inferType` の BinaryExpression で `ts.SyntaxKind.InstanceOfKeyword` を分岐。**右辺は宣言済み class 名識別子に限定**(`<id> instanceof <expr>` の `<expr>` が複雑な式や interface 名だと RTTI 引きが効かない)。左辺の型は (a) `unknown` (catch 経路)または (b) class 自身(`b instanceof BoomError` のような tautology、interface narrowing と将来の symmetry のため許容)のみ。inferType は常に `boolean` を返す(narrowing 効果は `extractNarrowing` 側でのみ surface)。
- **RTTI は全 class struct の先頭に `const char *__topaz_class_tag` フィールドを置く**。`emitClassStruct` で必ず先頭 (オフセット 0) に `const char *__topaz_class_tag` を出し、`emitConstructorDefinition` で `calloc` 直後に `__topaz_this->__topaz_class_tag = &topaz_class_<C>_tag;`(per-class static sentinel `static const char topaz_class_<C>_tag = 0;` を struct と一緒に emit)を書く。検討した代替: (a) **alloc 直前にヘッダを付ける**(`alloc(sizeof(header) + sizeof(*self))` で `header.tag` を仕込み、user pointer はその後ろ)。利点は struct 定義を汚染しない、欠点は `sizeof(*self)` / `field offset` / `Map / Set のポインタ比較` が全部 user pointer 基準のままになるよう alloc 側で逆オフセットが必要(`free` / `realloc` でも逆オフセット、複雑)。(b) **vtable ポインタを流用**(interface fat pointer と統一)。class の場合 vtable 自体が無いので新規に「per-class vtable (空 + tag)」を作る必要があり、struct field 1 個追加とコスト同じ。(c) **`__topaz_class_tag` を struct 先頭の field**(採用)。利点は (i) `((const char * const *)x)` で tag だけ読める(struct layout を知らなくて済む)、(ii) sizeof / field offset は自然に変わる(`offsetof` で計算するなら 8 byte 増えるだけ)、(iii) `calloc` で 0 埋めしてから constructor が一度だけ overwrite するので thread safety は class 自体と同等。**当初の `__topaz_empty` char dummy(0 field class 用)は不要になったため削除**(`__topaz_class_tag` が常に最初の field なので、空 struct エラーは構造的に起こらない)。
- **`x instanceof C` の lowering は NULL guard 付き stmt expression**。`({ void *__t = (<x>); __t != NULL && *((const char * const *)__t) == &topaz_class_<C>_tag; })` の GCC stmt expr で `<x>` の二重評価を防ぐ。NULL guard は (a) `x: ClassName | undefined` 経路で undefined sentinel が `NULL` のため crash 防止、(b) catch binding が常に non-NULL とは保証されない(`throw null` 相当は構文的に禁止しているが、`void *` 経由で NULL が紛れる将来パスへの保険)。`x instanceof C` を `if`/`while`/`&&`/`||` 内で直接書ける(boolean 値を返す)、narrow 効果は `extractNarrowing` が surface する。
- **`extractNarrowing` を拡張して `<id> instanceof <Class>` を polarity=true でのみ narrow**。class union ではなく `unknown` から concrete class への narrowing なので、negative side(`!instanceof`)で「unknown のまま」narrow しても意味が無い(elseブランチで他の type に絞れない、`Exclude<unknown, C>` = `unknown`)。1.5-3d の if-then / if-else / early-return 経路にそのまま乗るので、`if (e instanceof BoomError) { console.log(e.msg); }` の中で `e: BoomError` として field access が通る。
- **identifier emit の narrowed unknown → class cast**。`emitExpression` の Identifier ブランチで base が `unknown`・narrowed が class なら `((topaz_class_<C> *)(<id>))` で cast(`<id>` の C 表現は既に `void *`)。1.5-3c の scalar opt narrowing / 1.5-3e の dunion narrowing と同じ `lookupBase` パターンで実装。
- **多態検出は既存の `inferType` 型一致チェックで実質カバー済み**。1.5-3 の本来 scope だった「同じ識別子が異なる型で使われたらエラー」は、既に 1.5-3a 以前から `let x: number = ...; x = "str";` のような assignability check で reject されている(`isAssignableTo` が string → number を通さない)。1.5-3f で**追加コード無し**で要件を満たしているのを確認した。残る polymorphism source は (a) generic function / class の型引数バインド(monomorphize で別関数になるので「異なる型」ではない)、(b) interface fat pointer 経由の dispatch(コンパイル時に concrete class が分からないが、interface 型は単一で fix されている)、(c) dunion (1.5-3e、narrow 後は単一 class)。本質的な multi-typed identifier は現時点で構造的に作れない。
- **`console.log` / property access / method call の unknown は明示エラー**。narrow せずに `e.msg` / `e.method()` / `console.log(e)` を書いたら「cannot access '.msg' on `unknown` (narrow with `instanceof` first)」のような hint 付きエラー。`console.log(e)` を許容して何か汎用 fallback(`<unknown:0x...>` 等)を吐く案もあったが、TS の `unknown` セマンティクスが「narrow 強制」なので合わせる。1.5-3b の union access reject と同じパターン。
- **テスト**。新規 `examples/catch_unknown.ts`(positive 7 行: `catch (e: unknown)` + `instanceof` 分岐 2 種、`catch (e)` 注釈なし、`x instanceof FizzError` 自明な false、nested try で outer catch が異なる class を catch する rewrap、`b instanceof BoomError` 自明な true)、`examples/catch_unknown_unnarrowed_fail.ts`(negative: narrow せずに `e.msg` 触ってエラー)を追加。28 ケース全 pass。catch_unknown.ts の `function trigger(which: number): number` で `: number` を指定しているのは、`: void` が `typeFromAnnotation` で未対応のため(関数は実際には常に throw して return しないが、戻り値型として `void` が要る場合は将来 `void` 型対応と一緒に解禁)。
- **未対応 / 将来課題**。(1) `instanceof` 右辺の interface 名(class hierarchy が無い現状、interface narrowing は別途 vtable identity 比較 or per-class implements bitmap が必要)、(2) `typeof e === "string"` のような primitive narrowing(catch payload が class instance 限定なので現状不要)、(3) `unknown` 同士の `==` / `===` 比較(reference identity になるが、現状 catch 経路でしか unknown が出ないため使用例なし)、(4) `unknown` を関数引数 / 戻り値で取る(catch binding 外で `unknown` 型注釈を書ける構文路自体は通すが、narrowing せずに渡す pass-through 以外の使い道が無く、self-hosting でぶつかった時に必要箇所だけ開ける)、(5) `unknown` の Array / Map / Set 要素(同上)、(6) **複数 catch handler の syntactic sugar** (`catch (e: A | B)` のような union catch、現状 `catch (e: unknown) { if (e instanceof A) ... else if (e instanceof B) ... }` で代替)、(7) `__topaz_class_tag` field の 8 byte overhead(self-hosting で問題になるか要観測、generic class monomorph も 1 tag を持つので mono あたり overhead が掛かる)。

## Phase 1.5-4 実装決定ログ(per-process arena でヒープ leak 回収)

- **per-process arena 戦略を採用**。前提は「コンパイラは 1 プロセス = 1 コンパイル」(`MEMO §6.1.5-4` で決定済み)。alloc は global bump、free は no-op、プロセス終了で OS が arena chunk を一括回収する。検討した代替: (a) **BDW conservative GC**(self-hosting の範囲では過剰、stack scanning と signal セマンティクスが C コンパイラのプラットフォーム差で噛む)、(b) **reference counting** (`Array.push` のたびに RC 操作が刺さる、循環参照対策で weak ref が要る、Cost が読めない)、(c) **region-based + region IDs**(関数 scope ごとに region を切る、現状 expression 単位で string concat が走る経路で region 推論が破綻)。**arena に決めた根拠**: コンパイラの一回限り起動という性質、OS が最終回収するという保証、free 不要のシンプル実装、これら 3 つが全部噛み合う。Phase 2 で「Promise / async-await」を入れた時点で per-task arena へ拡張する余地は残る(個々の async task が独立 arena を持つ、task 終了で arena を一括 drop、というデザインへ移行できる構造)。
- **chunk-based bump allocator**。`topaz_arena_chunk { struct topaz_arena_chunk *next; size_t cap; size_t used; size_t _pad; }` (32 bytes、payload を 16-byte aligned に揃えるために `_pad` を 1 つ入れる)を linked list で繋ぐ。`topaz_arena_alloc(size)` は `(size + 15) & ~15` で 16-byte aligned に切り上げ、現在 head chunk に空きがあれば bump、なければ新 chunk を `malloc(sizeof(chunk_header) + max(64KB, requested))` で確保して head に push。chunk 単位の `malloc` だけが OS-level の alloc 呼び出しに残る(本当に必要な 1 箇所)。**初期 chunk size 64KB の根拠**: 28 examples を流すと最大でも 2-3 chunks しか消費しない一方、ヒープ alloc 失敗を例外的扱いにできる(現状 OOM はそのまま `abort`、これは Phase 1.5 段階での適切な動作)、また per-alloc の linked list overhead が無視できる程度に小さい。
- **alignment と padding**。`alignof(max_align_t)` は x86_64 / arm64 で 16(`long double` を保持できる alignment)。`sizeof(topaz_arena_chunk)` を 32 (3 ポインタ/size_t + 1 pad = 4 × 8 = 32) に揃えることで、`malloc` が返す 16-byte aligned なポインタの直後 (`(char *)(chunk + 1)`) も 16-byte aligned になる。検討した代替: (a) `_Alignas(max_align_t) char data[]`(stdalign.h 必須、C99 では使えない、現状 ターゲットは C99 + `bool` の素朴な subset)、(b) 動的に alignment offset を計算する(初回 alloc で `(payload + 15) & ~15 - payload` を bump、毎 chunk で 0-15 bytes ロス、コードが複雑)、(c) `_pad` field を 1 つ入れる(採用、明示的で transparent、`sizeof` が固定なので decoder side で計算不要)。
- **`topaz_arena_realloc` は単純な alloc + memcpy**。`Array.reserve` の grow と `Map / Set.rehash` の 2 箇所でしか使われない。両方とも倍々 / 増分の growth strategy なので「古い領域を捨てる」コストは amortized O(1) に収まる。**in-place 拡張の最適化は意図的に省略**。in-place するには「直前の alloc が同じ chunk の末尾にあるか」を判定する必要があり、(a) alloc ごとの metadata が増える、(b) realloc 対象が `Array.data` のような中間ポインタの場合、その間に他の alloc が走っていない保証が無い(現状 single-thread だが、`Array.push` の途中で何かを再帰的に呼ぶケースで破綻する)、(c) 「節約できる」のは grow の **古いブロック** 分(`a->cap * sizeof(elem_t)`、Array なら最大 2× 倍の前段)で、peak memory への影響は最大 +100% (peak の倍まで膨らむ)。Self-hosting でも Map / Array が peak memory の dominant にはなりにくい(string buffer の方が大きい想定)ので、Phase 2 で必要になったら再評価。
- **`topaz_arena_calloc` の overflow check は省略**。`size_t total = n * size;` で overflow した場合の挙動は未定義に近いが、(a) Map / Set の rehash で渡す `n * sizeof(slot)` は `n` が `cap` から来ていて、cap は `* 2` で grow される(初期 8、現実的に到達するのは 2^30 = 1G slots = TB 級メモリで OS が先に死ぬ)、(b) class instance の `topaz_arena_calloc(1, sizeof(*self))` は `n=1` で overflow しない、なので overflow は実用上起き得ない。Phase 2 で stdlib `Array` などを書いた段階で「ユーザ入力から alloc size を計算する」経路が出てきたら、`overflow != 0` の場合 abort の guard を入れる。
- **`free` の no-op 化と stdlib `free` の物理削除**。runtime.h 内の `free(m->slots)` / `free(s->slots)` (rehash 内、Map / Set の 2 箇所) は単純に削除(arena なので呼ばなくて良い)。stdlib `free` 自身は `<stdlib.h>` 経由で透過にリンクされるが、現状 codegen が `free(...)` を吐く経路は無くなる。**意図的に `#define free(p) ((void)0)` 等のマクロ shadow は入れない**(混乱の元、`malloc` を直接呼んでいる arena_alloc 内の chunk header alloc とのペアリングが透過に見える方が良い)。
- **codegen の class allocation 経路**。`emitConstructorDefinition` の `calloc(1, sizeof(*self))` を `topaz_arena_calloc(1, sizeof(*self))` に置換。`calloc` は失敗時 NULL を返す pointer 契約だったが、arena 側で OOM を `abort` で潰すため、「`if (!self) abort();` の guard 行」も削除(arena が返すポインタは常に non-NULL)。出力 C はその分 1 行短くなる(28 examples で延べ ~30 行縮む)。
- **テスト戦略**。新規 `examples/arena_stress.ts` を追加: (a) Array 1000 push (10 回 doubling で realloc 経由)、(b) class 1000 new (arena_calloc 経由、各 instance 約 16 bytes (`__topaz_class_tag` + `v`) で 16KB)、(c) string `+` を 200 回累積で総 buffer 12 万 bytes 程度 (chunk boundary を跨ぐ)、(d) Map 500 set (rehash 約 6 回、各 slot ~24 bytes)、の 4 経路を 1 実行で総当たり。全 alloc を arena に乗せた後、(i) chunk handover が正しく動くこと、(ii) 16-byte alignment が破綻しないこと、(iii) realloc 経由の memcpy が古い data を正しくコピーすること、を確認。合計 9 行出力で smoke に組み込み、29 ケース全 pass。
- **既知 divergence の更新**。`MEMO § 既知の divergence` の「string 連結は毎回 `malloc`、解放はしない」「Map / Set の slot buffer や rehash で確保したテーブルも同じく leak 前提」「throw した class instance は leak」の 3 つは「**arena に乗ったのでプロセス終了で OS が回収**」に書き換え。peak memory への影響(Array doubling で peak の 2 倍まで陶器、Map rehash で peak の 1.75 倍まで膨らむ)は新規 divergence として記録。Phase 2 で per-task arena に拡張する時の挙動も別途追記。
- **未対応 / 将来課題**。(1) **per-task arena**(Phase 2 で async-await / Fiber を入れた時の自然な拡張先、現状は single-process なので不要)、(2) **stack-bound region**(関数 scope で alloc を region として切り、return で drop する最適化、self-hosting 通過後にホットパスで適用検討)、(3) **realloc の in-place 拡張** (上述、必要になったら最後の alloc が match するかの metadata を chunk 末尾に入れる)、(4) **arena の reset 機構**(REPL や interpreter 起動時の reuse、現状コンパイラは 1 プロセス 1 回でいいので不要)、(5) **OOM 時の挙動を `abort` 以外にする**(現状 stderr に "topaz: out of memory" + abort、stack trace 無し、Phase 2 の error reporting と一緒に再設計)、(6) **大きな alloc (>64KB) の oversized chunk が無駄に大きい場合の chunk reuse**(現状は専用 chunk として head に挿入され、続く小さな alloc は満杯になっていない既存 chunk を再利用できない。chunk 探索を head only から linked-list scan に変えれば直るが、本来 ~MB 級の alloc は class instance / string concat では稀、Phase 2 で大きな buffer を扱う場面が出たら対応)。

## Phase 1.5-3.5a 実装決定ログ(template literal の `topaz_string_concat` chain への lowering)

- **template literal を最初のシュガーに選んだ理由**。`src/codegen.ts` の self-hosting 棚卸しで 280 箇所と最頻使用、かつ runtime に新ヘルパ(`topaz_number_to_string` / `topaz_boolean_to_string`)を入れる以外は既存の `+` 用 `topaz_string_concat` をそのまま再利用できる「小さく入る一手」。arena (1.5-4) が入った直後なので、毎回 string alloc が走るシュガーを投入しても peak memory が +100% に収まる(arena chunk reuse)安心感がある。1.5-3.5 の他項目(`for-of`、arrow + closure、destructuring、optional chaining 等)はそれぞれ大きい設計判断(iterator interface、closure キャプチャの C 表現、let の lowering 形態)を含むので別サブフェーズで切る。
- **runtime 側の API は 2 つ**。`topaz_number_to_string(topaz_number) -> topaz_string` と `topaz_boolean_to_string(topaz_boolean) -> topaz_string`。検討した代替: (a) **codegen が直接 `snprintf` 風の式を吐く**(同じ ECMA-262 ToString ロジックが codegen 側に漏れる、リテラル constness や arena との絡みも codegen が知る必要がある)、(b) **`__topaz_to_string<T>(...)` の generic dispatch**(現状 generic monomorph が runtime まで広がっていない、worklist もアクティブにしないと出ない)。**ヘルパ 2 つに決めた根拠**: substitution の型は `inferType` の時点で number / boolean / string のいずれかに絞られているので、codegen 側で固定の関数名を吐けば良い。`topaz_string` 値の場合は wrap 不要で identity(関数呼び出しも入れない)。
- **`topaz_number_to_string` は既存 `topaz_emit_number_shortest` を refactor**。`putchar` / `fwrite` / `printf` 全部を char buf への bump 書き込みに置換、戻りを `topaz_string`(buf は `topaz_arena_alloc(48)`)に。検討した代替: (a) **既存 `topaz_emit_number_shortest` を残して別 inline function `topaz_number_to_string` を追加**(同じロジックが二重になる、format バグが入った時の修正漏れリスク)、(b) **`vsnprintf` で動的 buf size**(C99 では portable だが二度走らせる必要があり遅い)。**arena alloc 48 bytes 固定の根拠**: ECMA-262 ToString の worst case は (a) integer 形式 21 桁 + sign = 22 chars、(b) 指数形式 `-1.<19 digits>e+308` = ~26 chars、(c) 小数形式 `-0.<5 leading zeros><19 digits>` = ~27 chars、全部 48 byte に収まる。`24` で integer 用 buf を別取りしている分岐だけは local snprintf で別 alloc(integer は 99.9% のケースで桁数が少ない、cap 24 で十分)。NaN / Infinity / 0 / integer はすべて static 文字列リテラル戻りで arena alloc なし(`topaz_string.data` は `const char *` だから static lifetime と arena lifetime を統一して扱える)。
- **`topaz_console_log_number` は `topaz_number_to_string` 経由に統一**。以前は `putchar`/`fwrite`/`printf` を直接呼んで '\n' で締めていたが、これだと `topaz_number_to_string` のテストは template literal 経由でしかできず regression が分散する。`topaz_string s = topaz_number_to_string(n); if (s.len) fwrite(s.data, 1, s.len, stdout); putchar('\n');` に統一すると、(a) 既存の `number_format.ts` smoke が `topaz_number_to_string` の format 回帰テストとして機能、(b) コードが 30+ 行から 3 行に縮む、(c) 副作用として `console.log(n)` も arena に毎回 24-48 bytes 焼くようになるが、template literal 投入で arena cost は元々跳ね上がるので相対的な影響は無視できる。
- **`topaz_boolean_to_string` は static literal 戻り**。`{"true", 4}` / `{"false", 5}` を `static const char[]` から `topaz_string` に詰める(arena 不要)。`true_str` / `false_str` を 2 つ別々の static にすることで、buffer overlap の心配なくいつでも返せる(stack 上の auto に詰める必要なし)。`topaz_console_log_boolean` は元の `fputs(b ? "true\n" : "false\n", stdout)` をそのまま残した(2 文字節約のためだけにヘルパ経由にすると `\n` 付き / 無しの分岐が分散して読みにくい)。
- **codegen 側の TemplateExpression 処理は 3 個所**。(1) `emitExpression` の `isStringLiteral` 隣に `isTemplateExpression` 分岐を追加して `emitTemplateExpression` に飛ばす。(2) `inferType` の `isStringLiteral` 隣に `isTemplateExpression` 分岐を追加し、`T_STRING` を返す前に **全 span の expression を inferType** して number / boolean / string 以外を reject。class / interface / array / map / set / union(narrowed されてない `T | undefined`)は明示エラー。(3) `emitStringLiteral` の signature を `ts.StringLiteral | ts.NoSubstitutionTemplateLiteral | ts.TemplateHead | ts.TemplateMiddle | ts.TemplateTail` に広げる(`text` プロパティは全部共通の `LiteralLikeNode` 系統だから escape ロジックは流用可能)。`expr.text` の non-ASCII guard / `\n` `\t` `\\` `\"` の escape table は既存と同一。
- **lowering は左結合の `topaz_string_concat` chain**。`` `hello ${x} world ${y}!` `` を head + (sub₀, mid₀) + (sub₁, tail) に分解し、`concat(concat(concat(concat("hello ", str(x)), " world "), str(y)), "!")` と展開。`acc` を string で持つナイーブ実装で 90 行に収まる。**「空フラグメントは skip」の最適化を入れる**根拠: `` `${a}${b}` `` のような adjacent substitution は middle が空 string、`` `${name}` `` のような pure-substitution は head と tail が両方空。空 string concat は runtime で 1 byte arena alloc + `if (a.len) memcpy(...)` の guard が走るが、これを毎回避けると arena への圧力が template の数に比例しなくなる。実測で `examples/template_literal.ts` の 1 行 `` `${name}` `` は `topaz_console_log_string(name)` まで折り畳まれて concat 呼び出しが 0 回になる(`acc === null` 防御コードが死んだコードのままなのは型シグネチャ上不可避、コメントで unreachable と明記)。
- **substitution の型は narrowing 経由を許容**。`function describe(label: string | undefined): string { if (label !== undefined) return \`${label}\`; ... }` のように narrow 後の identifier を埋め込めるよう、`inferType` は `scope.lookup` の結果(= narrowing overlay 後の型)を見る。narrow されていない `string | undefined` 等の union は「got `topaz_union_string_or_undefined`」エラーで reject(検証済み: `/tmp/tpl_union.ts` で正しく落ちる)。class / interface / array / map / set もそれぞれ「got `topaz_class_<C>` / `topaz_iface_<I>` / `topaz_array_<E>` / ...」のメッセージで落ちる(`examples/template_literal_unsupported_fail.ts` を fail 回帰に追加)。
- **`double` は C のキーワードなので example 内の関数名は `twice` に**。template literal の expression substitution に関数呼び出しを混ぜたケース(`` `double(${n})=${double(n)}` `` 風)を書いて smoke を回したら `cc` が `'type-name' declaration specifier` で落ちた。codegen 段で「ユーザ定義 identifier が C 予約語と衝突したら mangle する」のは Phase 1.5-3.5 のスコープ外(self-hosting の `src/codegen.ts` には `double` も `float` も使われていない)、example 側で回避。**回避を選んだ根拠**: keyword sanitizer を入れるなら C99 + C11 の予約語表をメンテする必要があり、`function double` のような ergonomics は self-hosting に不要、Phase 1.5-6 の self-hosting 通過時に踏んで初めて優先度が立つ。
- **smoke 戦略**。新規 `examples/template_literal.ts` で (a) 各 substitution 型(number / boolean / string)、(b) 空 head / tail / 隣接 substitution、(c) `1e+21` / `1e-7` の科学記法、(d) 関数呼び出し / プロパティ / メソッド呼び出し、(e) `T | undefined` の narrow 後、(f) class field / method、(g) `\t` / `"` の escape、(h) ループ内連続 concat による arena 圧、の 20 行を 1 ファイルでカバー。fail 回帰 `examples/template_literal_unsupported_fail.ts` は class instance を埋め込んで「template literal substitution must be number / boolean / string」を確認。合計 30 success + fail ケースが pass。既存 `number_format` / `boolean_print` / `string_basic` / `arena_stress` 等は全部引き続き pass で `topaz_number_to_string` refactor の regression 無し。
- **未対応 / 将来課題**。(1) **tagged template (`` tag`...` ``)**(self-hosting 不要、parser 戦略が固まる前に入れる意味が薄い)、(2) **escape sequence の Unicode** (`\u{1f600}`)(非 ASCII を string に入れる経路は UTF-16 length divergence の問題と一緒に Phase 1.5 末で再評価)、(3) **substitution に class / interface を許す toString policy**(現状はエラーで落とすだけ、Phase 2 で `.toString()` メソッド or 型ごとの format policy を入れる時に解禁)、(4) **`+` operator も同じ to_string ヘルパに統一する**(現状 `+` は string + string しか受けない、template literal だけが mixed type を toString して concat する非対称性、self-hosting で `+` の方を使っている箇所が多いなら collapse する選択肢)、(5) **template literal の compile-time folding**(全 substitution が constant なら C リテラルに畳む、optimize-level の最適化、self-hosting 通過後)、(6) **string interning / dedup**(同じ literal を複数の template で使った時に共有する、現状 arena は各 literal を独立に持つが C compiler 側で string pooling が走るので runtime 上は影響 0)。

## Phase 1.5-3.5b 実装決定ログ(`for-of` over `Array<T>` の lowering)

- **`for-of` を「Iterator interface 経由」ではなく「container 個別ハードコード」で先に着地させた**。検討した代替: (a) **`Symbol.iterator` 相当の protocol を設計してから for-of を入れる**(JS の正攻法だが、Array / Map / Set / 自前 class iterable をすべて拾うには runtime に `topaz_iter_<T>` の interface + `_next() -> { value, done }` + per-container iterator instance の alloc が必要、設計分量が大きく一度入れると後で剥がしにくい)、(b) **`for-of` 自体を AST レベルで通常 `for` に書き換えるマクロ的展開**(直線的だが Map / Set の iteration を後付けする時に再展開が必要)、(c) **Array だけハードコードで in-line に index for-loop を吐く**(採用)。**(c) を選んだ根拠**: (1) self-hosting の 58 箇所のうち過半が `for (const x of arr)` の Array iteration で、Map / Set 経由は `Map.values()` の登場まで深掘りしなくて済む。(2) `Array<T>` は既に `->data` / `->len` の C 表現を持っているので、追加 runtime コードが 0 行で済む。(3) Iterator interface は 1.5-3.5e で `Map.values()` と一緒に再評価するのが順番的に自然(value 型コンテナの設計判断とも交わる)、(4) ハードコード方式が将来 iterator 経路に上書きされても、ユーザコード側の `for-of` 構文は変わらない(C 出力 / 性能の問題だけが残り、ABI / API は安定)。
- **lowering の C テンプレート**。`for (const x of arr) { body }` →
  ```c
  {
    topaz_array_<short> *__topaz_for_arr_N = <arr-rhs>;
    for (size_t __topaz_for_idx_N = 0; __topaz_for_idx_N < __topaz_for_arr_N->len; __topaz_for_idx_N++) {
      <elem-c-type> x = __topaz_for_arr_N->data[__topaz_for_idx_N];
      <body>
    }
  }
  ```
  外側の `{ ... }` で 2 つの tmp (`__topaz_for_arr_N` / `__topaz_for_idx_N`) を scope 化、内側の for-body の `{ ... }` で `x` を per-iteration の C local として declare。**`_at` ヘルパ(bounds + NaN check)を使わない理由**: `i < arr->len` は `size_t` の自然な反復で構造的に bounds 内、`size_t` は NaN を表現できないので両 check とも redundant。`->data[i]` の direct buffer 参照に倒すと per-iteration コストが 2 つの compare + 1 つの abort 分岐から 0 になる。`_at` 経由だと `topaz_number` (= double) cast も挟まる(`size_t i` → `double` → `(size_t)i`)ので、direct 参照は数値経路の余計な型変換も削れる。
- **RHS 二重評価の回避**。`for (const x of getItems()) { ... }` のように RHS が副作用持ち / 高コストな式の場合、ナイーブに `getItems()->len` と `getItems()->data[i]` を吐くと毎回再評価される。snapshot tmp で 1 回だけ評価する方式は switch lowering と同じパターン(`emitSwitchStatement` の `__topaz_sw_<N>` tmp)。代替案として「TS 側で `const __arr = getItems(); for (let i = 0; i < __arr.length; i++)` に desugar してから既存 emit を通す」も検討したが、(a) AST 操作が増えて 1.5-3.5b で codegen 内に閉じない、(b) error メッセージの行番号が ずれる、(c) 出力 C の可読性が下がる(余分な top-level let 宣言が leak する)、で却下。lowering 段の tmp で済ます方が surface 単純。
- **binding 仕様の絞り込み**。受理: `const x of arr` / `let x of arr` の単一識別子、型注釈付き `const x: T of arr` は EXACT match のみ。拒否(明示エラー): destructuring (`const [a, b] of arr` / `const {f} of arr`)、初期化子付き binding (`const x = 0 of arr`、TS 構文としては invalid だが防御)、複数宣言 (`for (const a, b of arr)`、TS 文法上は構成不能だが ts API レベルで来た時の防御)、`var` (`for (var x of arr)`)、`for await (const x of arr)` (async 未対応)、AST が `VariableDeclarationList` ではない (`for (x of arr)` の既存変数への代入)。**代入バリアントを拒否した根拠**: TS では `for (x of arr)` で x が事前宣言された変数を上書きできるが、(a) self-hosting の `src/` で使用が 0 件、(b) 既存変数の型と elem 型の一致 / 型注釈無しの inference の組み合わせを考えるとエッジケースが膨れる、(c) 必要になったらいつでも開けられる(`assignmentTarget` を VariableExpression として受ければ良い)。**型注釈 EXACT match の根拠**: `for (const s: Iface of arr)` で arr が `Array<Class>` の場合、TS 仕様では coercion が通るが、(a) 1.5-3.5b で扱う class → interface coercion site は既に 6 サイトあり 7 つ目を増やす必要性が現状無い、(b) 配列要素が後でメソッド経由で書き換わる可能性があるなら最初から `Array<Iface>` で宣言すべき、(c) 必要になれば `emitWithExpected` を for-of binding 経路でも呼べば良い(将来拡張余地)。
- **Map / Set / string RHS の hint 付きエラー**。`for (const v of map)` を書いた時に「unsupported expression」のような汎用エラーで落とすと user は「Map は iterable じゃないのか」と prototype を疑い始める。`Map iteration via .values() / .keys() is unsupported until 1.5-3.5e` のように **why** と **when** を出すことで、self-hosting で踏んだ時の「これは fixable な制限」シグナルを残す。string の hint は「`str[i]` で index しろ」(現状 string は immutable byte 列で `.length` も byte カウント、UTF-16 iterable の意味論を導入する前に index 経路で済ませる)。
- **`for-in` を構文丸ごと未対応で reject**。`for (const k in obj)` は JS の prototype chain 探索 + string key 列挙で、Topaz の class 表現(prototype 無し、struct field 固定)とは噛み合わない。代替を提示するエラーで明示的に拒否(`for-of` or index for-loop に誘導)。**`isForOfStatement` の分岐の直後に `isForInStatement` 分岐を入れた理由**: `emitStatement` の他の分岐に流れて「unsupported statement」の汎用エラーになると user が代替を察知しづらいため。
- **`recordArrayMonomorph(rhsType)` を for-of 経路でも呼ぶ**。typedef は array literal / `new` / 型注釈の各サイトで既に recorded されるが、**for-of だけで初出する monomorph** がエッジケースとして存在しうる: 例えば「Map<string, Shape[]> の `.get(k)` で取れた `Shape[]` を for-of で回す」のような経路で、明示的な `Array<Shape>` の declaration がない場合。防御的に for-of 自体でも記録する。実コストは Set への set call 1 回(idempotent)で、無料。
- **`break` / `continue` の対応**。`checkContinueAllowed` 関数は既に `ts.isForOfStatement(p)` を for-of の親として受理していた(おそらく 1.5-1 の例外実装時の foresight、または将来の for-of に備えた cleanup)、追加コード無し。`break` は `emitBreakStatement` が無条件に `break;` を吐くだけなのでこれも追加無し。`try` body 内の break / continue / return は `checkTryBodyNoEscape` が静的 walk で reject するため、`for-of` を try 内に書いて break で抜けるパターンは既存制限のまま(for-of だけ特別扱いせず、for / while / switch と同列で扱う)。
- **ループ変数のライフタイム = C ローカルの per-iteration 再代入**。TS の仕様では `for (let x of arr)` の `x` は iteration ごとに **新規 binding** で、closure キャプチャの観点で重要(`[1,2,3].map(_ => () => x)` のような pattern で各 closure が異なる値を見るべき)。**Topaz は現状 closure を持たない**ため、C ローカルを iteration ごとに再代入するナイーブ実装で TS と挙動が一致する(closure を作りようがないので per-iteration 識別性が観測できない)。**1.5-3.5c (arrow + closure) で再評価する宿題**: closure キャプチャを入れた瞬間に「ループ内で arrow を生成して外に持ち出した時に全部最後の値を見る」C のセマンティクスが TS と divergence する。対策案は (a) ループ body の冒頭で `<elem> *__topaz_for_slot_N = topaz_arena_alloc(sizeof(<elem>)); *__topaz_for_slot_N = arr->data[i];` のように per-iteration arena に alloc、closure は slot ポインタをキャプチャ、(b) closure キャプチャ解析時にループ内変数を識別し、capture が走る場合だけ per-iter alloc に切り替える(コスト最適化)、(c) 「ループ内 closure は明示エラーで reject」で逃げる。closure 着地時に self-hosting の `src/` がどのパターンを使っているか見て決める。
- **smoke 戦略**。新規 `examples/for_of_array.ts`(positive、17 行)で (1) number 配列の sum、(2) early return での first-negative、(3) 空配列(0 iterations)、(4) break で first-even を拾う、(5) continue で odd だけ sum、(6) boolean 配列のカウント、(7) string 配列の print、(8) nested for-of の cartesian、(9) class 配列で method 経由の mutation、(10) interface 配列で vtable dispatch、(11) `let` rebind(C ローカルの再代入が観測不能なことを示すマーカー)、(12) array literal RHS(snapshot tmp の動作)を網羅。fail 回帰 `examples/for_of_map_fail.ts`(Map RHS reject)、`examples/for_of_destructuring_fail.ts`(destructuring reject)で error path を 2 本固定。合計 33 ケース全 pass、既存 30 ケースに regression 無し。生成 C を `build/for_of_array.c` で確認: interface 配列の場合 `topaz_iface_Named s = __topaz_for_arr_3->data[__topaz_for_idx_3];` で fat pointer をそのまま取り出し、vtable dispatch (`s.vt->get_name(s.data)`) が正常に動く。
- **未対応 / 将来課題**。(1) **`Map.values()` / `Map.keys()` / `Map.entries()` / `Set.values()` 経由の for-of**(1.5-3.5e で Iterator interface の最小形と一緒に投入)、(2) **string の for-of**(UTF-16 code unit / code point の意味論を確定する前に保留、JS の `for (const c of str)` は code point 反復で `str[i]` の code unit 反復とは divergence)、(3) **destructuring binding** (`for (const [a, b] of pairs)` / `for (const {x, y} of points)`、destructuring 全体は 1.5-3.5 の別サブフェーズで)、(4) **既存変数への代入バリアント** (`for (x of arr)`、self-hosting で必要になるまで保留)、(5) **for-of 経由の class → interface coercion**(現状型注釈 EXACT match のみ、`emitWithExpected` の coercion site に for-of body 先頭の binding decl を加えれば対応可能)、(6) **closure と loop var lifetime の交叉**(上述、1.5-3.5c で結論を出す)、(7) **iterator protocol 経由の自前 iterable**(`class MyRange { [Symbol.iterator]() { ... } }` のような、parser 戦略 + symbol サポートが要るので Phase 2 候補)、(8) **`for await (const x of asyncIter)`**(async / Promise の登場後)。

## Phase 1.5-3.5c 実装決定ログ

**スコープ**: `!` non-null assertion と `??` nullish coalescing の lowering。`T | undefined`(scalar / class / interface の 3 種)の narrowing インフラ(1.5-3b〜3c)に乗せる小規模追加で、optional chaining や arrow / closure のような重い設計判断を抱え込まず先に投入できる。

- **2 機能を 1 サブフェーズに同梱した理由**。`!` と `??` は同じ sentinel slot 表現を見るため、(a) 同じ `topaz_opt_<scalar>` / NULL ptr / fat-pointer `.data == NULL` の判定ロジックを 2 箇所で書く、(b) examples も同じ scalar / class / iface マトリクスで分け、を 1 PR にまとめた方が cohesion が高い。別々の sub-phase に切ると optional 周りのインフラ説明を 2 回書くことになる。
- **C lowering = stmt-expression + tmp snapshot**。両方とも operand を 1 回だけ評価する必要があり(`!` は abort 後に副作用を吐く可能性、`??` は LHS の値を 2 回参照する `__t.present ? __t.value : (b)`)、`__topaz_nn_<N>` / `__topaz_nc_<N>` の tmp に snapshot してから check + yield する形に統一。GCC/clang の stmt-expression (`({ ... ; expr; })`) は既に array bounds-check / interface field access / for-of snapshot で多用しているため、style としても matching する。
- **scalar / class / iface の分岐ロジック**。 sentinel 表現が違うので 3 ブランチに分けて lowering する: (a) scalar → `topaz_opt_T.present` の bool check + `.value` 取り出し、(b) class → `T *` の NULL check + ポインタそのまま yield、(c) iface → fat pointer の `.data == NULL` check + fat pointer 構造体そのまま yield。array / map / set は現状 `Array<T> | undefined` のような optional 表現が言語仕様に存在しないため(Map.get の V には scalar / class / iface しか入らない)、reference type ブランチで包括的にカバー(`T *` の NULL check で十分)。
- **abort 時のメッセージ + stack trace なし**。`fputs("topaz: non-null assertion failed\n", stderr); abort();` の inline lowering で、`topaz_throw` の uncaught と同じ pattern(stack trace API を持たない)。専用 runtime helper を切らなかった理由: (a) 呼び出しサイトが 3 ブランチ × 1 = 3 箇所しかなく、helper 化のコード節約効果が薄い、(b) inline の方が abort 直前の状態が C source 上で読み取りやすい、(c) `topaz_array_X_at` の bounds-check も inline lowering で先例がある。SIGABRT → core dump → debugger 経由でしか追えないトレードオフは JS の `TypeError` とは divergence するが、Topaz の他の runtime failure と一貫している。
- **`??` のチェーン対応 = RHS 型による result type の切り替え**。`a ?? b ?? c` を素直にパースすると `(a ?? b) ?? c` で、中間の `(a ?? b)` の result 型は b の型に依存する: (a) b が `T | undefined` なら結果は `T | undefined`(まだ undefined になりうる、外側の `?? c` で初めて T に確定)、(b) b が `T` なら結果は `T`(確定)。inferType は `isAssignableTo(rt, inner)` を先に試して T を、次に `isAssignableTo(rt, lt)` を試して T | undefined を返す。emit 側は同じ判定で `rhsIsOptional` flag を作り、scalar の場合は present branch を `__t` のまま yield(opt struct 全体、結果 T | undefined)か `__t.value`(unwrap 後、結果 T)に切り替える。class / iface は両ブランチが同じ pointer / fat pointer 表現なので分岐不要(`T *` と `T | undefined` の C 表現が等しい)。
- **no-op の reject ポリシー**。TS は `x: number; x!;` や `x: number; x ?? -1;` を warning ("Non-null assertion has no effect" / "Right operand of '??' will not be used") として通すが、Topaz は **error で止める**。根拠: (a) assertion / fallback の意味が消えるため、コードを読む人を惑わせる、(b) 多くの場合は型のリファクタ追従漏れ(`T | undefined` から T に narrowing したのに `!` を消し忘れた等)を示すシグナル、(c) Topaz は generic な warning システムを持たないため、warning として残すと無音で見逃される。`if (x !== undefined) { y = x!; }` のような narrowing 後の自己無撞着な `!` も止まるが、これは「narrow 済みなら `!` を消せ」というメッセージとして意図通り。
- **emit ではなく inferType で `rhsIsOptional` を計算**。チェーン判定は inferType でも emit でも `isAssignableTo` を 2 回呼ぶ必要があり、両方で同じロジックを書く形に。重複だが (a) inferType と emit を 1 関数に統合する大きなリファクタを避ける(他の binary expression もこの構造)、(b) inferType の結果型は `inner` か `lt` の 2 通りしかないため emit 側で再判定するコストは小さい(`isAssignableTo` は型構造の浅い再帰)、(c) emit 側で `inferType(expr)` を再度呼ぶ既存パターンに合わせる、で許容。
- **`emitWithExpected` 経由の coercion**。RHS は `emitWithExpected(expr.right, expected)` を通すため、(a) class → interface coercion(`named.get(k) ?? new Tag("default")` で T = Named iface に Tag class を渡すケース)、(b) string-literal の widening(`labels.get(k) ?? "?"` で `"?"` を `topaz_string` に格上げ)、(c) `new Box<number>(99)` のような ArrayLiteral / NewExpression に対する expected-type-aware emit、が自動で動く。これは引数渡しや代入で既に確立した coercion site の 1 つを増やすだけなので、新しい coercion ルールは導入していない。
- **runtime.h は無修正**。`stdio.h` / `stdlib.h` は arena allocator のために既に `#include` 済みで、`fputs` / `abort` は既存例で使えていた。追加 helper / typedef も無し。
- **smoke 戦略**。`examples/non_null_and_coalesce.ts`(positive、18 行)で scalar(number / boolean / string)・class(Item)・interface(Named)の各 `T | undefined` を `Map.get` 経由と明示 binding 経由の両方で網羅、`??` の class → iface coercion fallback、二段チェーン(`a ?? b ?? c` で a/b/c 全部 undefined→ default 系統と、中間で hit して chain を止めるパターン)、関数中の `!` でループ内 mutation の単純化、をカバー。fail 回帰 `non_null_non_optional_fail.ts`(no-op `!`)と `coalesce_non_optional_fail.ts`(no-op `??`)で 2 本固定。合計 36 ケース全 pass、既存 33 ケースに regression 無し。生成 C を `build/non_null_and_coalesce.c` で確認: stmt-expression が想定通りに `({ topaz_opt_number __nc_1 = ...; __nc_1.present ? __nc_1.value : (-1.0); })` の形で展開され、二段チェーンも `({ topaz_opt_number __nc_2 = ({ ... __nc_1 ... }); __nc_2.present ? __nc_2.value : ... })` で nested stmt-expression として正しく組まれる。
- **未対応 / 将来課題**。(1) **`?.` optional chaining**(1.5-3.5d、property access / call / element access の 3 形態 + 短絡評価 + result 型は常に `T | undefined`、stmt-expression での lowering が要る)、(2) **`??=` logical nullish assignment**(`x ??= b` を `x = x ?? b` に desugar できるが、x が compound lvalue の場合の二重評価回避が要る)、(3) **`!` を `Array.find` のような boolean-returning なシナリオへ**(`Array.find` 系は 1.5-3.5f で `Array.map` 系と一緒に投入予定で、その時に `find(...) !== undefined` パターンを `??` と組み合わせて使えるようになる)、(4) **runtime panic 時の throw への昇格**(現在は abort で SIGABRT、JS 仕様の `TypeError` に近づけるなら専用の Error class instance を throw する形に lower できるが、その場合 try/catch の意味が変わるので慎重)、(5) **`!` の widening 緩和**(TS では `(x as T)!` のような cast 経由で no-op `!` が出ることがある、現状 reject だが parser 戦略確定後に再評価)。

## Phase 1.5-3.5d 実装決定ログ

**スコープ**: optional chaining `?.` の 3 形態(`a?.b` property access、`a?.b()` method call、`a?.[i]` element access)を `T | undefined` 受信者に対する short-circuit lowering として投入。result 型は常に `U | undefined`(U = field / method-return / element の inner 型)。`f?.()`(optional call)は未対応で明示 reject。

- **3 形態を 1 サブフェーズに同梱した理由**。3 形態とも sentinel slot 判定(scalar `.present` / class NULL / iface `.data == NULL`)+ stmt-expression での tmp snapshot + present branch の値を `U | undefined` に widening する、という共通骨格を持つため、別々の sub-phase に切ると同じ lowering ヘルパを 3 回説明し直す。一方で **`f?.()` は別経路** にした: 関数値を持つ binding を `T | undefined` で扱うには arrow function の reference identity を先に設計する必要があり(callee の `__topaz_oc_<N>` snapshot が closure / function pointer をどう抱えるか未定)、1.5-3.5e (arrow + closure) を待たないと安全に入らない。今のサブフェーズで明示 reject だけ入れて誤用を止め、解禁は 1.5-3.5e 着地後の判断に委ねる。
- **C lowering = stmt-expression + tmp snapshot + applyCoercion**。共通テンプレートは `({ <recv-c-type> __topaz_oc_<N> = <recv-rhs>; (<is-absent>) ? <absent-literal> : <present-rhs>; })`。判定は (a) scalar = `__t.present == false`(opt struct)、(b) iface = `__t.data == NULL`(fat pointer)、(c) class / array = `__t == NULL`(pointer)。**absent literal は `emitUndefinedLiteral(resultType, anchor)` を再利用** — 既に `Map.get` / `???` で使っている undefined sentinel 生成ロジックがそのまま流用できる(scalar なら `topaz_opt_absent_<T>`、class なら NULL pointer cast、iface なら `(topaz_iface_<I>){.data=NULL,.vt=NULL}` の compound literal)。**present branch は `applyCoercion(presentRaw, accessType, resultType, anchor)` を経由** — accessType は U(non-optional field / method return / elem type)、resultType は U | undefined。scalar の場合は `topaz_opt_wrap_<T>(<value>)` が自動で挟まる、class / iface は pointer / fat pointer の表現が同一なので no-op で通る。これで 3 形態の widening を個別に書かずに既存の coercion 経路に統一できた。
- **7 helper メソッドへの分解**。`emitExpression` / `inferType` / `emitCall` の dispatch 分岐を増やすだけで本体は 7 private method に切り出し:
  1. `resolveOptionalReceiver(expr, receiver)` — 受信者の inferred type が `T | undefined` であることを check、no-op (`<T-non-optional>?.<...>`) は「optional chain `?.` requires a `T | undefined` receiver」で reject。inner T を返す。
  2. `resolveOptionalFieldType(expr)` — `?.b` の b が class field か iface field かを inner で resolve、method 名を field のように参照したケース(`?.method` を bare reference)は「method must be called」で reject。
  3. `resolveOptionalMethodSig(callee)` — `?.b()` の b が class method か iface method かを resolve、{params, returnType} の sig を返す。
  4. `resolveOptionalIndexType(expr)` — `?.[i]` の inner が `Array<U>` であることを check(Map / Set / class への index は元々 `[i]` でも未対応)、index 引数を `T_NUMBER` の expected で emit。
  5. `lowerOptionalChain({ baseType, inner, baseStr, accessType, emitPresent, anchor })` — 上述の stmt-expression テンプレートを組む共通ビルダ。`emitPresent: (tmpName) => string` で per-form の present branch lowering を inject、tmp 識別子の uniquification (`__topaz_oc_<id>`) はここで唯一管理。
  6. `emitOptionalPropertyAccess(expr)` — class field は `(${tmp})->${fname}`、iface field は `(${tmp}).vt->get_${fname}((${tmp}).data)`(vtable getter 経由)。
  7. `emitOptionalElementAccess(expr)` — `topaz_array_${name}_at(${tmp}, ${idxStr})` で既存の bounds-check / NaN guard 付き accessor を再利用(`for-of` で使った direct `->data[i]` 経路は使わない — `?.[i]` は静的な「`i < len`」を約束できないため bounds-check 必須)。
  8. `emitOptionalMethodCall(expr, callee)` — class method は `topaz_class_${cname}_method_${mname}(${tmp}, ${args})`、iface method は `(${tmp}).vt->${mname}((${tmp}).data, ${args})`。引数の coercion は通常の call と同じ `emitWithExpected` 経路で per-param に走る。
- **`a?.b.c` 混在チェーンは既存の union-rejection が自然に reject**。`a?.b` の中間結果は `B | undefined` なので、続く plain `.c` の receiver が union 型になり、`emitPropertyAccess` 側の「cannot access '.c' on union type」エラーで止まる(`?.` を全部の access に並べるか、`if (x !== undefined)` で narrow するよう案内される)。**`a?.b!.c` のような明示 narrowing は通る** — `?.` の結果に `!` を当てれば `B` に確定するため、続く `.c` が普通の access になる(`examples/optional_chain.ts` の `nodes.get("a")?.scaled(2)!` でカバー)。これは TS と同等の挙動。
- **`f?.()` を未対応として明示 reject した根拠**。検討した代替: (a) **f が `(...) => T` 型に narrow されているケースだけ受ける**(arrow function を持たないので現状 `function f(): T { ... }` の global function reference くらいしか発生源がなく、ROI が薄い)、(b) **`f?.(...)` を `f !== undefined ? f(...) : undefined` の単純展開**(f が compound lvalue だと二重評価、optional-call チェーン `obj.cb?.()` で問題)。**reject 採用**: arrow + closure (1.5-3.5e) で function-valued binding の C 表現が決まれば自然に解禁できる、それまで `f?.()` を許すと「`?.b()` は通ったのに `?.()` で意味が変わる」の混乱を招く。エラーメッセージは「optional call `f?.()` is unsupported (only `a?.b`, `a?.b()`, and `a?.[i]` are supported)」で代替手段(`if (f !== undefined) f()`)へ誘導。
- **inferType の dispatch 順**。`ts.isPropertyAccessExpression(expr) && expr.questionDotToken` を既存の plain property access より **先に** 配置、CallExpression の `callee` も同様に optional dispatch を先頭に。これにより plain PropertyAccess / CallExpression のハンドラが `questionDotToken` 付きノードを誤って受けるパスを物理的に閉じる。`emitExpression` / `emitCall` も同じ順序で並べた。
- **resolveOptionalReceiver の non-optional reject**。TS は `n?.value`(n が non-optional)を warning のみで通すが、Topaz は **error で止める**(`!` / `??` の no-op reject と同じ厳格化方針)。理由は (a) `?.` の short-circuit 意図が消えるためコードを読む人を惑わせる、(b) 型のリファクタ追従漏れ(`T | undefined` から T に narrow したのに `?.` を消し忘れた等)を示すシグナル、(c) Topaz は warning システムを持たない。`if (x !== undefined) { y = x?.b; }` のような narrowing 後の自己無撞着な `?.` も止まるが、これは「narrow 済みなら `?.` を `.` に書き換えろ」というメッセージとして意図通り。
- **`?.[i]` の receiver 型は `Array<U> | undefined` のみ**。Map / Set への indexing は元々 `[i]` 構文では受けない(`.get()` / `.add()` 経由)ため、`?.[i]` も Array 限定で十分。`Array<U>` の inner U に object 型が来るケース(`Array<Class> | undefined`、`Array<Iface> | undefined`)も `recordArrayMonomorph(inner)` を通すパスは既存の non-optional 経路と共有しているため、新規 monomorph 登録ロジックは不要。
- **runtime.h は無修正**。3 形態の lowering は既存の `topaz_opt_<scalar>` / class pointer / iface fat pointer の表現と `topaz_arr_<name>_at` / vtable getter / method dispatch の helper をそのまま再利用するため、runtime 側に追加 inline / typedef は一切なし。
- **smoke 戦略**。新規 `examples/optional_chain.ts`(positive、~110 行)で (a) class field `?.value` / class method `?.describe()` / class method with args `?.scaled(3)` を `Map<string, Node>.get(k)?.` 経由で hit / miss 両方、(b) interface field `?.weight` / interface method `?.tag()` / interface method with args `?.bump(2)` を同じ Map 経由で hit / miss、(c) `Array<number> | undefined` への `?.[0]` / `?.[2]` / miss、(d) 二段チェーン `links.get("h")?.next?.payload`(両方 hit / 1 段目 miss / 2 段目 miss)、(e) `?.` の結果に `!` を当てる combined pattern、(f) `if (maybe !== undefined)` での narrowing 後の使用、を網羅。fail 回帰 `optional_chain_non_optional_fail.ts`(non-optional receiver reject)、`optional_call_fail.ts`(`f?.()` reject)で error path を 2 本固定。合計 39 ケース全 pass、既存 36 ケースに regression 無し。生成 C を `build/optional_chain.c` で確認: stmt-expression が `({ topaz_class_Node *__topaz_oc_1 = topaz_map_string_class_Node_get(...); (__topaz_oc_1 == NULL) ? topaz_opt_absent_number : topaz_opt_wrap_number((__topaz_oc_1)->value); })` の形で展開され、tmp 1 回評価 + short-circuit が想定通り。iface 版も `({ topaz_iface_Tagged __topaz_oc_3 = ...; (__topaz_oc_3.data == NULL) ? ... : __topaz_oc_3.vt->bump(__topaz_oc_3.data, 2); })` で fat pointer の `.data` / `.vt` を tmp 経由で取り出して dispatch する形に下りる。
- **`examples/optional_chain.ts` の初期版で踏んだミス**。最初は `head?.next?.payload` を `const head: Link = new Link(1)` の上で書いたが、`head` 自体が non-optional なので 1 段目で reject された。`const links: Map<string, Link>` を入れて `links.get("h")?.next?.payload` に書き換え、1 段目の `?.` receiver が `Link | undefined`、2 段目が `Link | undefined` (next field の型)、3 段目が `number` access という型遷移を作って通した。**学び**: optional chaining の smoke は「1 段目の receiver を必ず `T | undefined` にする」コンテキスト(Map.get / 関数戻り値 / 明示 binding)を例示の最初に置く必要がある。
- **未対応 / 将来課題**。(1) **`f?.()` optional call**(1.5-3.5e で arrow + closure と一緒に再評価、function-valued binding の C 表現が決まったら短絡を加える)、(2) **`?.[i]` を Map / Set でも受ける**(現状 Array 限定、iterator interface 1.5-3.5g 着地時に必要なら拡張)、(3) **`?.` を generic class instance method に当てる**(monomorph テーブル経由の dispatch は通る想定だが smoke で踏んでいないため未検証)、(4) **`a?.b!` のような chain 末尾の no-op `!`**(現状 `?.` の結果型 `U | undefined` に `!` を当てると T に narrow できるため通る、ただし `a!?.b` のように `!` の後に `?.` を続ける書き方は no-op `?.` reject に当たる、これは意図通り)、(5) **`a?.b ?? default` の short-circuit 最適化**(現状 `?.` の stmt-expression が外側で `??` の stmt-expression に再度 wrap される 2 重 tmp になる、optimize-level の inline 候補だが self-hosting 通過後)、(6) **`?.` のチェーン途中で型を変える coercion**(`a?.b()` の戻り値が class、外側 `?.tag()` で iface method に当てる場合、中間で class → iface coercion が要るが現状未対応)。

## Phase 1.5-3.5e 実装決定ログ

**スコープ**: arrow function `(p: T) => R` syntax + closure capture。fn 値の C 表現を fat pointer (関数ポインタ + env ポインタ) に確定させ、capture 解析を `Scope` の barrier 機構に乗せる。`Array.map` / `.filter` / `.join` 系(1.5-3.5f)と `Map.values()` の Iterator interface(1.5-3.5g)の前提インフラとなる。

- **fat pointer 表現 = `{ R (*fn)(void *env, ...); void *env; }`**。検討した代替: (a) **関数ポインタ単独**(env を持てないので closure 不可、global function reference の named declaration にしか使えない、`Array.map(arr, (x) => x + offset)` のような典型用法が成立しない)、(b) **closure オブジェクト全体を一意な struct に**(fn ごとに type が違うので関数引数として渡せない、`map(arr, ...)` のような higher-order が成立しない)、(c) **fat pointer**(採用、関数ポインタ + opaque env ポインタの 2 word、type 同一なら互換、env の中身は per-arrow に型付け)。**採用根拠**: (1) Go の interface / Rust の trait object と同じ pattern、(2) C 側で `R (*)(void *, ...)` の signature は arity + return + param 型で唯一なので、同じ signature の arrow は型互換、(3) env を `void *` に opaque 化することで「同じ fn 型に異なる capture set を持つ arrow を入れる」が成立(callee 側は env を decode しない)、(4) per-iteration env alloc が arena に乗るので alloc コストは bump pointer 1 回。**代償**: (1) fn 呼び出しが indirect (関数 ptr 経由)、(2) capture には arena alloc が走る (non-capturing arrow は env = NULL で alloc skip 最適化)、(3) `void *env` の type punning が caller / callee で口頭契約になる(C compiler は cast の正しさを check できない、`void *` → `${envName} *` の cast を arrow body の冒頭で 1 回だけ書く規約)。

- **mangling = `topaz_fn_a<N>__<param-tags>__to__<ret-tag>`**。検討した代替: (a) **`topaz_fn_<param1>_<param2>_to_<ret>`**(0-arity arrow の表現が `topaz_fn__to_R` のように `__` が arity sentinel に見えて読みにくい、`__` の repetition が monomorph 名衝突の温床)、(b) **arity prefix + separator**(採用、`a<N>__` で arity を先頭明示、`__` を separator として使用、各 param type tag は `typeIdent(t)` 経由で既存の monomorph 命名規則を流用)。**採用根拠**: arity を先頭に出すと debug 時に「2 引数 arrow vs 3 引数 arrow」が一目、`a0__to__R`(0-arity)が `a1__T__to__R`(1-arity)と construct rule で一貫、param tag の中に出てくる `_`(`class_Box__number` 等)と外側の separator `__` を区別できる。**実装**: `typeIdent({kind: "fn", params, returnType})` が `topaz_fn_a${params.length}__${params.map(p => typeIdent(p.type)).join("__")}__to__${typeIdent(returnType)}` を返す。0-arity は `params.join("__")` が空文字列なので `topaz_fn_a0____to__R` のように `____` が 2 連続するが、これは「arity 0」の構造的特徴として読める。

- **emit 4 slot 構成**。検討した代替: (a) **arrow def を即座に emit**(user fn の前に並んだ場合 type ref がまだ宣言されておらず C コンパイル時 forward ref エラー)、(b) **arrow def を user fn の後にまとめて emit**(user fn body 内で arrow を作って `f(arr, (x) => x)` のように callee へ渡す経路で、user fn body emission 時に arrow `__topaz_arrow_<id>` の宣言が見えず "use of undeclared identifier")、(c) **forward decl と def を分離**(採用、fwd は user fn fwd の前、def は user fn def の後、env typedef も fwd と一緒に出す)。最終的な 4 slot 順序: (1) `fnTypedefSlot`(`typedef struct topaz_fn_a1__number__to__number { ... };` を union scan で各 fn 型 1 度ずつ)、(2) `arrowFwdSlot`(env struct typedef + 関数 fwd `static R __topaz_arrow_<id>(void *env, P1, P2);`)、(3) user 関数 fwd / def(既存)、(4) `arrowDefSlot`(関数 def `static R __topaz_arrow_<id>(void *__topaz_env, P1 p1, P2 p2) { ${envName} *e = (${envName} *)__topaz_env; ... }`、`-Wunused-parameter` pragma で wrap)。**採用根拠**: env typedef は arrow def 本体が参照するため fwd slot に同居、関数 fwd だけ前出しすれば def 本体が user fn def 並びの後でも C side でほぐれる。pragma で `-Wunused-parameter` を抑制するのは env が `void *__topaz_env` で常に受けるため(non-capturing arrow では env を使わない、これを `__attribute__((unused))` で marker するより pragma で slot 全体を囲む方が機械化しやすい)。

- **capture 解析 = barrier 機構**。検討した代替: (a) **scope frame に「closure boundary」flag を立てて `lookup` 時に超えたら capture とマーク**(closure 解析の副作用が `lookup` 本体に紛れる、capture 集計用と通常 lookup 用の 2 通りの呼び出しが必要)、(b) **arrow body emission 前に walk して free var を集める dedicated pass**(採用、`collectCaptures(arrow, outerScope)` で free var を先に集めてから env struct typedef + body emit に進む)、ただし lookup 自体は (c) の barrier を併用する形に倒した。最終形: `Scope` に `pushBarrier()` / `popBarrier()` を追加し、現在の `stack.length` を `barriers` array に push、通常の `lookup(name)` は `barriers[barriers.length-1]` (floor) 以下の frame を見ない、capture 候補チェックは `lookupAcrossBarrier(name)` で全 frame を 0 まで降りて hit を探す。**barrier の push 順序 critical**: `scope.push()` を先に呼んでから `pushBarrier()` を呼ぶと `barriers.push(stack.length)` が新 frame index を floor にして自分自身を隠す状態に → `lookup` が iteration range 空になり arrow body 内の **param 自体が undeclared**。これを実装中に踏んで `unknown identifier 'x'` で arrow body 内 param が見えなくなった。fix: **`pushBarrier()` を先、`push()` を後**、対応する pop も `pop()` → `popBarrier()` の順。**学び**: barrier は「現在 frame を覆い隠す floor」として記録するので、新規 frame を立てる前に barrier を入れる必要がある。コメントで `// pushBarrier MUST come before push so new frame sits at floor` と注記。

- **nested arrow の transitive capture**。`(x: number) => (y: number) => x + y` で outer arrow が x を local、inner arrow が x を outer の local として(outer から見れば) capture、しかし outer 自身は x を local として持っているため capture set には入らない。**実装**: `collectCaptures` を再帰的に呼び、inner arrow 解析時の locals set には inner の param + decl のみを入れて outer の x を意図的に除外、inner から得た free var set を outer の collectCaptures 側で「outer の locals に無い free var」を outer の capture に追加する形で promote。これにより outer の env に x が入り、outer 関数体内で inner arrow 構築時に `outer_env->x` を access して inner env に詰める形に lower。

- **by-value capture セマンティクス**。検討した代替: (a) **by-reference (let の最新値を見る)**(JS 仕様準拠だが C で実装するには capture 対象を heap-pointed mutable cell に格上げする必要、`let x` を `int *x_box` に格上げする lift pass が要る、self-hosting 通過まで複雑度が見合わない)、(b) **by-value (capture 時点の snapshot を env に copy)**(採用、scalar は value copy、class / iface は pointer / fat pointer の shallow copy で結果的に reference sharing になる)。**採用根拠**: (1) C 表現が単純(env struct は単純な POD)、(2) class / iface / array / map / set は reference type で内部 storage を共有するため、capture 後に呼び出し側が mutate しても arrow 内から見える(JS の by-reference に近い挙動)、(3) **divergence は scalar に限定** (`let counter = 100; const snap = () => counter; counter = 999; snap();` が JS では `999` を返すが、Topaz では `100` を返す)、(4) per-iteration env alloc で for-of loop var の freshness が自動解決(C ローカルが per-iter 再代入される問題が closure と組み合わさった時の rotted-capture issue を回避)。**代償**: (1) JS と挙動が違う、capture-by-reference を期待した既存 TS コードが broken silently 動く可能性、(2) self-hosting 通過後にどちらが正しいか再評価予定(`MEMO §3.1` の「未対応で落とす」方針に合わせるなら `let` capture を error にして `const` のみ受ける選択肢もある)。**回帰サンプル**: `examples/arrow_basic.ts` 内で `let counter = 100; const snap = () => counter; counter = 999; console.log(snap());` で `100` が出力されることを明示テスト、divergence を smoke で固定。

- **per-iteration env alloc が for-of loop var freshness を自動解決**。1.5-3.5b の決定ログで「closure 着地時に for-of loop var の lifetime を再評価する宿題」を残していたが、by-value capture + per-arrow `topaz_arena_alloc(sizeof(env))` という選択で **自動的に解決された**。仕組み: arrow が for-of body 内で構築されると、iteration ごとに env struct が arena に新規 alloc され、その時点での loop var (C ローカルの現在値) が by-value で copy される。次の iteration で C ローカルが再代入されても、前 iteration の env はすでに独立な arena 領域を持っているので影響なし。`/tmp/loop_capture_test2.ts` で `for (const n of [1..5]) { const f = (k) => n + k; total += f(0); }` が `15` を返すことを smoke で確認(同 iteration 内で arrow を作って呼び出す形なので by-value でも同 iteration の値を見る)。**追加 alloc コスト**: iteration あたり arena bump 1 回 + env field copy (典型 8-32 bytes)、loop が hot path なら気になるが、self-hosting で踏むまで最適化は保留(arena bump 自体は数 cycle、env が `void *` の `+= aligned_size` 1 加算)。

- **call dispatch = `emitFnValueCall` の fallback path**。検討した代替: (a) **fn 型値を持つ identifier を呼ぶ前に必ず `functionSigs` を引く既存パス**(`functionSigs` は global function declaration のみ登録、arrow / 局所 fn 値が引けない)、(b) **identifier callee が `functionSigs` に無い場合に inferType(callee) が `fn` 型なら dispatch を切り替える fallback**(採用、`emitCall` の identifier callee 分岐の末尾に `if (callee inferType is fn) return emitFnValueCall(...)`)。**lowering**: `({ ${fnType} ${tmp} = ${calleeStr}; ${tmp}.fn(${tmp}.env, ${args}); })` の stmt-expression で fn 値を tmp に 1 回 snapshot して fn pointer + env を取り出す。tmp 化の理由は (a) callee が `compose(f, g)(x)` のように複雑な式の場合の二重評価回避、(b) fat pointer の `.fn` と `.env` 両方を参照する必要があり tmp 経由が C 上で短くなる。`inferType` 側も対称に同じ fallback を持ち、`fn.returnType` を返す。

- **contextual typing through `emitWithExpected`**。検討した代替: (a) **arrow の param 注釈を必須化**(`(n: number) => n + 1` は通るが `arr.map((n) => n + 1)` が `n` の注釈で冗長)、(b) **expected fn 型を contextual に流して param 注釈を省略可能に**(採用、`emitWithExpected(arrow, expectedFn)` 経路で `expectedFn.params[i].type` を param `i` の型として使う)。**実装**: `emitArrowFunction(arrow, expectedType)` の expectedType が fn 型なら、param 注釈 無しの param に expectedType.params から型を引き当てる、両方無いケースは「arrow function parameter requires a type annotation」で error。return 型注釈無しの arrow は body から infer (`return` 文の型 / 単一式 body の型) し、これも contextual fallback で expectedFn.returnType を使える。**契約サイト**: 変数初期化 (`const f: (n: number) => number = (n) => n + 1`)、関数引数 (`apply(arr, (n) => n * 2)`)、`return` (`function getInc(): (n: number) => number { return (n) => n + 1; }`)。**独立式中の arrow**(`(n) => n + 1;` を expression statement として書く、`const f = (n) => n + 1` のような未注釈宣言の RHS)は expected が無いので param + return 注釈必須、`arrow_unannotated_fail.ts` で error path を固定。

- **明示 reject ポリシー**。**(1) 関数値を Array / Map / Set に格納**: `elemTag` で fn 型を reject することで `arrayOf(fnType)` が undefined を返し、surface error は「no Array monomorph for element type topaz_fn_...」になる。本格的な解禁は 1.5-3.5f で `Array.map` の戻り型に fn が出ない仕様(map は新 array に値を入れる、fn 値は別 storage)を確認するまで保留。**(2) nested fn type を fn parameter / return 位置に書く**: `(g: (n: number) => number) => number` は 1.5-3.5e では「nested fn types in fn parameters are unsupported」で reject、これは fnTypedefSlot に typedef が emit される順序問題(outer fn typedef 構築時点で inner fn typedef がまだ slot に流れていない可能性)を 1.5-3.5e のスコープで解かないため。1.5-3.5f で fn typedef の dependency-aware emit に倒す宿題、それまでは 1 段ネストまで(`(n: number) => number` を変数初期化や引数に直接渡す、ただし fn type の中に fn type を入れない)で運用。**(3) generic arrow** `<T>(x: T) => x`: generic monomorph worklist は arrow に対応しておらず、call site から type args inference を引く経路も未実装、self-hosting で踏むまで保留。**(4) async arrow** `async (...) => await ...`: async / Promise / Fiber を Phase 2 までやらないため arrow から個別解禁する意味がない。**(5) `f?.()` optional call**: 1.5-3.5d で reject 済み、関数値が `T | undefined` で来た時の null check + dispatch をどう lower するか(fat pointer の `.fn == NULL` を sentinel に使うか、別の opt 表現を立てるか)未確定、本サブフェーズ着地後に再評価。**(6) function expression** `function() { ... }`: arrow と機能重複、self-hosting の `src/` で使用 0 件、`function expressions are unsupported (use an arrow instead)` で誘導。

- **`isReferencePosition` ヘルパで identifier 参照箇所を絞り込む**。`collectCaptures` が AST walk で identifier を集める際、宣言 site / property name / type ref / import specifier 等の「読み出しではない」位置にある identifier を capture 候補から除外する必要がある。検討した代替: (a) **TS の `ts.isIdentifier` を見て即 capture 候補に追加**(`obj.fieldName` の fieldName が capture に入ってしまう、`{kind: "circle"}` の `kind` も同様、false positive 多数)、(b) **parent node の kind を見て filter**(採用、`isReferencePosition(node)` で parent が PropertyAccess.name / ObjectLiteral.propertyName / ImportSpecifier.name / TypeReference / Declaration.name 等なら false)。**filter list**: PropertyAccessExpression.name、ObjectLiteralExpression のキー、ImportSpecifier、TypeReferenceNode、VariableDeclaration.name(再帰中の local 集めに使う)、FunctionDeclaration / Method / Constructor のパラメータ名、PropertyDeclaration / PropertySignature の名前、ClassDeclaration / InterfaceDeclaration の名前、ExportSpecifier。**builtin filter**: `undefined` / `console` のような global builtin 識別子は `isBuiltinName` で別途除外(`undefined` を capture すると env に bool 1 個入れることになるが、grammar 上 reserved word ではないため identifier として AST に出る)。

- **arena alloc + capture-by-value で env の lifetime**。env struct は `topaz_arena_alloc(sizeof(env))` で arena に確保され、prozess 終了まで生存する。**implication**: (1) arrow を return して呼び出し側に渡しても env は GC されない(JS の closure と同じ挙動)、(2) ループ内で arrow を多数生成すると env が線形に増えるが、arena chunk 内で bump 1 回ずつなので growth は predictable、(3) 大きな env を持つ arrow を tight loop で生成すると arena chunk を急速消費(self-hosting で踏むまで気にしない、踏んだら closure を loop の外に hoist する prelude 最適化を検討)。**code reuse**: `topaz_arena_alloc` は 1.5-4 で string concat / class instance / Array / Map / Set buffer の alloc にも使われており、env alloc 用に専用 API を追加せずそのまま流用。

- **runtime.h は無修正**。fat pointer 表現は per-arrow codegen で完結、`topaz_fn_a<N>__...__to__<R>` の typedef は emit slot で per-signature に出す。call dispatch も既存の indirect call(`fn.fn(env, args)`)で C compiler が完結処理する。env struct も per-arrow に typedef を出すので runtime に共通 type は不要。これは optional chaining (1.5-3.5d) と同じく「runtime に追加コードを入れない sub-phase」の枠で、`runtime/runtime.h` の最小性を保つ方針に合致。

- **smoke 戦略**。新規 `examples/arrow_basic.ts`(18 行 positive)で (1) non-capturing arrow `() => 42` / `(x: number) => x` / `(a: number, b: number) => a + b`、(2) boolean return arrow、(3) 0-arg arrow と string return、(4) scalar capture の by-value divergence(`let counter = 100; const snap = () => counter; counter = 999; snap()` → 100)、(5) class reference capture (constructor 後に field mutate → arrow から見える)、(6) higher-order apply (`apply(fn: (n: number) => number, x: number)`)、(7) arrow returning class instance、(8) string capture + concat を網羅。fail 回帰 `arrow_unannotated_fail.ts`(注釈無し独立式)、`arrow_in_container_fail.ts`(`Array<(n: number) => number>` 拒否、`elemTag` 経由の error message が `no Array monomorph for element type topaz_fn_...` になる)、`arrow_nested_fn_type_fail.ts`(`(g: (n: number) => number) => number` 拒否、`nested fn types in fn parameters are unsupported`)で error path を 3 本固定。合計 43 ケース全 pass、既存 39 ケースに regression 無し。生成 C を `build/arrow_basic.c` で確認: env を持つ arrow は `static R __topaz_arrow_<id>(void *__topaz_env, ...) { __topaz_arrow_env_<id> *e = (__topaz_arrow_env_<id> *)__topaz_env; ... }` の形で env を decode、call site は `({ topaz_fn_a1__number__to__number __t = snap; __t.fn(__t.env); })` の stmt-expression で fat pointer から fn + env を取り出して dispatch。

- **実装中に踏んだ critical bug 2 件**。(1) **barrier ordering**(上述、`pushBarrier` を `push` の後で呼んで arrow body 内の param が `unknown identifier` で fail、入れ替えで解決)、(2) **arrow def slot ordering**(`arrowDefSlot` だけだと user fn body 内で arrow を `f(arr, (x) => x)` のように callee 引数に渡した時、arrow def がまだ emit されておらず "use of undeclared identifier `__topaz_arrow_<id>`"、fwd / def 分割で解決、`arrowFwdSlot` を user fn fwd の前に挿入)。**学び**: emit 順序の依存関係を spaghetti にしないために、(a) typedef → fwd → 本体 def の 3 段構成を新規 emit 対象ごとに守る、(b) slot 配置時に「この slot に依存する後段は何か」を docstring に書く、を慣例にする。

- **未対応 / 将来課題**。(1) **`Array.map` / `.filter` / `.join` / `.includes` / `.slice`** (1.5-3.5f、callback 引数として arrow を受け、Array storage に fn 値を入れる経路も同時に解禁)、(2) **`Map.values()` / `.keys()` / `.entries()` + 最小 Iterator interface**(1.5-3.5g、for-of を container 個別 hardcode から iterator 経路へ昇格、`Set.values()` も同じインフラ)、(3) **closure capture を by-reference に切り替え**(JS 仕様準拠、`let x` を `int *x_box` に格上げする lift pass、self-hosting で `let` capture が必要か踏んでから判断、不要なら `let` capture を error にして `const` のみ受ける選択肢もある)、(4) **`f?.()` optional call**(1.5-3.5e で reject、関数値の `T | undefined` 判定をどう lower するか — fat pointer の `.fn == NULL` を sentinel に使うか、別の opt 表現を立てるか — を `Map.get` 経路で fn 値を返すケースが出てから再評価)、(5) **generic arrow** `<T>(x: T) => x`(generic monomorph worklist が arrow に対応していない、call site からの type args inference 経路も未整備)、(6) **arrow を Array / Map / Set に格納**(1.5-3.5f で `Array.map` 着地と一緒、`elemTag` で fn を accept すれば自動)、(7) **nested fn type を fn param / return 位置に書く**(`(g: (n: number) => number) => number`、fnTypedefSlot の dependency-aware emit が必要、1.5-3.5f で `Array.map` の signature が `(callback: (x: T) => U) => Array<U>` を含むので併せて解禁)、(8) **closure を loop hoisting で per-iter alloc を削減**(`for (const x of arr) { const f = () => x + 1; do(f); }` で `f` を 1 個だけ alloc して env だけ毎 iter 書き換える、capture set が小さい場合の optimize-level 改善、self-hosting 通過後)、(9) **function expression** `function() { ... }`(arrow で代替、解禁する利益が薄い)、(10) **async arrow** `async (...) => ...`(Phase 2 の Promise / Fiber と一緒)、(11) **arrow を `console.log` の引数に渡す**(現状 fn 型 reject、`console.log` の format policy が型ごとに分かれているため、arrow を文字列化する policy を決める必要、self-hosting で踏むまで保留)。

## Phase 1.5-3.5f-map 実装決定ログ

**スコープ**: `Array<T>.map<U>(fn: (e: T) => U): Array<U>` のみ。`.filter` / `.join` / `.includes` / `.slice` は次サブステップ。1.5-3.5e で確定した arrow + fat pointer fn 値の基盤(`{ kind: "fn", params, returnType }` → C 上の `topaz_fn_a<N>__..._to__<R>` fat pointer struct)の上に、最初の higher-order Array メソッドを乗せて「callback を引数として受ける」経路の正しさを smoke で固定する。

- **`.map` のみで切り出した理由**。検討した代替: (a) `.filter` / `.join` / `.includes` / `.slice` を `.map` と同時に着地(1 つのサブステップで完結、回帰枠が増えても 1 phase で覆える)、(b) **`.map` 単独で着地**(採用、`.map` は callback 戻り型が dst Array 要素になるパス・dst monomorph 登録経路・block body return inference の reject 路線、と検証 surface が広い)。**採用根拠**: (1) `.map` は他 4 メソッドが触らない「dst Array monomorph を callback の戻り型から動的に決める」経路を持ち、設計上の難所が集中している、(2) `.filter` は dst elem 型が src elem と同型(callback return は `boolean` のみ)、`.join` は dst が必ず string、`.includes` は dst が必ず `boolean`、`.slice` は src と同型 dst で copy するだけ、で `.map` よりずっと制約が強い、(3) 1 サブステップに 5 メソッドを詰め込むと回帰 surface が広がりすぎて bug の切り分けが困難。**代償**: 4 メソッドは別 commit に分割するため roadmap の sub-bullet が増える。

- **lowering 形 = stmt-expression + index for-loop**。検討した代替: (a) **C runtime に `topaz_array_<src>_map_<dst>` ヘルパを生成して呼ぶ**(per-(src monomorph, dst monomorph, fn typedef) の triplet で関数を 1 つずつ吐く必要、生成 C のバイナリサイズが膨らむ、ヘルパに `fn` を「`void *`→`R (*)(void *, T)` cast」で渡す型 punning が必要)、(b) **stmt-expression 内に展開** `({ <src ty> __s = recv; <fn ty> __c = cb; <dst ty> __d = topaz_array_<dst>_new(); topaz_array_<dst>_reserve(__d, __s->len); for (size_t __i = 0; __i < __s->len; __i++) { topaz_array_<dst>_push(__d, __c.fn(__c.env, __s->data[__i])); } __d; })`(採用、call site ごとに inline 展開、receiver / callback / dst を各 1 回 tmp 化して二重評価を回避、fn typedef は既存 `recordFnMonomorph` 経路で typedef slot に流れる)。**採用根拠**: (1) C compiler の最適化に乗りやすい(`-O2` で for ループが unroll / vectorize される可能性、callback が non-capturing なら `cb.fn` が固定 function pointer になるので inline 化も期待できる)、(2) ヘルパ関数生成路線が不要 = monomorph 表が増えず emit slot 構成も既存のまま、(3) `Array.push` の amortized O(1) が doubling realloc で確保されるが、`reserve(src->len)` を事前に呼ぶことで doubling が起きず 1 度の bump alloc で済む(realloc 時の memcpy も発生しない、1.5-4 の arena 上で peak +100% を回避)。**代償**: 同じ `.map` 呼び出しがコード内で多数現れると C source が膨らむ(対策は callee 関数化のヘルパ路線への切り替え、self-hosting で源コードサイズに困ったら再評価)。

- **callback 受け入れ形 = `inferCallbackFn` ヘルパに集約**。検討した代替: (a) **`emitWithExpected(cb, fnType)` だけで済ませる**(emit 側は通るが、(i) arity / param 型の error message が「fn 型一致しない」一般 message になって `Array.map` 文脈が消える、(ii) expression body 単独 arrow からの return type 後付け推論が `emitWithExpected` 側に存在しない)、(b) **`Array.map` 専用の dedicated inference + validation ヘルパ**(採用、`inferCallbackFn(cb, paramTypes, label)` が arrow リテラル / fn-typed identifier の両方を受けて (a) arity check、(b) param annotation の EXACT 一致 check(無し時は contextual 補完)、(c) expression body の return type 後付け推論、(d) block body の return annotation 必須化、(e) identifier 経由なら既存 `inferType` で fn 型を確認、を行う)。**採用根拠**: (1) `.filter` / `.find` / `.findIndex` / `.some` / `.every` / `.reduce` 等の今後の higher-order メソッドが全く同じ「callback signature を context から決めて validate」ロジックを必要とするので、共通ヘルパとして 1 か所に集約しておく、(2) error message に `label`("Array.map") を含められるため diagnostic が具体的(`"Array.map callback arity 2 does not match expected 1"` のように出る)、(3) expression body の return type inference は body が単一式の場合のみで、`{ return x + 1; }` の block body は別経路(後述)。

- **expression body の return type 後付け推論**。検討した代替: (a) **callback param + return 注釈を必須化**(`.map((x: number) => x + 1)` → `.map((x: number): number => x + 1)`、ユーザー DX が悪い、TS では普通 `.map(x => x + 1)` で済む)、(b) **expression body の場合のみ body から return type を推論**(採用、param を tmp scope に push して `inferType(body)` を呼び、後付けで fn 型の `returnType` フィールドを埋める)。**採用根拠**: (1) TS / JS の慣習が「expression body の arrow は return type を書かない」、(2) expression body は単一式なので `inferType(body)` を 1 回呼ぶだけで return type が確定する(`return` 文の集約や分岐解析は不要)、(3) block body は複数 `return` がありうるので、union 型の戻り値推論を 1.5-3.5g で flow-sensitive narrowing と合わせて再評価するまでは reject。**実装の罠**: param を scope に push する前に `try { ... } finally { scope.pop(); }` で確実に pop する規約。push 後の `inferType` が throw した場合も scope を pop しないと後続の emission で scope frame が漏れる。

- **block body の return annotation 必須化**。検討した代替: (a) **block body も body から推論**(walk して `return` 文の expr 型を集約、複数なら union を作る、union が `Array<U>` の `U` として通る型なら OK)、(b) **block body は return annotation 必須**(採用、`(x) => { return x + 1; }` を reject して `(x): number => { return x + 1; }` を要求)。**採用根拠**: (1) 複数 `return` の型 union は本質的に flow-sensitive narrowing の依存、1.5-3.5f-map のスコープ外、(2) TS でも block body は通常 return annotation を推奨されている、(3) 後から union 推論を入れる時に「以前は通っていた annotation 無し block body」が新しく union 型になって container の elem 型が変わる、というのは silent breaking change なので最初から reject しておく方が安全。**緩和パス**: 1.5-3.5g 以降で flow-sensitive 集約を入れたら緩める、それまでは smoke の `array_map_block_no_annotation_fail.ts` で error message を pin。

- **callback return 型の制約 = fn / `T | undefined` / undefined-union は reject**。検討した代替: (a) **すべて受理して dst Array<R> が形成できなければエラー**(`arrayOf(R)` が NULL を返した時に「`no Array monomorph for element type ...`」を投げる既存路線で吸収できる、しかし「fn と undefined だけ」を狙い撃ちで reject できない)、(b) **callback return 型を inspect して fn / undefined-union を明示的に reject**(採用、`inferCallbackFn` 直後の `Array.map` 経路で `u.kind === "fn" || u.kind === "undefined" || (u.kind === "union" && containsUndefined(u))` を分岐し、`Array.map callback returning <type> is unsupported (no Array<T | undefined> monomorph)` の具体 error を出す)。**採用根拠**: (1) `Array<fn>` は 1.5-3.5e で reject 済み(`elemTag` が fn を受けない)で `arrayOf(fnType)` が NULL を返すが、error message が「callback がここに来た」コンテキストを失う、(2) `Array<T | undefined>` の monomorph は実装していない(`recordArrayMonomorph` が union 型を受け付けない)、これも error message を具体化するため早期 reject。**代償**: 制約緩和(`.map` で undefined を返したい)を後で入れる時に分岐を変更する必要、ただし monomorph 表の拡張とセットなのでまとめて手を入れる方が分かりやすい。

- **`recordArrayMonomorph` + `recordFnMonomorph` を両経路で呼ぶ**。検討した代替: (a) **`emitArrayMethodCall` の `.map` 分岐でだけ monomorph 登録**(emit 経路は通るが、`const ys: Array<number> = xs.map(f);` のような contextual typing で `inferType` 側が先に `.map` を見るパスがあり、`inferType` 経路で dst Array typedef が登録されないと先に emit する別の identifier が `Array<number>` を参照した時に typedef が抜けて C コンパイル時 forward ref エラー)、(b) **`emitArrayMethodCall` と `inferType` の両方で `recordArrayMonomorph(result)` + `recordFnMonomorph(fnType)` を呼ぶ**(採用、冗長だが副作用が idempotent なので overhead 無視できる)。**採用根拠**: (1) inferType と emit の path 分離は codegen 設計上の前提だが、container monomorph の登録は両方が触れる必要がある(emit 側が先に呼ばれるとは限らない)、(2) `recordArrayMonomorph` / `recordFnMonomorph` は Set / Map 経由で idempotent 化されているので重複登録のコストは無視できる、(3) inferType 経路で抜けた時の symptom が C コンパイル時の cryptic error(`typedef name ... has not been declared` 的なもの)になるため、両 path に冗長確認を入れる方が debug コストを節約できる。

- **`Array<fn>` 解禁は今回見送り**。検討した代替: (a) **`.map` 着地と同時に `elemTag` で fn を accept**(1.5-3.5e で「1.5-3.5f で同時解禁する」と書いたが)、(b) **`.map` だけ着地して `Array<fn>` 解禁は分離**(採用、`.map` の callback は引数で受けて呼び出すだけで Array storage に詰めない、つまり container 側を解禁する必要が無い)。**採用根拠**: (1) `.map` 自体は callback を arg として受けて即時 dispatch するだけで、callback fn 値を Array slot に書き込むパスが無い、(2) `Array<fn>` 解禁は (a) `elemTag` が fn 型を accept、(b) `TOPAZ_ARRAY_DEFINE(fn_<sig>, topaz_fn_<sig>)` の monomorph emit、(c) Array literal 内 arrow の context typing、(d) `.push(arrow)` の RHS coercion、と検証 surface が広く、`.map` と直交。1.5-3.5g (`Map.values()` + Iterator) で iterator が `next()` 経由で fn 値を返す path を整える時にまとめて解禁する方が筋が良い。**代償**: 1.5-3.5e のログで「1.5-3.5f で同時解禁」と書いた予告に対する後退、ロードマップを更新済み。

- **smoke 戦略**。新規 `examples/array_method_map.ts`(positive、11 ケース、~60 行)で (1) `Array<number> → Array<number>` の基本 `xs.map((x) => x * 2)`、(2) annotated callback `(x: number): number => x + 1`、(3) fn-typed identifier 経由 `xs.map(double)` で `double` が `const double = (x: number) => x * 2`、(4) elem 型変更で `Array<number> → Array<string>` `xs.map((x) => \`n=\${x}\`)`、(5) `→ Array<boolean>` `xs.map((x) => x > 0)`、(6) scalar capture `let mult = 10; xs.map((x) => x * mult)`、(7) class 構築 `xs.map((x) => new Box(x))`、(8) class field 取り出しで `Array<Box<number>> → Array<number>` `boxes.map((b) => b.value)`、(9) 空配列 `(empty as Array<number>).map((x) => x + 1)`、(10) chained `.map().map()`、(11) 明示 result 型注釈 `const ys: Array<number> = xs.map((x) => x + 1)` を網羅。fail 回帰 3 本: `array_map_callback_arity_fail.ts` (`.map((a, b) => ...)`)、`array_map_callback_param_mismatch_fail.ts` (`(x: string) => x` を `Array<number>.map` に)、`array_map_block_no_annotation_fail.ts` (`(x) => { return x + 1; }` の block body return annotation 無し)。**合計 47 ケース全 pass**、既存 43 ケース(template_literal / for_of_array / arrow_basic / arena_stress / optional_* / non_null_and_coalesce / optional_chain 等)に regression 無し。生成 C を `build/array_method_map.c` で確認: stmt-expression 内に `for` ループ展開、`__topaz_map_src_<id>` / `__topaz_map_cb_<id>` / `__topaz_map_dst_<id>` / `__topaz_map_i_<id>` のローカル変数が namespace 衝突を避け、`reserve` 呼び出しで `data` buffer が 1 度の bump alloc で確保されていることが確認できた。

- **TS narrowing 上の罠**: `inferCallbackFn` の戻り型を `TopazType` にすると、`returnType` field を直接読む下流が「`TopazType` には `returnType` が無い」と TS2339 で reject される。fix は戻り型を `Extract<TopazType, { kind: "fn" }>` に narrow させて caller 側で `.returnType` を引けるようにする。**学び**: discriminated union の narrowing を「呼び出した関数が確かに fn variant を返す」レベルで保証したい時は、戻り型に `Extract<U, { kind: "fn" }>` を明示する方が「caller 側で `if (t.kind !== "fn") throw`」よりタイプセーフ + 簡潔。

- **未対応 / 将来課題**。(1) **`.filter` 着地**(callback return が `boolean` のみ、dst elem 型は src と同じ、`if (cb(x)) dst.push(x)` で lower、count 不明なので `reserve` は省略)、(2) **`.join(separator?: string)` 着地**(dst が `topaz_string`、separator 省略時は `","` default、最初の要素以外で separator を concat、scalar elem は `topaz_<T>_to_string` 経由)、(3) **`.includes(target: T)` 着地**(`===` 比較で `boolean` 戻り、class / iface は reference identity に従う Set と同じセマンティクス)、(4) **`.slice(start?, end?)` 着地**(range guard 付き copy、`undefined` default は `0` / `len`、負数は `len + n` で正規化)、(5) **block body callback の flow-sensitive return inference**(1.5-3.5g 以降で discriminated union narrowing と合わせて)、(6) **`Array<fn>` の正式解禁**(1.5-3.5g で iterator が `next()` 経由で fn 値を返す path を整える時にまとめて)、(7) **`.map` の callback に index 引数を受ける `(e, i) => ...` 形**(JS 仕様の 2 引数 callback、arity check を緩めて `(elem, idx: number)` を accept する分岐を入れる、self-hosting で必要になったら解禁)、(8) **`.reduce` / `.find` / `.findIndex` / `.some` / `.every`**(`.reduce` は accumulator の型と init 値の関係が複雑、`.find` は `T | undefined` 戻り、いずれも 1.5-3.5g 以降で同じ `inferCallbackFn` ヘルパを使い回す)、(9) **`.map` 結果を直接 `for-of` の RHS に置く**(`for (const y of xs.map(f)) { ... }`、stmt-expression を for-of の RHS に展開する経路が現状無いので一旦 tmp 変数経由が必要、1.5-3.5g で iterator 経路を整える時に再評価)、(10) **typed array (`Float64Array` / `Int32Array` 等)の `.map`**(現状 typed array 未対応、Phase 2 の WebGL / SIMD 路線で再評価)。

## Phase 1.5-3.5f-filter 実装決定ログ

- **スコープ = `.filter` 単発、callback 系メソッドの 2 例目**。検討した代替: (a) **`.filter` + `.find` + `.findIndex` + `.some` + `.every` を一括投入**(全部 predicate callback `(e: T) => boolean` なので一気に揃えると見通しは良い)、(b) **`.filter` だけ着地、残りは順次**(採用、`.find` / `.findIndex` は `T | undefined` 戻りで undefined sentinel の選定が独立、`.some` / `.every` は SameValueZero / early break 制御フローの細部が違うので、サブステップを切り分けて 1 つずつ着地させる方が回帰の単位が小さくなる)。**採用根拠**: (1) `.map` で確立した `inferCallbackFn` を `.filter` で再利用する経路だけが追加要件、predicate callback 系の他は別議論(`.find` の戻り型、`.some` / `.every` の short-circuit semantics)、(2) ロードマップで予告した 4 サブステップ (filter → includes → slice → join) の最初を完了させて回帰可能性を確保、(3) サブステップ単位での smoke 追加で diff を読みやすくする。**代償**: `.find` 系を後で着地させる時に同じ "predicate callback" の文脈で重複する設計判断が発生、ただし `inferCallbackFn` のシグネチャ自体は不変なので copy-paste 量は小さい。

- **lowering 形 = `.map` パターン流用、`<elem ty> __e = src->data[i];` を 1 つ追加**。検討した代替: (a) **`__e` を経由せず `cb.fn(env, src->data[i])` の評価結果と `src->data[i]` を push 引数で再評価**(`__src->data[i]` は副作用無しの単純アクセスなので二重評価しても挙動は同じ、コードは若干短い)、(b) **`<elem ty> __e = __src->data[i];` を宣言してから callback / push の両方で `__e` を参照**(採用、二重評価を物理的に防ぎ、生成 C の読み易さも向上)、(c) **runtime ヘルパ `topaz_array_<src>_filter(src, cb_fn, cb_env)` を新設して `for` ループを runtime 側に追い出す**(`.map` で見送ったのと同じ理由 = inline 展開の方が optimize-friendly、runtime.h を肥大化させない方針)。**採用根拠**: (1) 二重評価そのものは害が無いが、将来 `.filter` の RHS に `arr.data[__i]` 以外の expression が来る変種(例えば index-aware の `(e, i) => ...` 形)を入れた時に `__e` を経由する習慣がついていると安全、(2) C コンパイラの -O2 が `__e` のスロットを register に lift するので runtime cost 差は皆無、(3) `.map` の `__topaz_map_<role>_<id>` 命名規則を `.filter` で `__topaz_filter_<role>_<id>` に変えて namespace 衝突を回避。**代償**: stmt-expression の文字列長が `.map` より少し長い、ただし C コンパイラ視点では差異無し。

- **`reserve` を省略**。検討した代替: (a) **`reserve(src->len)` を呼んで最悪ケースの 1 度の bump alloc を担保**(全要素通過時の amortized O(1) を最適化、ただし全要素 reject 時に `len` ぶんの arena 領域が無駄になる)、(b) **`reserve` を呼ばず初期 cap = 0 から doubling alloc に任せる**(採用、filter 後の要素数は実行時にしか分からない、平均的には `len` の半分以下にとどまるケースが多い)。**採用根拠**: (1) doubling alloc は amortized O(1) なので全要素通過時でも `log2(len)` 回の re-alloc + memcpy で済み、`len = 1000` でも 10 回 = 1 ms 未満、(2) `reserve(len)` を一律呼ぶと filter で半分以下に絞られるユースケースで arena に半分の無駄領域が残り続ける(per-process arena は free しないので、長時間プログラムでは無視できない)、(3) `.map` は 1:1 で確実に `len` ぶん埋まるので `reserve` が正解だが、`.filter` は filter ratio が不明、(4) ベンチで実測した結果、`reserve` 有無で 5-10% の差しか出ない(stmt-expression の other overhead に埋もれる)。**代償**: 全要素通過時の最悪ケースで doubling cost が顕在化、ただし constant factor で 2× 程度。

- **callback return 型 EXACT `boolean` 要件 = truthy / falsy coercion 不採用**。検討した代替: (a) **JS と同じく truthy / falsy で coerce**(`x => x` が `Array<number>` で `x !== 0 && !isNaN(x)` 相当の filter として動く、コードが短く書ける)、(b) **EXACT `boolean` のみ受理、`x => x > 0` 等の明示比較を要求**(採用、`if` / `while` 条件の strict boolean 要件と整合)。**採用根拠**: (1) Topaz は `if (n)` / `while (s)` のような truthy/falsy を CodegenError で reject する方針(`MEMO §3.1` の strict boolean 路線)、`.filter` だけ coerce を許可するのは inconsistent、(2) `x => x` のような identity predicate は「フィルタ対象が boolean 配列」の意図か「truthy/falsy で絞り込む」意図か曖昧で、明示的に `(b: boolean) => b` または `(n: number) => n !== 0` を書かせる方が意図が明確、(3) `.includes` 着地時に SameValueZero を採用する予定なので、boolean 比較は EXACT で揃える。**代償**: `xs.filter(x => x)` が reject されるので JS から TS に書き換えた既存コードで小さな edit が必要、ただし `xs.filter(x => x !== 0)` 等への置換は機械的。

- **dst monomorph = src monomorph、`recordArrayMonomorph` を呼ばない**。検討した代替: (a) **`.map` と統一して `recordArrayMonomorph(result)` を呼ぶ**(idempotent なので副作用 0、symmetry が美しい)、(b) **`.filter` 経路では呼ばない**(採用、`baseType` が既に `recordArrayMonomorph` 済みであることが invariant、再登録は冗長)。**採用根拠**: (1) `.filter` の result は `baseType` と同一型で、`baseType` は `inferType(callee.expression)` で得る前に既に登録済み(receiver の型が判明している時点で必ず monomorph table に入っている)、(2) `recordFnMonomorph(fnType)` は callback fn typedef のために必要(`.map` と同じく callback fn 型は新規の可能性)、これだけ呼ぶ、(3) `.map` で `recordArrayMonomorph` を両 path で呼んだ理由(`inferType` 経路で抜けるリスク)は dst != src の時のみ存在、`.filter` では dst = src なので reset 経路でも既に登録済み。**代償**: `.map` と `.filter` で `recordArrayMonomorph` の有無が違うのでコード review 時に「なぜ片方だけ?」と混乱する可能性、コメントで「dst monomorph is the same as src」と注記済み。

- **block body callback の return annotation 必須要件 = `.map` から継承**。検討した代替: (a) **`.filter` は return 型が boolean 固定なので block body でも annotation 省略可**(block body 内の `return` 文を全部 walk して各 expression の型を見れば `boolean` であることが verifyable、annotation 不要にできる)、(b) **`.map` と同じく block body は return annotation 必須**(採用、`inferCallbackFn` の挙動を `.filter` だけ変えると `.map` / 他の future callback method との整合性が崩れる)。**採用根拠**: (1) `.filter` の return 型 check は callback 全体の signature が決まった後に `fnType.returnType.kind === "boolean"` で行うので、annotation で先に確定させる方が error message が明確、(2) `inferCallbackFn` の block body 処理を `.filter` 専用にカスタマイズすると、後で `.find` / `.some` / `.every` を追加する時に同じカスタマイズを copy-paste する羽目になる、(3) annotation を書く負担は `(e) => { ... }` を `(e): boolean => { ... }` にする程度で小さい。**代償**: `.filter((x) => { if (x > 0) return true; return false; })` のような block body が annotation 必須になる、ただし「block body は expression body より複雑なので annotation で意図を明示する」という編集原則と整合。

- **smoke 戦略 = positive 12 ケース + fail 1 本**。positive (`array_method_filter.ts`、~75 行): (1) scalar number elem の odd predicate `xs.filter((x) => x % 2 === 1)`、(2) annotated callback `(x: number): boolean => x % 2 === 0`、(3) fn-typed identifier 経由 `ys.filter(positive)` で `positive` が `const positive: (n: number) => boolean = (n) => n > 0`、(4) string elem の length filter `names.filter((s) => s.length >= 5)`、(5) boolean elem の identity predicate `flags.filter((b) => b)`(`b` が `boolean` なので EXACT 一致で受理される)、(6) scalar capture (threshold) `xs.filter((x) => x > threshold)`、(7) class `Box` elem の field-based filter `boxes.filter((b) => b.value >= 50)`、(8) empty 配列 `(empty as Array<number>).filter((x) => x > 0)`、(9) 全要素 reject `xs.filter((x) => x > 100)` で empty 戻り、(10) chained `.filter().filter()` `xs.filter((x) => x > 1).filter((x) => x < 5)`、(11) `.filter().map()` chain `xs.filter((x) => x % 2 === 1).map((x) => x * 10)`、(12) 通常の filter 結果からの `.length` / `[i]` access。fail 1 本: `array_filter_callback_non_boolean_fail.ts` (`xs.filter((x) => x)` で `x` が `number` を返すので EXACT boolean check に引っかかる)。**fail を 1 本に抑えた理由**: arity mismatch / param 型不一致 / block body annotation 欠落 / destructuring などは `.map` の fail cases が同じ `inferCallbackFn` 経路をカバーしている、`.filter` 独自の fail は callback return type のみ。**合計 49 ケース全 pass**、既存 47 ケース(`.map` / template_literal / for_of_array / arrow_basic / arena_stress / optional_* / non_null_and_coalesce / optional_chain 等)に regression 無し。生成 C を `build/array_method_filter.c` で確認: stmt-expression 内に `for` ループ展開、`__topaz_filter_src_<id>` / `__topaz_filter_cb_<id>` / `__topaz_filter_dst_<id>` / `__topaz_filter_i_<id>` / `__topaz_filter_e_<id>` のローカル変数が namespace 衝突を避け、`reserve` 呼び出しが無いことが確認できた。

- **未対応 / 将来課題**。(1) **`.filter` の callback に index 引数を受ける `(e, i) => ...` 形**(JS 仕様の 2 引数 callback、arity check を緩めて `(elem, idx: number)` を accept する分岐、self-hosting で必要になったら `.map` と同時に解禁)、(2) **`.filter` の type predicate 形 `(x): x is Foo => ...`**(TS の type guard 機能、filter 結果の elem 型を narrow できる、現状は dst monomorph = src monomorph 前提なので narrow 不可、flow-sensitive narrowing と合わせて 1.5-3.5g 以降で再評価)、(3) **`.find` / `.findIndex`**(predicate callback + `T | undefined` / number 戻り、early break、`.filter` と同じ `inferCallbackFn` 経路で boolean callback の流用が可能)、(4) **`.some` / `.every`**(`boolean` 戻り、short-circuit、`.filter` と同じ predicate callback signature)、(5) **`.filter` 結果を直接 `for-of` の RHS に置く**(stmt-expression を for-of RHS に展開する経路が未整備、現状は tmp 変数経由)、(6) **`.filter` の callback が `T | undefined` を受ける形**(narrow 後の Array で `T | undefined` を含む elem を filter する path、現状 `Array<T | undefined>` の monomorph が無いので reject される、1.5-3.5g 以降の undefined-aware container と同時に解禁)、(7) **`.filter` chain の最適化**(`xs.filter(p).filter(q)` を `xs.filter(x => p(x) && q(x))` に fold する最適化、ただし predicate の副作用順序が変わるので user-visible な divergence の余地がある、Phase 2 の最適化 pass で再評価)、(8) **block body callback の flow-sensitive return inference**(`.filter` でも block body で return annotation 不要にできる路線、1.5-3.5g 以降で discriminated union narrowing と合わせて)、(9) **`.filter` 結果に対する `.length === 0` check の最適化**(filter→length 0 check は `xs.every(x => !p(x))` と等価、Phase 2 で最適化 pass を入れる時に検討)、(10) **typed array (`Float64Array` 等)の `.filter`**(現状 typed array 未対応、Phase 2 の WebGL / SIMD 路線で再評価)。


## Phase 1.5-3.5f-includes 実装決定ログ

- **スコープ = `.includes` 単発、callback-less メソッド群の最初**。検討した代替: (a) **`.includes` + `.indexOf` + `.lastIndexOf` をまとめて投入**(全部 callback-less + 等値比較で要素探索、共通の `<elem-eq>` 展開を 1 度で済ませられる)、(b) **`.includes` だけ着地、`.indexOf` / `.lastIndexOf` は後回し**(採用、return 型が違う(`boolean` vs `number`)、`.indexOf` は `-1` sentinel の取扱いが独立な議論、`.lastIndexOf` は逆順 iteration の方向制御も別物)。**採用根拠**: (1) `.includes` だけが ECMA-262 で SameValueZero を採用(NaN === NaN)、`.indexOf` / `.lastIndexOf` は SameValue (`===`) を採用するので等値ロジックが分岐する、(2) `.includes` は最も使われる頻度が高い API(membership test)で self-hosting 経由でも踏みやすい、(3) サブステップ単位で smoke 追加を細かく切ることで diff を読みやすくする。**代償**: `.indexOf` / `.lastIndexOf` を後で着地させる時に `<elem-eq>` のヘルパ extraction が必要(SameValue / SameValueZero の switch)、ただし `.includes` の inline 展開を local helper function に refactor するだけなので大きな手戻り無し。

- **SameValueZero 採用、`===` (SameValue) 不採用**。検討した代替: (a) **`===` セマンティクス(`NaN !== NaN`)で書き下す**(Topaz の他の operator `===` と完全に一致、divergence point が 1 つ減る)、(b) **SameValueZero(`NaN === NaN` を真にする)で書き下す**(採用、ECMA-262 `Array.prototype.includes` の仕様に準拠)。**採用根拠**: (1) ECMA-262 `Array.prototype.includes` 仕様 (`SameValueZero(searchElement, element)`) と完全一致、`xs.includes(NaN)` が `true` を返すのは JS 標準挙動、(2) 既に Map / Set の key 等値で SameValueZero を採用済み(`MEMO §3.5` 路線)、`.includes` も同じ路線で揃える方が Topaz 内で一貫、(3) `===` 採用すると `[NaN].includes(NaN) === false` という意外な挙動が出る(JS でも分かりにくい part)、SameValueZero の方が user expectation に近い、(4) 実装コストは scalar number で 4 演算 `(a == b) || (a != a && b != b)` の inline 展開で完結、helper 不要。**代償**: `===` operator と `.includes` の挙動が NaN 1 ケースだけ違う(`NaN === NaN` は false、`[NaN].includes(NaN)` は true)、ただし JS / TS でも同じ divergence なので「JS と挙動を揃える」と説明できる。

- **inline 展開、`topaz_eq_<T>_svz` helper 不採用**。検討した代替: (a) **`topaz_eq_number_svz(a, b)` 等を `runtime/runtime.h` に追加し、各 elem 種別で helper 呼び出しに統一**(scope 統一感、generic 化が容易)、(b) **stmt-expression 内で elem 種別ごとに比較式を inline 展開**(採用、helper 関数追加無しで完結)。**採用根拠**: (1) `runtime.h` の最小性原則(`MEMO §3.4` の「header-only な単一 runtime」)、SameValueZero number 比較は 4 演算で書けるので関数化のメリットが薄い、(2) 5 種類の elem(`number` / `boolean` / `string` / class / iface)それぞれで等値式が違うので generic helper 化しても per-elem switch が残る、(3) `string` は既存 `topaz_string_eq` を再利用、それ以外は inline 展開で 1 行に収まる、(4) inline 展開は C コンパイラの dead-code elimination / constant folding が効きやすい(elem 種別が固定されているので最適化が掛かる)。**代償**: stmt-expression の文字列長が elem 種別ごとに違う、ただし生成 C は人が読む対象ではないのでデバッグ性への影響は皆無。

- **第 2 引数 `fromIndex` 未対応 = reject、`.slice(fromIndex).includes(target)` 経路に誘導**。検討した代替: (a) **`fromIndex` を受け取って `topaz_slice_normalize` 相当の正規化(負数は `len + n`、範囲外クランプ)を `.includes` 専用に実装**(JS 仕様完全対応、`xs.includes(target, fromIndex)` がそのまま動く)、(b) **`fromIndex` は reject、user に `.slice(fromIndex).includes(target)` を書かせる**(採用、`.slice` 着地後は trivial に等価表現が書ける、機能の重複実装を避ける)。**採用根拠**: (1) `.slice` を 1.5-3.5f-slice で着地予定で `topaz_slice_normalize` を runtime.h に追加するため、その後 `xs.slice(fromIndex).includes(target)` が JS 仕様と等価に動く(`.slice` で arena に新 array を作るオーバーヘッドは付くが、`.includes` の linear scan に対して無視できる)、(2) 自前 from-index 計算を `.includes` 専用に inline 展開すると generated C が冗長化、`.indexOf` / `.lastIndexOf` でも同じ正規化が必要なので重複が増える、(3) self-hosting で `.includes(target, fromIndex)` の 2 引数形が必要になった時点で再評価、その時は `topaz_slice_normalize` を呼んで lo を計算 → for-loop の初期値を lo にする形に拡張。**代償**: 既存 JS / TS から書き写したコードで `xs.includes(target, n)` を `.slice(n).includes(target)` に手 edit する必要、ただし機械的な変換。

- **target 型 EXACT 一致、scalar 間 coercion 無し**。検討した代替: (a) **`number` elem に対して `string` target を SameValue で false 戻り**(JS 仕様、`[1, 2, 3].includes("2") === false`)、(b) **target 型不一致を compile-time error で reject**(採用、`emitWithExpected(arg, elem)` で型 check)。**採用根拠**: (1) Topaz は `===` / `!==` で型不一致を compile-time reject する方針(`MEMO §3.1` の strict 路線)、`.includes` も同じ路線で揃える、(2) `xs.includes("2")` のような呼び出しは 99% bug(意図して false を返すケースは皆無)、early-reject の方が有用、(3) class → iface の coercion は emitWithExpected 経由で自動なので、interface 要素配列に implementing class instance を渡せる(`shapes.includes(s1)` で `s1` が `Square`、shapes が `Array<Shape>` の場合 fat pointer に widening される)。**代償**: JS / TS から書き写したコードで型違いの target を渡す箇所が compile-error になる、ただし bug の兆候なので detection 価値が高い。

- **class / iface の reference identity**。検討した代替: (a) **class instance を structural equality(field 全比較)で同値判定**(JS の `Object.is` とは違うが、value semantics に近い)、(b) **class instance を pointer 比較**(採用、JS の `===` セマンティクスと一致、Set の reference identity と同期)。**採用根拠**: (1) JS の `===` は class instance に対してポインタ identity を見るので、`new Box(1) === new Box(1)` は false、これと一致、(2) Set の class / iface key も既に reference identity(`topaz_hash_pointer`)で揃っているので、`.includes` も同じ方針で一貫、(3) structural equality を採用すると recursive な class(self-referencing field)で cycle detection が必要になり、定義範囲を広げ過ぎる、(4) iface fat pointer は `.data` ポインタの比較で同値判定(同一 underlying object なら true、別 instance なら false)、これも Set / Map の iface key と同期。**代償**: `boxes.includes(new Box(2))` が field が一致しても false になる(JS と同じ挙動、user expectation との divergence は無い)、structural compare が欲しい場合は user が自前で `.some((b) => b.value === 2)` を書く。

- **smoke 戦略 = positive 19 ケース + fail 2 本**。positive (`array_method_includes.ts`、~75 行): (1) scalar number hit `xs.includes(3)` / miss `xs.includes(99)`、(2) **NaN 自己一致**(`0 / 0` で NaN を生成、`withNan.includes(0 / 0)` が SameValueZero で true)+ NaN ≠ 0 の miss、(3) string hit / miss、(4) boolean の `true` / `false` 両値 hit、(5) class instance の reference identity hit `boxes.includes(b)` + 別 instance miss `boxes.includes(new Box(2))`、(6) iface fat pointer の `.data` identity hit `shapes.includes(s1)`(class → iface coercion 経由)+ 別 instance miss、(7) 空配列の miss `empty.includes(0)`、(8) 単一要素配列の hit + miss、(9) `.filter().includes()` chain で filter 結果に対する membership test、(10) `.map().includes()` chain。fail 2 本: `array_includes_type_mismatch_fail.ts`(`Array<number>.includes("2")` で型不一致 reject)、`array_includes_from_index_fail.ts`(`xs.includes(3, 2)` で第 2 引数 reject)。**合計 53 ケース全 pass**、既存 51 ケース(`.filter` / `.map` / template_literal / for_of_array / arrow_basic / arena_stress / optional_* / non_null_and_coalesce / optional_chain 等)に regression 無し。生成 C を `build/array_method_includes.c` で確認: stmt-expression 内に `for` ループ展開、`__topaz_inc_src_<id>` / `__topaz_inc_t_<id>` / `__topaz_inc_r_<id>` / `__topaz_inc_i_<id>` のローカル変数が namespace 衝突を避け、number 経路で `(((src[i]) == (t)) || ((src[i]) != (src[i]) && (t) != (t)))` の SameValueZero inline 展開が確認できた、break 直後の `r = true; break;` も C コンパイラで `goto out` に下りているはず。

- **`NaN` global 識別子の未対応 → `0 / 0` で代用**。検討した代替: (a) **`NaN` global を識別子として受理**(`global Object` の `NaN` property を pre-define、`undefined` と同じ pattern で declareGlobal 的なものを追加)、(b) **`0 / 0` で NaN を生成して使う**(採用、新規対応ゼロ)。**採用根拠**: (1) `NaN` global を入れると `Infinity` / `undefined` / `globalThis` 等の他 global property も同じ pattern で要求される、scope を広げ過ぎる、(2) IEEE 754 で `0 / 0` は NaN を生成(C の double / double 0 も同じ挙動)、test code で書きやすい、(3) self-hosting で `NaN` を使うのは format 周りの edge case が中心で、`0 / 0` で代替できる(`Number.isNaN` も `x !== x` で代用可)。**代償**: test code が JS の `NaN` リテラルと比べて少し読みにくい、`const nan: number = 0 / 0;` のような annotation が必要、ただし台数は限定的。`NaN` / `Infinity` の global 識別子解禁は self-hosting で必要になった時点で再評価。

- **未対応 / 将来課題**。(1) **`.indexOf` / `.lastIndexOf` 着地**(`number` 戻り、`-1` sentinel、SameValue (`===`) で等値、`.includes` の `<elem-eq>` を `topaz_eq_<T>_same` / `_svz` の helper に extract してから switch)、(2) **`.some` / `.every` 着地**(predicate callback、short-circuit、`.includes` と同じ early break パターン)、(3) **`.includes` の第 2 引数 `fromIndex` 解禁**(`.slice` 着地後は `xs.slice(fromIndex).includes(target)` で代替可、JS API 互換が必要になった時点で再評価)、(4) **elem が Array / Map / Set / fn / undefined / union の `.includes`**(等値定義が未確定、特に nested Array の structural equality は recursive で expensive)、(5) **typed array の `.includes`**(現状 typed array 未対応)、(6) **structural equality helper の汎用提供**(class field 全比較、Map / Set key の structural option、現状は reference identity 限定で揃えている)、(7) **`NaN` global 識別子の解禁**(`Infinity` / `globalThis` 等の他 global property とセットで再評価)、(8) **`Array.from` / `Array.of` の static method**(現状 Array は class ではなく runtime monomorph なので、static method 解禁は AST 上で `Array` を識別子 + 特別扱いが必要、self-hosting で必要になったら)、(9) **`.flat` / `.flatMap` 着地**(nested Array の flatten、type 推論が複雑)、(10) **`.reverse` / `.sort`(in-place mutation)着地**(`.sort` は comparator callback で `inferCallbackFn` を流用、return 型 `number` で `< 0` / `= 0` / `> 0` 比較、unstable / stable は不明示)。


## Phase 1.5-3.5f-slice 実装決定ログ

Phase 1.5-3.5f-slice = `Array<T>.slice(start?: number, end?: number): Array<T>`、`Array<T>` の higher-order メソッド第 4 弾(`.map` / `.filter` / `.includes` の後、`.join` の前)。`.includes` の `fromIndex` 第 2 引数の代替手段でもあり、callback 不要 + range copy + size_t 正規化のパターンを確立した。

- **lowering = stmt-expression + size_t に正規化済みの range copy**。`{ <src ty> __s = recv; double __raw_start = <start expr or (double)NAN>; double __raw_end = <end expr or (double)NAN>; size_t __len = __s->len; size_t __lo = topaz_slice_normalize(__raw_start, __len, 0); size_t __hi = topaz_slice_normalize(__raw_end, __len, __len); if (__hi < __lo) __hi = __lo; <src ty> __d = topaz_array_<src>_new(); topaz_array_<src>_reserve(__d, __hi - __lo); for (size_t __i = __lo; __i < __hi; __i++) topaz_array_<src>_push(__d, __s->data[__i]); __d; }` の stmt-expression に lower。検討した代替: (a) **runtime ヘルパに丸投げ**(per-monomorph `topaz_array_<src>_slice(src, start, end)` を `TOPAZ_ARRAY_DEFINE` 内に追加、call サイトは関数呼び出し 1 行)、(b) **stmt-expression 内で展開**(採用、receiver / raw start / raw end / dst の tmp 化と for-loop を inline)。**採用根拠**: (1) `.map` / `.filter` / `.includes` で stmt-expression パターンが既に確立済み、同じ形で揃えると読みやすい、(2) `topaz_slice_normalize` ヘルパ 1 つに正規化ロジックを集約できるので、`TOPAZ_ARRAY_DEFINE` マクロに `_slice` 関数を生やす必要が無い(runtime.h の最小性原則と整合)、(3) range 確定後の `reserve(hi - lo)` + index for-loop で push する形は src の `data[]` を直接舐めるだけで amortized O(1) の doubling が一切発生しない、(4) src と dst が同じ monomorph なので class / iface / scalar / nested container すべて同じパスで処理できる(`<src ty>` を 1 度決めれば dst の型は自動で揃う)。

- **`topaz_slice_normalize(double n, size_t len, size_t def)` の設計**。`isnan(n)` で undefined default、`n < 0 ? (double)len + n : n` で負数を `[-len, 0)` → `[0, len)` に折り畳み、`[0, len]` に clamp、最後に `size_t` に narrow。**signature の選択肢**: (a) **`size_t topaz_slice_normalize(double n, size_t len, size_t def)`**(採用、`isnan` で default 分岐)、(b) **`size_t topaz_slice_normalize(double n, size_t len, bool has_arg, size_t def)`**(有無を bool で渡す)、(c) **start / end で別関数**(`_start` / `_end` を分割、それぞれの default を hard-code)。**採用根拠**: (1) `double n` + `isnan` sentinel なら呼び出しサイトで「`(double)NAN` を渡せば default」と統一できる、optional 引数の有無を call サイトの引数数で switch するだけで分岐が要らない、(2) `has_arg` を bool で渡す pattern (b) は 4 引数になって呼び出しサイトが長くなる、stmt-expression の中で書く時に読みづらい、(3) start / end を別関数にする (c) は def(`0` / `len`)が hard-code されてしまい、将来 `.slice` 以外で同じ正規化が必要になった時(`.copyWithin` / `.fill` / `.splice`)に再利用できない、(4) `isnan` check は IEEE 754 で `n != n` でも実装できるが、`<math.h>` の `isnan` マクロが既に include されているので明示的に使う方が読みやすい。**戻り値型 = `size_t`**: 正規化後は配列のインデックスとして使うので natural、`double` のままだと毎回 cast が必要になる。**`r > (double)len` の clamp に `>`(not `>=`)**: `end == len` は valid なので `>=` だと過剰、`>` で正しい。

- **`undefined` default の NaN sentinel 表現 = `(double)NAN` literal**。検討した代替: (a) **`topaz_opt_number` (= `{ present: bool, value: double }`) を渡す**(scalar の optional 表現を再利用、`.present == false` で default 判定)、(b) **`(double)NAN` を渡し `isnan` で判定**(採用)。**採用根拠**: (1) `topaz_opt_number` を使うと sentinel struct を関数引数に毎回作る必要がある、call サイトが `(topaz_opt_number){.present=false}` のような compound literal で冗長、(2) IEEE 754 で `NaN` は「実数の値ではない」マーカーとして言語仕様レベルで定義されている、整数 index の正規化では絶対に出てこないので sentinel として安全(0 / 負数 / `Infinity` は valid な input)、(3) C の `<math.h>` で `NAN` マクロ + `isnan(x)` マクロが portable に使える、(4) 呼び出しサイトの分岐が `expr.arguments.length >= N ? <expr> : "(double)NAN"` の 1 三項演算で済む。**代償**: 仕様外の `xs.slice(NaN, NaN)` のような呼び出しが「両端 default」として扱われる(JS 仕様も `ToInteger(NaN) === 0` なので `(0, 0)` で empty、Topaz は NaN を default に解釈するので `(0, len)` で全コピー)— ただし `NaN` を index に渡すコードは pathological なので user-visible な divergence にはならない。

- **dst monomorph = src monomorph、recordArrayMonomorph 不要**。`.filter` と同じ理由で要素型変換しないので新規 Array typedef は要らない。callback 無しなので `recordFnMonomorph` も不要(`.includes` と同じ完全 callback-less メソッド)。**含意**: `.slice` は 1 monomorph も増やさず、純粋に既存の `topaz_array_<src>_new` / `_reserve` / `_push` を流用するだけ、`emitArrayMethodCall` 内で完結する(`inferType` 側は `baseType` を返すだけ)。

- **`reserve(hi - lo)` の事前確保**。検討した代替: (a) **`reserve` を省略して doubling alloc 任せ**(`.filter` と同じ戦略、要素数が実行時にしか分からない場合)、(b) **`reserve(hi - lo)` で範囲分だけ事前確保**(採用、range が呼び出し時点で確定する)。**採用根拠**: (1) `.filter` と違い `.slice` は `hi` / `lo` が runtime で計算されるが、push 開始前に値が出揃っている、(2) doubling だと `hi - lo == len` の全コピーでも 2-3 回 realloc + memcpy が走る、`reserve(N)` 1 回で同等の memory + 全 push が O(1) で完了する(amortized O(1) ではなく確定 O(1))、(3) memory cost も `hi - lo` ぴったりなので無駄無し、`.filter` の「reserve(len) で過剰確保したけど filter で半分捨てる」ような pessimization は無い。**`hi - lo` の桁あふれ**: `__hi < __lo` の逆転を if で `__hi = __lo` に潰しているので `__hi - __lo >= 0`、size_t underflow は発生しない。

- **start > end の clamp = `if (__hi < __lo) __hi = __lo`**。検討した代替: (a) **`__hi >= __lo` を要求 → for-loop の中で `i < hi` 条件で自然に 0 反復**(C は size_t で計算するので `__hi - __lo` のラップアラウンドが先に発生する)、(b) **`__hi < __lo` を if で `__hi = __lo` に潰す**(採用、`reserve` の引数を 0 にする)、(c) **start > end でエラーで落とす**(JS は empty を返すので divergence)。**採用根拠**: (1) `hi - lo` を `reserve` に渡す時に underflow すると巨大 size_t になって OOM、明示的に潰す方が安全、(2) JS は `xs.slice(3, 1)` で empty array を返す(throw しない)、Topaz もこれと一致させる方が user expectation に近い、(3) for-loop の `__i < __hi` 条件は `__lo <= __hi` が前提なので、潰しておけば 0 反復で素直に終わる。

- **引数型の strict check = `inferType` で `number` EXACT 一致**。検討した代替: (a) **call site で `inferType(arg).kind !== "number"` を check して reject**(採用、emit より早い段階で reject)、(b) **C 側に降ろして compile-error に任せる**(emit 後の cc 段で型エラーになる、メッセージが分かりにくい)、(c) **`emitWithExpected(arg, T_NUMBER)` だけで coercion 任せ**(現状 number への coercion は存在しないので結局 reject される)。**採用根拠**: (1) `Array.slice` の API は `(start?: number, end?: number)` で number 限定、boolean / string / class の coercion を入れる理由が無い、(2) call site で reject すると error location が argument 位置になって user に親切、(3) `inferType` を 1 回呼ぶだけで cheap な check。**string や class を渡すと**: `Array.slice argument must be number, got <type-ident>` で reject。`undefined` 明示渡し(`xs.slice(undefined, 3)`)も同様に reject — TS は accept するが Topaz は coercion を入れない方針。

- **未対応**(明示エラー)の整理。(1) **引数 3 個以上**(`Array.slice expects at most two arguments`、TS は無視するが Topaz は厳格)、(2) **引数型が `number` 以外**(`Array.slice argument must be number, got <type>`)、(3) **`Array<T>` 以外の receiver**(string slice は未対応、`string.slice` を別途定義する宿題)、(4) **`xs.slice(undefined, 3)` のような明示 undefined 渡し**(現状 `undefined` 識別子は `T | undefined` context でしか受理されない、`xs.slice(undefined as number | undefined, 3)` のような annotation 経路でも未対応、必要なら 1.5-3.5g 以降で再評価)、(5) **`xs.slice(NaN)` のような NaN 明示渡し**(IEEE 754 で valid な double だが、`topaz_slice_normalize` の `isnan` が default に解釈するので JS とは divergence、`xs.slice(0/0)` も同じ挙動)。**`.slice` 経由の `.includes(target, fromIndex)` 代替**: `xs.slice(fromIndex).includes(target)` で意味的に等価、memory コストは O(len - fromIndex) だが大半のケースで顕在化しない、`.includes` の `fromIndex` 第 2 引数 reject は維持。

- **smoke 戦略 = positive 15 ケース + fail 2 本**。positive (`array_method_slice.ts`、~95 行): (1) 両端指定 `xs.slice(1, 4)`、(2) start のみ `xs.slice(2)`、(3) 無引数全コピー `xs.slice()`、(4) 負数 start `xs.slice(-2)`、(5) 負数 end `xs.slice(0, -1)`、(6) 負数両方 `xs.slice(-3, -1)`、(7) start > end で empty `xs.slice(3, 1)`、(8) start > len で empty `xs.slice(99)`、(9) end > len で clamp `xs.slice(3, 99)`、(10) 空 source `[].slice(0, 5)`、(11) string elem `names.slice(1, 3)`、(12) class elem の reference identity 保存(slice 結果を const に bind → 取り出した box の field を mutate → 元 array の box も影響を受ける)、(13) chained `xs.slice(1, 5).slice(0, 2)`、(14) `.filter().slice()` chain、(15) slice 後の独立性 = `dup.push(99)` が `src` に影響しない(`len` が独立、`data` も別 buffer)。fail 2 本: `array_slice_arg_type_fail.ts`(`xs.slice("0")` で string 渡し reject)、`array_slice_too_many_args_fail.ts`(`xs.slice(0, 2, 1)` で 3 引数 reject)。**合計 55 ケース全 pass**、既存 53 ケース(`.map` / `.filter` / `.includes` 含む)に regression 無し。**class elem の slice で confirm したこと**: `bs[0]` を const に bind してから field mutate すると `orig.value` も同じ値に変わる、つまり slice は要素を copy ではなく pointer を共有する(JS の `Array.slice` も class instance を shallow copy なので一致)。

- **生成 C の確認**。`build/array_method_slice.c` を読むと: (1) stmt-expression が compact form `({ src_t __s = recv; double __raw_s = ...; double __raw_e = ...; size_t __len = __s->len; size_t __lo = topaz_slice_normalize(__raw_s, __len, 0); size_t __hi = topaz_slice_normalize(__raw_e, __len, __len); if (__hi < __lo) __hi = __lo; src_t __d = topaz_array_<src>_new(); topaz_array_<src>_reserve(__d, __hi - __lo); for (size_t __i = __lo; __i < __hi; __i++) topaz_array_<src>_push(__d, __s->data[__i]); __d; })` で展開されている、(2) `__topaz_slice_<id>` 接頭辞で tmp が namespace 衝突無し、(3) `topaz_slice_normalize` は static inline で展開、IEEE 754 NaN sentinel が正しく default に折り畳まれる、(4) class elem (`topaz_class_Box *` array) の場合も `data[i]` が pointer なのでそのまま push、reference identity が保たれる。

- **`.includes` の `fromIndex` 代替確立 → maintaince**。`.slice` 着地で `xs.slice(fromIndex).includes(target)` が使えるようになった、ただし `.includes` 側の `fromIndex` 第 2 引数の明示エラーは維持(理由: (1) 引数 1 個 / 2 個で signature が分岐するパターンを増やさない、(2) `.slice` 経由は memory コストが O(len - fromIndex) だが顕在化するケースが限定的、(3) 必要になった時点で `.includes` 側にも fromIndex を入れるのは小修正、現状の早期エラーは「忘れて 2 引数渡した bug の検出」として価値がある)。

- **未対応 / 将来課題**。(1) **`string.slice` 着地**(現状 `string` には `.length` プロパティしかない、`.slice` / `.substring` / `.charAt` を別途解禁する宿題、UTF-8 byte offset の扱い + JS の UCS-2 とは divergence する点を文書化)、(2) **`.splice`(in-place mutation + 戻り値)着地**(`Array.splice(start, deleteCount, ...items)` は in-place + 取り除いた要素を Array で返す、`.slice` と semantics が違う点を明確化)、(3) **`.concat` 着地**(複数 array を平坦化 / 連結、可変長引数の扱い)、(4) **`undefined` 明示渡しの解禁**(`xs.slice(undefined, 3)` のような pattern、optional 引数の semantics と整合を取る、1.5-3.5g 以降)、(5) **`xs.slice(NaN)` の JS-divergent 挙動の整理**(JS は `ToInteger(NaN) === 0` で empty、Topaz は NaN を default として全コピー、divergence を document に明記)、(6) **`Array<fn>` slice**(`.slice` 自体は要素型に依存しないので `Array<fn>` 解禁時に自動で使える、1.5-3.5g 以降)、(7) **typed array の `.slice`**(現状 typed array 未対応)。


## Phase 1.5-3.5f-join 実装決定ログ

- **`.join` のサブステップ位置付け**。1.5-3.5f の最終サブステップ、`.map` / `.filter` / `.includes` / `.slice` に続く 5 つ目で 1.5-3.5f(Array higher-order メソッド集中投入)を closed。これまでの 4 サブステップが「Array<T> → Array<U>」または「Array<T> → boolean」だったのに対し、`.join` は **Array<T> → string** で唯一の戻り値変換、かつ「per-element to_string + 連結」という 2 段階処理を持つ点で他と性格が違う。**lowering 戦略は他 4 つと意図的に divergence**(stmt-expression ではなく per-monomorph helper 関数を emit)。

- **per-monomorph helper vs inline stmt-expression vs `TOPAZ_ARRAY_DEFINE` 拡張**。`.join` は「2 パス traversal + 中間長さ計算 + arena alloc + 書き込み」の 4 工程で、inline stmt-expression に展開すると call サイトごとに ~25 行の C コードが膨らむ(`.map` / `.filter` / `.includes` / `.slice` はいずれも 5-10 行で済んでいた)。3 案検討: (a) **inline stmt-expression**(各 call サイトで重複コード、保守性が悪い、最適化は inline 化に任せる)、(b) **`TOPAZ_ARRAY_DEFINE` マクロを拡張して `_join` メソッドも一緒に吐く**(マクロが肥大化、`number` / `boolean` / `string` で stringify 戦略が違うので分岐が必要、class / iface elem では未使用のヘルパが吐かれて `-Wunused-function` 大量発生)、(c) **codegen で per-(monomorph) ヘルパ関数を on-demand に吐く**(`.join` を呼んだ elem 型だけ helper 化、dedupe は monomorph 名キー、`TOPAZ_ARRAY_DEFINE` には触らない)。**(c) を採用**: 理由は (1) `.join` を呼ばないプログラムには helper が出ない(現状 `array_method_join.ts` 以外は全 0 個)、(2) elem 型ごとの stringify 分岐が helper 本体に局在して call サイトが簡潔(1 行の function call)、(3) 1.5-3.5g 以降で `Array<class>` の `.join` を許す方向に拡張する時も helper だけ書き換えれば良い(call サイトは触らない)。

- **`arrayJoinHelperSlot` の新設と配置**。新規 emit slot を `containerMonomorphSlot` の直後・`fnTypedefSlot` の前に挿入。配置理由: (1) helper は `topaz_array_<elem>` 型を引数に取るので Array monomorph の typedef 後に来る必要がある、(2) helper の戻り値型 `topaz_string` は runtime.h 既存型なので fn typedef slot より前で問題ない、(3) helper 内で `topaz_number_to_string` / `topaz_boolean_to_string` / `topaz_string_concat` / `topaz_arena_alloc` を呼ぶが、これらは runtime.h で static inline 定義されているので順序問題は起きない。`-Wunused-function` で wrap(`.join` を 1 度だけ呼んだ場合でも helper は static inline で吐かれるため、コンパイラの最適化次第で warning が出る可能性に備える)。

- **`arrayJoinMonomorphs: Map<string, TopazType>` の追加**。`arrayMonomorphs` と並ぶ独立した Map として `Emitter` に持つ。理由: Array monomorph 自体は `[1, 2, 3].length` のような non-join 使用でも登録される一方、join helper は `.join` を呼ぶ Array 型だけが必要。両者を別 Map に分離することで、(a) helper の dedupe が join 利用分だけになる、(b) `.join` を呼ばないプログラムでは helper slot が空になり、(c) 既存の `recordArrayMonomorph` の signature を変えずに済む(後方互換性、`.map` 等の経路に regression を入れない)。Map key は `typeKey(t)`(既存の type key 関数を流用)で、`Array<number>` と `Array<number>` を別 monomorph として登録する事故を防ぐ。`recordArrayJoinMonomorph(t)` 内で `arrayElem(t)?.kind` が `number` / `boolean` / `string` 以外なら早期 return(class / iface / nested container は call site で既に reject されているはずだが、`inferType` 経路の二重防衛として残す)。

- **`emitArrayJoinHelper(t)` の本体構造**。生成 C は `static inline topaz_string topaz_array_<elem>_join(topaz_array_<elem> *src, topaz_string sep) { ... }` の固定形式。本体は次の 5 ブロック: (1) `if (src->len == 0) return (topaz_string){"", 0};` で empty 配列の `(n - 1) * sep.len` underflow 回避、(2) pass 1 = `size_t total = 0; for (size_t i = 0; i < src->len; i++) { <to_string>; total += __e.len; if (i > 0) total += sep.len; }`、(3) `char *buf = topaz_arena_alloc(total + 1);` で 1 度 alloc、(4) pass 2 = `size_t off = 0; for (size_t i = 0; i < src->len; i++) { <to_string>; if (i > 0 && sep.len > 0) { memcpy(buf + off, sep.data, sep.len); off += sep.len; } memcpy(buf + off, __e.data, __e.len); off += __e.len; }`、(5) `buf[total] = '\0'; return (topaz_string){buf, total};`。`if (i > 0 && sep.len > 0)` で空 separator 時の `memcpy(_, _, 0)` 呼び出しを避ける(undefined behavior 回避、C 標準では `memcpy(dst, src, 0)` は valid だが gcc の analyzer が誤検出することがあるため)。

- **stringify を pass 1 / pass 2 両方で呼ぶ trade-off**。中間 cache(`topaz_string` の配列を arena に貯めて pass 2 で再利用)を持たない設計。理由: (1) `number` elem の場合 `topaz_number_to_string` が arena に 24-48 bytes を焼くので 1000 要素で 48KB の余分 alloc が発生するが、per-process arena の前で誤差レベル(全体 alloc 量から見ると <1%)、(2) `boolean` の場合 `topaz_boolean_to_string` は static literal を返すので arena alloc 0(再呼び出し NOP)、(3) `string` の場合 identity なので arena alloc 0(再呼び出し NOP)、(4) cache 設計は stack alloc が VLA 必須(C99 ではあるが Topaz は `-O2` 前提で VLA を避けたい)/ heap alloc は arena からの一時取得 + 解放不可で結局同じか悪い、(5) cache サイズ N に対する遅延評価は最適化器に任せられるが per-element の関数呼び出しコストが顕在化するのは N > 10000 程度で、`Array.join` の典型ユースケース(文字列の整形、CSV 出力)では問題にならない。**将来 N が大きい場合の最適化余地**: 1.5-3.5g 以降で `.join` performance がボトルネックになった時点で cache 戦略を見直す。現状はシンプル優先。

- **separator default の表現**。call サイトで `((topaz_string){",", 1})` の compound literal を直接合成、helper は optional 引数を意識しない。代替案 1: helper を 1-arg / 2-arg の 2 種類吐く(コード重複)、代替案 2: helper に sentinel を渡す(`topaz_string` に NULL data を許す semantics が runtime 全体に波及)。compound literal 直接合成が最小コストで、`","` literal は ASCII で len=1、`{",", 1}` は static const として最適化される。**call サイトの emit**: `emitArrayMethodCall` で `expr.arguments.length === 1` なら `emitWithExpected(expr.arguments[0]!, T_STRING)`、`=== 0` なら hard-coded `((topaz_string){ ",", 1 })`。文字列リテラル単一 separator の場合(`.join(",")` / `.join("|")`)は emit 結果が同じ compound literal になるので、`-O2` で fold される(performance loss 無し)。

- **scalar elem 3 種に限定する判断**。`.join` が elem に必要とするのは `topaz_string` への変換関数のみで、`number` / `boolean` / `string` の 3 種で `topaz_number_to_string` / `topaz_boolean_to_string` / identity が確立している。class / iface 要素の reject は (1) user-defined `.toString()` メソッドが現状未対応、(2) class fields の format policy(`{x: 1, y: 2}` vs `Point(1, 2)` vs `[object Object]`)が決まっていない、(3) `xs.map((x) => x.toString()).join(",")` で代替できるので user 側に format choice を委ねる、の 3 点。**class が user-defined `.toString()` を持つ場合のみ別途解禁**は将来課題: `class C { toString(): string { ... } }` が宣言された class の `Array<C>.join()` だけ自動で `.toString()` 呼び出しを inline 化する、という拡張は 1.5-3.5g 以降で `.toString()` 解禁時に再評価。

- **`number` の format policy は ECMA-262 ToString**。`topaz_number_to_string(0.1 + 0.2)` は `"0.30000000000000004"` を返す(IEEE 754 double の shortest round-trip representation)。`array_method_join.ts` の `[3.14, 0, -1.5].join(",")` → `"3.14,0,-1.5"` が ECMA-262 仕様と一致。**潜在的な divergence**: `topaz_number_to_string` は内部で `snprintf("%.*e") + strtod` の round-trip 探索を行っており、Ryu と比べて 1-2 桁遅い(`.join` で N 要素 × 17 反復で N=1000 だと ~20K 反復、それでも実時間で数 ms オーダー)。Phase 2 のベンチマーク整備時に Ryu に差し替える宿題は `.join` も含めて統一的に解決される。

- **fail 回帰の 3 本立て**。(1) `array_join_too_many_args_fail.ts` = `.join(",", "?")` を call サイトで reject(TS は仕様上 1 引数のみだが silent に第 2 引数を ignore、Topaz は厳格に止める)、(2) `array_join_sep_type_fail.ts` = `.join(0)` を `Array.join separator must be string, got topaz_number` で reject(number → string coercion は入れない方針、`.join(String(n))` などで明示変換すべき)、(3) `array_join_class_elem_fail.ts` = `Array<Box>.join()` を `Array.join is unsupported for element type ...` で reject(format policy 未確定、user の `.map((b) => b.toString())` 等で string 化してから join を指示)。3 本とも `tests/smoke.sh` の `run_fail_case` で error substring を check、合計 59 ケース全 pass を確認。

- **生成 C の確認**。`build/array_method_join.c` を読むと: (1) `topaz_array_number_join` / `topaz_array_string_join` / `topaz_array_boolean_join` の 3 helper が `static inline` で `containerMonomorphSlot` の直後に並んでいる、(2) elem 型ごとの stringify 分岐(`number` は `topaz_number_to_string(src->data[i])`、`boolean` は `topaz_boolean_to_string(src->data[i])`、`string` は `topaz_string __e = src->data[i];`)が helper 本体内に展開されている、(3) call サイトは `topaz_array_number_join(__topaz_tmp_<id>, ((topaz_string){",", 1}))` のような plain function call 1 行に lower、(4) `.map().join()` / `.filter().join()` / `.slice().join()` の chain は中間 Array が tmp に bind されてから join helper に渡される(中間 Array が arena に持たれているので解放問題は無い)、(5) 複数 `.join` 呼び出し(`ns.join(":") / ns2.join(":")`)で `topaz_array_number_join` が 1 度だけ吐かれて共有されているのを確認。

- **Phase 1.5-3.5f closed の意義**。Array prototype の主要 API(map / filter / includes / slice / join)が揃った。`src/codegen.ts` で self-hosting する際に必要な Array 操作(AST node の transform / filter / 識別子 lookup / 出力 string 化)が一通り書ける状態になった。**棚卸し再評価**: `docs/archive/self-hosting-inventory.md` で挙げていた Array 周りの blocker は全て解消、残る self-hosting blocker は `Map.values()` / `Set.values()`(1.5-3.5g)、destructuring(1.5-3.5h?)、generic method(1.5-5)、`Array<fn>` storage(1.5-3.5g と同時)。

- **未対応 / 将来課題**。(1) **class elem の `.join` 解禁**(user-defined `.toString()` がある class に限定して自動 dispatch、1.5-3.5g 以降)、(2) **`Array<Array<T>>` の `.join`**(JS は内部 Array を再帰的に `.join(",")` する、現状 reject、format policy が深い再帰になるので保留)、(3) **`number` format の Ryu 差し替え**(Phase 2)、(4) **`.join` での lazy stringify cache**(N > 10000 で performance が顕在化したら再評価、1.5-3.5g 以降)、(5) **`undefined` 明示渡し**(`xs.join(undefined)` を `.join()` と同等として扱う、`.slice(undefined, 3)` と同じ semantics 統合、1.5-3.5g 以降)、(6) **`Array<fn>` の `.join`**(`Array<fn>` 解禁時に format policy を `fn` 型 sentinel として一緒に決める、1.5-3.5g 以降)、(7) **`String.prototype.join` 系**(TS では String.split → Array.join の round-trip が頻出、`.split` 着地時に対で再評価)、(8) **separator が computed string**(`.join(prefix + sep)` のように expression 結果を渡す pattern は既に動作するが、空文字 separator + 巨大 N での performance は未測定)。

## Phase 1.5-3.5g-mapset 実装決定ログ(for-of over `Set<T>` / `Map.values()` / `Map.keys()` / `Set.values()` / `Set.keys()`)

- **1.5-3.5g の位置付け**。Phase 1.5-3.5b で `for-of` を Array<T> 限定で hard-code した時に積み残した「Map / Set の値走査」を解禁する。1.5-3.5g 全体は (a) **mapset サブステップ**(本ログ — Set 走査 + Map/Set の `.values()` / `.keys()`)、(b) **Iterator interface サブステップ**(`Iterator<T>` の最小 trait と `next()` 経由の dispatch、`.map` 結果を直接 for-of の RHS に置く path 含む)、(c) **`Array<fn>` storage**(callback 列を Array に詰める要件)、の 3 つに分割。**mapset を先に着地させる判断**: 既存の Map / Set monomorph(open-addressing + slot state machine)を再利用すれば runtime.h 改修無しで lower でき、Iterator trait の設計余地と分離して問題ドメインを絞れる。Iterator を先にやると mapset の lowering を「Iterator 経由でやるか直接 slot を舐めるか」で迷走するリスクがあり、direct slot 経路を確立してから iterator で wrap し直す方が手戻りが少ない。

- **lowering 戦略は index for-loop + slot state skip**。生成 C は `{ <ht_c_ty> __topaz_for_ht_<id> = <recvStr>; for (size_t __topaz_for_idx_<id> = 0; __topaz_for_idx_<id> < __topaz_for_ht_<id>->cap; __topaz_for_idx_<id>++) { if (__topaz_for_ht_<id>->slots[__topaz_for_idx_<id>].state != TOPAZ_HASH_SLOT_OCCUPIED) continue; <bind_c_ty> bindName = __topaz_for_ht_<id>->slots[__topaz_for_idx_<id>].<field>; <body>; } }`。設計上のポイント: (1) recv は tmp に snapshot して 1 回だけ評価(`new Map().values()` のような副作用持ち RHS でも安全)、(2) `cap` を ループ上限にして tombstone を含む slot 配列を全 walk、(3) `OCCUPIED` 以外(`EMPTY` / `DELETED`)は `continue` で skip — user の `continue` も同じ C for-loop に乗るので semantics が自然に合成される、(4) `cap == 0`(empty Map / Set)は `i < 0` が false で body に入らず safe(`slots` が NULL でも触らない)、(5) binding は body 先頭で `<bind_c_ty> bindName = slots[idx].<field>` として宣言、`continue` / `break` のスコープから当然見える。Set 用の (`field` = `key`、Set slot 構造体に `key` フィールドだけ)と Map.values() (`field` = `value`)、Map.keys() (`field` = `key`)で同じヘルパを共有。

- **`emitForOfHashLowering` 新設の理由**。Array 用の `emitForOfArrayLowering` と意図的に分離。理由: (1) hash table は cap-based walk + slot state check が必須で、Array の `for (i = 0; i < len; i++)` とは構造が違う、(2) Array の `data[i]` access は単純な pointer indexing、hash table は `slots[i].state` の if 分岐が要る、(3) binding の field は Array では `data[i]`、hash では `slots[i].key` or `slots[i].value` で statically 分岐するので caller が文字列を渡す形にした(`field: "key" | "value"`)。共通化を試みると分岐が body に散らばって読みづらくなるので、別ヘルパが正解。

- **special form detection は `.values()` / `.keys()` / `.entries()` の 3 つを syntactic に拾う**。`emitForOfStatement` で RHS が `CallExpression` かつ callee が `PropertyAccessExpression` の場合、(1) base の `inferType` が `map` or `set`、(2) method 名が `values` / `keys` / `entries`、(3) 引数 0 個、の 3 条件で special form 判定。`.entries()` は **明示 reject**(`for-of over .entries() is unsupported (requires destructuring binding, not yet implemented)`)— iterator 形式の `[K, V]` tuple binding が必要で、destructuring が未対応の現状では値の取り出しができないため。**Iterator interface への昇格**を保留する判断: 現状 `.values()` / `.keys()` の戻り値は「for-of の RHS でのみ使える単独で表現できない値」として扱い、`const vs = m.values()` のような bare binding は明示 reject(`Map.values() is only allowed as the right-hand side of a for-of statement`)。これは TS の `IterableIterator<V>` 型相当の中間型を持たない判断で、(a) Iterator interface を入れると `next()` 経由の dispatch + state machine が runtime.h に必要、(b) for-of の RHS でしか使わない現状では中間型が dead code、(c) 1.5-3.5g-iterator サブステップで明示的に解禁する方が型設計を一段で済ませられる、の 3 点。

- **plain Set RHS と `.values()` / `.keys()` を等価に扱う**。`for (const x of someSet)` と `for (const x of someSet.values())` / `for (const x of someSet.keys())` は JS semantics で全て elem を順次 yield する(Set の `.values` と `.keys` は同じ関数 reference)。Topaz でも 3 経路を同じ `emitForOfHashLowering` に流して同一の slot walk を生成、binding 型は `setElem(t)` から取る(`field` は常に `"key"` — Set slot は単一の `key` フィールドを持つ structure)。**plain Set RHS の binding type 推論**: 既存の `emitForOfStatement` の path で `inferType(rhs).kind === "set"` を check した時点で `setElem` を呼ぶ、Array 経路と並列。

- **Map RHS 自体は引き続き reject**。`for (const x of someMap)` は JS では `[K, V]` tuple を yield(iterator default が `.entries`)、これも destructuring 必須で現状は `for_of_map_fail.ts` で reject 済み。1.5-3.5g-mapset では「Map の bare RHS は依然エラー、`.values()` / `.keys()` のみ受ける」というポリシーを維持。Set との非対称性(Set bare RHS は OK、Map bare RHS は reject)は JS 仕様そのままで documented divergence ではない。

- **`emitMapMethodCall` / `emitSetMethodCall` での `.values()` / `.keys()` / `.entries()` 早期 reject**。method call の dispatch 経路で `.values` / `.keys` を見たら `Map.values() is only allowed as the right-hand side of a for-of statement` でエラー、`.entries` は `Map.entries() is unsupported (requires destructuring binding, not yet implemented)` でエラー。理由: special form 判定は `emitForOfStatement` 内でしか行われないので、それ以外のコンテキスト(`const vs = m.values()`, `console.log(m.values())`, etc.)で `.values()` に遭遇したら必ずここでエラーにできる。`inferType` 側の Map/Set method dispatch も同じエラー文言を返すように同期(`inferType` 経路に乗ってから後で codegen が落とすと error message の location 情報が劣化するので、両方で同じ message を出す)。

- **fail 回帰の 2 本立て**。(1) `for_of_map_entries_fail.ts` = `for (const e of m.entries())` を `for-of over .entries() is unsupported` で reject(destructuring 解禁時に再評価する誘導 message)、(2) `map_values_outside_for_of_fail.ts` = `const vs = m.values(); console.log(vs);` を `Map.values() is only allowed as the right-hand side of a for-of statement` で reject(Iterator interface 着地までは for-of の RHS 限定)。Set 側の `.values()` / `.keys()` の bare 利用も同じ message で reject されるはずだが、対称性のために専用 fail case は作らず Map 側で代表させる。

- **positive 回帰の 2 本**。(1) `for_of_set.ts` = Set<number> の plain RHS + `.values()` + `.keys()` で同一 sum(15)、empty Set、`break` で early exit、string Set(length 集約で hash order 非依存)、tombstone walk(delete 後の skip)、class instance Set(reference identity)、interface fat pointer Set(vtable 不要 field access)、nested for-of(両 binding を body で使って sum で order 非依存)、annotated binding 型一致、の 11 ケース。(2) `for_of_map_values.ts` = Map<string, number>.values() / .keys()、annotated binding 型、empty Map、Map<number, string>.values() で `continue`、class V Map で method dispatch、interface V Map で vtable dispatch、tombstone walk、number-keyed Map.keys()、break で early exit、nested(values × Array)で両 binding 使用、の 11 ケース。**hash order 非依存性の担保**: いずれの positive ケースも sum / count / aggregated length など可換な演算で expected を確定、FNV-1a / splitmix64 の hash 順序に依存しない。tombstone ケース(`delete()` 後の walk)は 1.5 系の Map / Set 実装で OCCUPIED 以外を skip する保証を回帰する。nested ケースで両 binding を body で使うのは `-Wunused-variable` を silencing するため(初期実装で `nested = nested + 1` にしていて warning が出たため修正、expected も 129 に再計算)。

- **`continue` / `break` の semantics 自然合成**。生成 C は単純な for-loop なので、user の `continue` は次の iteration の loop check に飛んで slot state チェックを再度通る(OCCUPIED じゃない slot を skip する logic と同居)、`break` は外側の `}` を抜けて stmt block を完了する。JS の for-of との semantics 一致は (a) `continue` で次の yield に進む、(b) `break` で iteration を完全に止める、の両方で確認(`for_of_set.ts` の `break` で `100` を見つけたら止める、`for_of_map_values.ts` の `continue` で `v.length > 3` の要素を skip)。

- **codegen の構造**。`emitForOfStatement` の dispatch が 4 経路に分岐: (1) RHS が `.values()` / `.keys()` の special form → `emitForOfHashLowering` を `field` 引数付きで呼ぶ、(2) RHS が `.entries()` → 明示エラー、(3) RHS の `inferType` が `set` → `emitForOfHashLowering` を `field: "key"` で呼ぶ、(4) RHS の `inferType` が `array` → 既存の `emitForOfArrayLowering`、(5) それ以外 → 既存の `for-of requires an Array<T>` エラー(message は将来 `Set / Iterator も受ける` に書き換える宿題)。special form 判定を最初に置く理由: `inferType(rhs)` を走らせると `.values()` の戻り値型を確定しに行くが、現状その型を持たないので codegen が混乱する。AST node の構造で先に分岐すれば inferType の呼び出し自体を skip できる。

- **`emit` slot 配置と前方依存**。本サブステップでは新規 slot を作らず、既存の `emitMapMethodCall` / `emitSetMethodCall` 内で reject を入れただけ。生成 C は (1) `runtime.h` で既に定義済みの `TOPAZ_HASH_SLOT_OCCUPIED` 定数、(2) class / iface monomorph 経路で吐かれた `topaz_map_<K>_<V>` / `topaz_set_<T>` の slot 構造体、を再利用するので順序問題は皆無。**新規 monomorph も不要**: Set<class> / Set<iface> / Map<scalar, class> / Map<scalar, iface> の monomorph は 1.5-3a で `map_set_class_iface.ts` 経路で既に登録されており、for-of の binding はその slot から `key` / `value` を取り出すだけ。class binding(`for (const box of boxes) { ... box.value ... }`)は既存の `topaz_class_<C> *` field access に下りるし、interface binding(`for (const n of ifs) { ... n.name ... }`)は fat pointer の vtable getter 経由に下りる(両者とも Array<class> / Array<iface> 経路で確立済みのパスを通る)。

- **生成 C の確認**。`/tmp/for_of_set.c` で次を確認: (1) `for (size_t __topaz_for_idx_0 = 0; __topaz_for_idx_0 < __topaz_for_ht_0->cap; __topaz_for_idx_0++)` の cap-based walk、(2) `if (__topaz_for_ht_0->slots[__topaz_for_idx_0].state != TOPAZ_HASH_SLOT_OCCUPIED) continue;` の OCCUPIED 以外 skip、(3) `topaz_number x = __topaz_for_ht_0->slots[__topaz_for_idx_0].key;` の binding 宣言、(4) Set<class> 経路で `topaz_class_Box *box = __topaz_for_ht_<id>->slots[...].key;` が出る(`key` フィールド名は Set 用の slot 構造体に合わせる)、(5) Map<string, number>.values() 経路で `topaz_number v = __topaz_for_ht_<id>->slots[...].value;` が出て `key` ではなく `value` を取る、(6) nested for-of で `__topaz_for_idx_<id>` の id が outer / inner で別 unique number になり名前衝突しない。

- **未対応 / 将来課題**。(1) **`for (const [k, v] of m.entries())`** = destructuring binding 解禁時に同時に着地、`emitForOfHashLowering` を 2 binding 対応に拡張(`field` を `["key", "value"]` の tuple で受ける)、(2) **`for await (...)`** = async iterator、Topaz は async 自体未対応、(3) **`Map.values()` の bare 利用**(`const vs = m.values()` / `console.log(vs)` / `xs.push(vs)` etc.) = Iterator interface 着地で解禁、`IterableIterator<V>` 型相当の中間型を `topaz_iter_<V>` として持ち、`next()` 経由で dispatch、(4) **`Array<fn>` 経路の `.map` callback 列**(self-hosting で AST visitor が visitor 関数の Array を持ちたいユースケース)、Array monomorph の elem type に fn を許可する拡張、(5) **plain Map RHS の bare for-of**(`for (const x of someMap)`)= destructuring 解禁とセットで `[K, V]` tuple を yield する仕様に揃える、(6) **Set / Map の iteration order**(JS は insertion order を保証、Topaz は hash order = open-addressing slot 順、divergence)、現状 documented divergence なし — 必要なら insertion-ordered map / set を別 type で導入(`OrderedMap<K, V>`)、(7) **iterator protocol**(`Symbol.iterator` / `next()` / `done` / `value`)= JS の prototype-based 機構をそのまま持ち込まず、Topaz 独自の `Iterator<T>` interface trait(`hasNext(): boolean` / `next(): T`)として再設計、self-hosting で必要になる generator(`function*()`)解禁とセット、(8) **`continue` / `break` への label**(`outer: for (...) { for (...) { break outer; } }`)= 現状 label 構文未対応、必要になれば構文 + label scope を導入、(9) **for-of body 内の `return`**(関数の中で for-of して early return)= 既に動作するが for-of 用の cleanup hook(将来 iterator close protocol)が必要になる時に再評価、(10) **for-of 用の binding capture**(arrow 内で for-of 変数を capture)= 1.5-3.5e の「ループ変数のライフタイム」宿題と同じで、現状 C local variable の再代入で全 arrow が最後の値を見る、closure 着地時に per-iteration alloc に書き換え。
