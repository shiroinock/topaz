# v0.1.3 release state handoff

This handoff records the non-mutating release-state boundary for the
`v0.1.3` runtime TS prelude checkpoint. It is for the case where repo-local
gates can be green at the intended checkpoint, but an existing final `v0.1.3`
tag may peel to a different commit.

Do not treat this document as approval to create, delete, move, push, trust, or
force-move any release tag. Do not edit, trust, reuse, or publish any GitHub
Release from this handoff alone.

## Local Gate Snapshot

Run the local gates from the intended release commit:

```sh
pnpm run build
pnpm test
pnpm run build:release
```

These commands prove only local readiness. They do not prove that a final tag
or draft Release belongs to this commit.

## Final Tag Comparison

Compare the final tag with the intended `HEAD` immediately before trusting any
final `v0.1.3` tag, draft Release, assets, or release notes:

```sh
tag="v0.1.3"
head_commit=$(git rev-parse HEAD)
tag_commit=$(git rev-parse "${tag}^{commit}")

if [[ "${tag_commit}" != "${head_commit}" ]]; then
  echo "STALE FINAL TAG: ${tag} points at ${tag_commit}, not HEAD ${head_commit}" >&2
  echo "Do not push the stale tag." >&2
  echo "Do not reuse the draft Release." >&2
  echo "Do not silently switch to v0.1.4 or any other release vehicle." >&2
  exit 1
fi
```

If `git rev-parse "${tag}^{commit}"` fails because the tag is absent, this
handoff still does not create it. Return to the normal release workflow and ask
for explicit release intent before creating a tag.

## STALE FINAL TAG

If the final `v0.1.3` tag exists and does not peel to the current `HEAD`, stop.
The release operator must choose one of these human-owned actions:

- Give explicit human approval to change local-only `v0.1.3` tag state, but
  only after confirming the tag is not public or trusted.
- Choose and document a new patch/RC release vehicle in a later
  version-allocation phase.
- Defer publication and start the v0.2 track only after recording that no final
  runtime checkpoint release was cut from the current `HEAD`.

Do not push a stale tag. Do not reuse the draft Release associated with a stale
tag. Do not silently switch to v0.1.4, `v0.1.4-rc.1`, or any other tag without
an explicit version-allocation/release-intent decision.

## Allowed Next Actions

Allowed next actions are intentionally procedural and human-owned:

- If the tag is known to be local-only and untrusted, ask for explicit human
  approval before changing local tag state.
- If the release still needs a vehicle, record a new patch/RC release vehicle
  in a later version-allocation phase.
- If the runtime checkpoint will not be published from this commit, defer
  publication and record that result before starting the v0.2 release track.
  In short: defer publication until that choice is explicit.

This handoff changes no runtime behavior, CLI behavior, artifact name, checksum
format, package version, tag, or GitHub Release.
